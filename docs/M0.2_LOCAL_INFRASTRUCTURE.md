# Work Item M0.2 — Local Infrastructure

## 1. Status

- Milestone: M0 — Repository Foundation
- Status: Ready for review
- Execution order: After M0.1 is implemented and accepted
- Primary outcome: A developer can reliably start and verify local PostgreSQL and Mailpit services without production credentials or cloud infrastructure.

## 2. Outcome

Add the local-development infrastructure required by later milestones:

- PostgreSQL in Docker Compose.
- Mailpit in Docker Compose for captured development email.
- Persistent local PostgreSQL storage.
- Health checks for both services.
- Loopback-only host port bindings.
- Typed environment-variable validation.
- A private, ignored local document-storage directory.
- Documented `pnpm` commands to start, stop, inspect, and verify infrastructure.

The Next.js application and future worker continue running directly on the developer’s host. This task must not containerize the application.

## 6. In Scope

### 6.1 Docker Compose file

Create `compose.yaml` containing exactly these Release 1 local services:

- `postgres`
- `mailpit`

Do not add the web application, worker, Redis, object storage, reverse proxy, monitoring stack, or administration GUI.

### 6.2 PostgreSQL service

Use the official PostgreSQL image.

Requirements:

- Pin a current supported stable PostgreSQL 18 patch/image variant available at execution time.
- Record the selected tag in the completion report.
- Do not use a floating `latest` tag.
- Bind the host port to `127.0.0.1` only.
- Default host port: `5432`, configurable through a local Compose interpolation variable.
- Use an obvious local-only database name, user, and password.
- Use a named Docker volume for persistence.
- For PostgreSQL 18+, mount the volume at the official image’s supported parent location so the version-specific `PGDATA` layout persists correctly.
- Add a `pg_isready` health check using escaped container environment variables.
- Set a deterministic project/container/service naming approach without globally common container names that cause collisions.
- Do not enable trust authentication for host connections.
- Do not expose PostgreSQL on all interfaces.

Recommended local-only values:

```text
Database: psa_hiring
User: psa_local
Password: psa_local_only_change_me
Host: 127.0.0.1
Container port: 5432
```

These values must be prominently labeled as local development defaults and must never be used in staging or production.

### 6.3 Mailpit service

Use the official `axllent/mailpit` image.

Requirements:

- Pin a current stable version tag available at execution time.
- Do not use `latest`.
- Bind SMTP and web UI host ports to `127.0.0.1` only.
- Default SMTP host port: `1025`.
- Default web UI host port: `8025`.
- Add a health check using Mailpit’s documented `/readyz` endpoint or its supported built-in health-check mechanism.
- Mailpit must capture messages locally and must not relay to external recipients.
- Do not add authentication/TLS complexity to the local Mailpit instance unless required by its current image health behavior.
- Do not configure any real SMTP credential, domain, recipient, or provider.

### 6.4 Volumes and network

- Declare one named volume for PostgreSQL data.
- Use the Compose project’s default private network or one explicitly named project-scoped network.
- Do not mount source code, `.env.local`, the Docker socket, home directories, or arbitrary host paths into either service.
- Do not persist Mailpit messages unless a tested business-development need is approved; ephemeral captured email is preferred.

### 6.5 Typed environment configuration

Add Zod as the approved runtime validation dependency if not already present.

Create a server-only configuration module, for example:

```text
src/config/server-env.ts
```

The module must:

- Define the environment schema once.
- Parse from an explicit input such as `process.env`.
- Return a typed immutable configuration object.
- Provide concise errors naming missing/invalid variable names without printing secret values.
- Prevent accidental browser/client import through project convention and a server-only guard when appropriate.
- Avoid reading environment values at module-import time if that would break Next.js build phases unnecessarily.
- Avoid exporting the raw environment object.

Validate at least:

| Variable | Rule | Example |
|---|---|---|
| `APP_ENV` | `local`, `test`, `staging`, or `production` | `local` |
| `DATABASE_URL` | Valid PostgreSQL URL | Local Docker URL |
| `SMTP_HOST` | Nonempty host | `127.0.0.1` |
| `SMTP_PORT` | Integer 1–65535 | `1025` |
| `SMTP_FROM` | Syntactically valid safe development address | `no-reply@example.test` |
| `DOCUMENT_STORAGE_ROOT` | Nonempty local path in local mode | `./.local/documents` |
| `PROVIDER_MODE` | `fake` or `production` | `fake` |

Required cross-field rules:

- `APP_ENV=production` must reject `PROVIDER_MODE=fake`.
- `APP_ENV=production` must reject local-loopback database/SMTP endpoints and the repository-local document path.
- Validation errors must not echo credentials embedded in URLs.

Do not add production secrets or decide the production configuration provider.

### 6.6 Environment example

Create or update `.env.example` with:

- Every M0.2 variable.
- Safe local-only placeholder values.
- Comments clearly stating that it contains no production secrets.
- The database URL corresponding to the Compose local defaults.
- Mailpit SMTP host/port and `example.test` sender.
- The private local document path.
- Fake-provider mode.

Do not create, commit, or overwrite `.env`, `.env.local`, or any developer-specific environment file.

### 6.7 Configuration-check script

Add a TypeScript script such as:

```text
scripts/check-env.ts
```

Add:

```text
pnpm config:check
```

The command must load the developer’s local environment using the pinned Node/TypeScript execution approach and validate it through the same server environment schema used by application code.

If the project adds `tsx` solely to execute TypeScript scripts, place it in `devDependencies` and document the reason.

The command must:

- Exit zero with a concise success message for valid configuration.
- Exit nonzero with safe actionable variable errors for invalid configuration.
- Never print the database password or a complete credential-bearing URL.

### 6.8 Private local document directory

Add a small cross-platform Node script such as:

```text
scripts/setup-local.ts
```

Add:

```text
pnpm local:setup
```

The command may:

- Create the configured local document-storage directory when it is safely inside the repository’s approved `.local/` area.
- Refuse broad, root, home-directory, parent-traversal, or `public/` paths.
- Leave an existing directory unchanged.

It must not:

- Copy `.env.example` over an existing local environment file.
- Create sample candidate documents.
- Delete or empty any directory.
- Make the directory web accessible.

Ignore `.local/` completely in Git.

### 6.9 Infrastructure commands

Add cross-platform `package.json` scripts or Node wrappers for:

| Command | Behavior |
|---|---|
| `pnpm infra:up` | Start PostgreSQL and Mailpit in detached mode and wait/report health |
| `pnpm infra:down` | Stop containers while preserving the PostgreSQL volume |
| `pnpm infra:status` | Show service status/health |
| `pnpm infra:logs` | Show/follow scoped local service logs without exposing secrets |
| `pnpm infra:check` | Verify PostgreSQL port/readiness and Mailpit `/readyz` |
| `pnpm local:setup` | Safely create the private local document directory |
| `pnpm config:check` | Validate typed environment configuration |

Do not add a routine script that destroys volumes. If a database reset procedure is documented, it must be clearly manual, destructive, local-only, and separate from normal start/stop commands.

### 6.10 Infrastructure verification script

If `infra:check` uses a Node script, it should:

- Verify Docker Compose reports both services healthy.
- Verify the configured PostgreSQL host/port is reachable without logging credentials.
- Verify Mailpit’s readiness endpoint returns success.
- Use bounded timeouts.
- Exit nonzero with a concise service-specific error.
- Avoid adding a PostgreSQL application driver before M0.3 solely for this check.

It is acceptable to use `docker compose exec -T postgres pg_isready` plus Mailpit HTTP readiness through a safe wrapper.

### 6.11 README update

Update the root `README.md` with:

- Docker/Compose prerequisites.
- Copy/create-local-environment instructions that never overwrite an existing file.
- `pnpm local:setup`.
- `pnpm config:check`.
- `pnpm infra:up`, `infra:status`, `infra:check`, `infra:logs`, and `infra:down`.
- PostgreSQL local connection summary without encouraging password reuse.
- Mailpit UI URL: `http://127.0.0.1:8025` using the default port.
- Statement that the application/worker run on the host.
- Statement that M0.2 does not yet create database tables or send application email.
- Troubleshooting for occupied ports, Docker unavailable, unhealthy service, and stale local volume after an explicitly approved major-version change.
- A warning that normal `infra:down` preserves data.

## 9. Compose Requirements

The final Compose configuration must satisfy:

- `docker compose config` succeeds.
- Service names are `postgres` and `mailpit`.
- Images use stable versioned tags.
- No service uses `privileged: true`.
- No Docker socket mount.
- No host-network mode.
- Host ports bind to `127.0.0.1`.
- PostgreSQL data uses a named volume.
- Health checks have bounded interval, timeout, start period, and retries.
- Local password is not passed as a command-line argument visible through normal process listings when avoidable.
- Container logs do not print the complete `DATABASE_URL`.
- Stopping with `docker compose down` does not remove the named database volume.

Do not set an obsolete top-level Compose `version` key unless current Compose documentation requires it.

## 10. Environment-Safety Rules

- `.env.example` is committed; `.env`, `.env.local`, and environment variants containing local values are ignored.
- No script prints all of `process.env`.
- No variable with a secret value uses the `NEXT_PUBLIC_` prefix.
- Client components may not import server configuration.
- No default configuration silently falls back to production.
- `APP_ENV` and `PROVIDER_MODE` must be explicit.
- Production/fake incompatibility fails closed.
- Local credentials must contain wording that discourages reuse.
- The application must not need Docker credentials beyond those already configured on the developer’s machine.

## 11. Tests Required in This Task

M0.4 will establish the main test framework, so do not install Vitest yet. Use executable script checks and isolated Node assertions where practical.

At minimum verify:

- Valid local environment passes.
- Missing `DATABASE_URL` fails safely.
- Invalid SMTP port fails.
- Credential-bearing invalid URL does not appear in error output.
- `APP_ENV=production` plus `PROVIDER_MODE=fake` fails.
- Production with loopback database/SMTP or `.local` document path fails.
- Safe `.local/documents` setup succeeds and is idempotent.
- Root, home, parent traversal, and `public/` document paths are refused.
- `docker compose config` passes.
- Both containers become healthy.
- Mailpit readiness endpoint succeeds.
- PostgreSQL readiness succeeds.
- `infra:down` preserves the named volume.

If a check cannot be automated without adding premature tooling, document and run it manually.

## 12. Acceptance Criteria

### AC-M0.2-01 — M0.1 remains healthy

Given the accepted M0.1 application, when M0.2 is complete, then lint, typecheck, format-check, and production build still pass without UI or route regressions.

### AC-M0.2-02 — Compose configuration

Given the repository, when `docker compose config` runs, then it succeeds and contains only the approved PostgreSQL and Mailpit services plus the PostgreSQL named volume.

### AC-M0.2-03 — Loopback-only exposure

Given the resolved Compose configuration, then PostgreSQL, Mailpit SMTP, and Mailpit UI host ports are bound to `127.0.0.1`, not all network interfaces.

### AC-M0.2-04 — Healthy local services

Given Docker is running, when `pnpm infra:up` completes, then PostgreSQL and Mailpit reach healthy status within bounded time and `pnpm infra:check` passes.

### AC-M0.2-05 — Persistent local database

Given PostgreSQL has been started and stopped with normal `infra:down`, when it is started again, then its named volume remains present and no automatic data deletion occurs.

### AC-M0.2-06 — Captured email only

Given Mailpit is running, then the local SMTP port and UI are reachable, no external relay is configured, and no real provider credential exists.

### AC-M0.2-07 — Valid typed configuration

Given safe local values based on `.env.example`, when `pnpm config:check` runs, then it exits successfully and returns no secret values.

### AC-M0.2-08 — Invalid configuration fails safely

Given missing, malformed, or prohibited environment combinations, when configuration is checked, then it exits nonzero with actionable variable names but without echoing credentials.

### AC-M0.2-09 — Production rejects local/fake configuration

Given `APP_ENV=production`, when fake providers, loopback infrastructure, or repository-local document storage is configured, then validation fails closed.

### AC-M0.2-10 — Private local documents

Given the approved `.local/documents` configuration, when `pnpm local:setup` runs, then the directory is safely created outside `public/`, remains ignored by Git, and repeated execution does not delete or overwrite content.

### AC-M0.2-11 — Developer documentation

Given a new developer with Docker available, when they follow `README.md`, then they can prepare configuration, create local directories, start, verify, inspect, and stop the infrastructure without undocumented commands.

### AC-M0.2-12 — Scope containment

Given the completed change, when dependencies, services, routes, and source files are reviewed, then no database ORM/schema, authentication, email-sending logic, worker, object-storage emulator, cloud resource, application container, or hiring feature has been added.
