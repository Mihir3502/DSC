## 1. Summary

A candidate can upload a resume or credential, replace it, download it, and remove it from their application. Each file is size- and type-checked, quarantined under a generated key, scanned, and only then moved to private storage. Every upload, refusal, scan result, removal, and download is audited.

The malware scanner is a **test double that flags only the EICAR test string**, and storage is a local directory. No production scanner or storage provider is approved, so **real files aren't protected yet**, and production mode refuses uploads rather than storing them unscanned.

## 4. Model and behavior

- **Versions:** each upload is an immutable version. It starts `PENDING`, finishes once as `CLEAN`, `REJECTED`, or `FAILED`, and can't change afterward (triggers).
- **Current version:** moves only to this document's clean version, so a failed replacement leaves the earlier file in place.
- **Validation:** size, allowed extension, declared type, then file signature. The stored type comes from the bytes. Display names lose paths and unsafe characters, and storage keys are generated UUIDs.
- **Malware:** bytes are discarded, and the version row stays as evidence. **Scanner failure:** bytes stay in quarantine, and the file is unavailable.
- **Removal:** hides the document. Its record, versions, and stored bytes stay.
- **Download:** passes the M1.5 document gate, commits its audit event, then reads the bytes. The response is an attachment with a closed content type, `nosniff`, a sandbox CSP, and `no-store`.
- **Upload protection:** same-origin check, declared length required and bounded before the body is read, exact form fields, and a per-account rate limit.

## 8. Not met or not tested

- **Real malware scanning:** none. The test scanner recognizes only EICAR, and PDF active content isn't inspected.
- **Production storage and encryption:** none. The local directory has owner-only permissions but no application-level encryption, so it must hold synthetic data only.
- **Stuck `PENDING` versions:** if the server stops between receipt and scan, the version stays `PENDING` with no retry job. It stays unavailable, and the candidate can upload again.
- **Quarantine cleanup:** `FAILED` files stay in quarantine with no cleanup job, and a crash can leave orphaned files.
- **Server limits:** rate limits are per process, and downloads read the whole file into memory (10 MB at most).
- **Person merge with attachments:** not tested. Documents reference the candidacy, which keeps its ID.
- **Auditors:** covered at the catalog level only, and no route exists for them.
- **`document_link` and `document_access_event`:** not created. Audit records access, and the data model says so.
- **Required attachments:** none are required, because no spec requires one. M2.6's whole-application validation needs this confirmed.
- **Manual verification (§18):** not done, including screen readers and real devices.
- **`color-contrast` failure:** the intermittent failure from M2.2 hasn't recurred, but its cause is unknown. One component test (`staff-auth-forms`, a focus assertion) also failed once while the machine was busy and passed on every rerun, with no cause established.
