## 1. Summary

Staff can read a submitted application and return it, selecting sections to reopen, optionally flagging fields, choosing a reason, and writing instructions the candidate will see. The candidate is emailed, reads the instructions after signing in, and starts a correction: a new version pre-filled from what they submitted, with only the reopened sections editable. Resubmitting re-certifies, creates a new frozen record and receipt, and marks the earlier version superseded. Every submission is kept.

## 4. Model and behavior

- **One transaction** covers the return record, version status, stage change and history, task swap, outbox row, audit event, and idempotency receipt.
- **Version lifecycle** (trigger): `DRAFT`, `SUBMITTED` with its frozen record, `RETURNED` with its return, then `SUPERSEDED` once a correction is submitted. Anything else is refused.
- **Reopening is enforced on the server:** closed sections are refused on save and return not-found on read, and attachments can change only if reopened.
- **Instructions** live only on the return record, shown as plain text. They never reach audit or email.
- **Prior submissions** stay frozen and append-only, and staff see the last frozen submission while a correction is drafted, never the draft.
