## 1. Summary

A signed-in candidate now lands on `/candidate`, which shows their application status, one next step, and task counts. They can move between Home, Application, My Tasks, Security, and Help, and can switch applications when they have more than one. A new `work_item` table tracks the "Complete your application" task. It never decides candidacy state.

**Out of order:** M2.3 was built after M2.4, at the project owner's direction. The Application destination is therefore M2.4's overview page, and the next-action link goes there instead of to a read-only placeholder.

## 4. Model and behavior

- **Status mapping:** one exhaustive registry. Unknown stages or statuses fail closed to "Status unavailable" and log a safe code.
- **Next action:** one result, revalidated against the candidacy. If the task row is missing, the stage still produces the same action. No due date is invented, and no percentage appears.
- **Context selection:** follows packet §7.4, deterministically. A reference that isn't the candidate's own returns one safe not-found, with no fallback data.
- **`work_item`:** one active item per candidacy, type, and target (partial unique index). It holds no stored text or URLs, its identity is immutable, finished items are final, and each update adds one version. RESTRICT foreign key. The runtime role has no `DELETE` or `TRUNCATE`.
- **Task lifecycle:** opened in the same transaction as the stage change, backfilled by migration, and repaired by reconciliation, which is bounded, repeatable, and reports counts only. Pages never write. Completion belongs to M2.6, so today a task stays open.
- **Navigation:** implemented routes only. Documents, Messages, Training, and a notification indicator are absent.

## 5. Evidence

`tests/integration/candidates/portal.test.ts` proves:

- Anonymous, staff, and disabled sessions are refused on every portal query.
- Zero, one, and many candidacies render correctly, and exact projections expose no internal ID or code.
- Another candidate's reference, an unknown one, and malformed ones all get the same result.
- One task opens per start; an unowned candidacy gets none.
- A stale task is hidden on read and unchanged until reconciliation cancels it, and a second reconciliation changes nothing.
- Reads change no task, candidacy, draft, or audit row.
- The runtime role and triggers refuse deletes, duplicates, identity changes, and edits to finished tasks.

Browser tests cover sign-in to next action, task filters, an invalid filter, sign-out followed by Back, `no-store` headers, the empty state, and cross-candidate 404s. Accessibility tests cover axe, the mobile menu's state, Escape, and focus return, 320 px reflow, and 44 px targets in the menu.

## 7. Defects found and fixed

- WebKit logged cancelled background prefetches as page errors. Turning prefetch off cleared them in two straight three-browser runs. That they were harmless cancellations is the likely explanation, not a proven one.
- The shell added a second "Sign out" button and extra list items to the security page. The duplicate button was removed, and the sessions list now has an accessible name.
- Older tests expected the old sign-in landing page, the old status wording, and a public `/candidate`, and were updated. The public-page checks now run against `/sign-in`, so the removed page's own coverage is gone with it.

## 8. Not met or not tested

- **Dual-role accounts:** not tested, because account types are exclusive in the current model. Staff sessions are refused.
- **Ownership change or merge after render:** not tested against the portal. Queries re-read ownership on every request.
- **Service-worker checks:** not tested. None is registered.
- **Unknown-status logging:** the fail-closed mapping is tested, but the log line is not.
- **Loading states:** no dedicated `loading.tsx` was added. Pages are server-rendered, and errors use the existing fallback.
- **Modal menu behavior:** the mobile menu is a disclosure, not a modal, so it doesn't contain focus. The packet allows this "where appropriate".
- **Landmark placement:** the navigation sits inside `<main>`, because the shared shell owns the header.
- **Start confirmation:** after starting, candidates still see the confirmation page with a link to continue, rather than a direct redirect.
- **Task assignee and completion-event columns:** deferred until staff tasks and completion commands exist.
- **"Get started" status:** not registered, because the claim path it needs was deferred in M2.2.
- **Manual verification (§31):** not done, including screen readers, real devices, iOS Safari, and Android Chrome.
- **`color-contrast` failure:** the intermittent failure from M2.2 hasn't recurred, but its cause is still unknown.
