## 1. Summary

Scoped staff can now see their work on a dashboard and a filtered, paged queue, take or assign responsibility for a candidate, and set a due date on staff work. Candidates see none of this. Nothing here moves a candidate through the hiring stages.

**Engineering assumptions for you to confirm:**
- "My team" means candidates on a team where the staff member holds a team-scoped role. A branch-scoped recruiter has no team, so that option is hidden.
- The queue is read by Recruiter, HR, and PSA Manager. Compliance and classification reviewers, auditors, and administrators don't get it.
- "Assigned to me" reads the candidate's owner rather than a per-task assignee.
- Owner-change reasons are Balancing workload, Covering for someone away, Staff role changed, and Correcting an earlier assignment.
- A due date is a calendar day ending at the end of that day in UTC, from today through one year ahead.
- Scoped staff see an owner's name. Earlier screens said only "Another staff member".

- **Auditor:** no integration run with a real audit assignment. Denial is proven by the role-permission matrix and the grant test.
- **Staff member's own candidacy:** the query excludes it, but no integration test covers it, because the database only lets candidate accounts own a person record.
- **Mass assignment:** the new forms use the shared exact-field parser, and commands read only named fields. No new test sends extra fields through the Server Actions.
- **Migration with data:** `0012` was applied from empty in test databases. It was not upgrade-tested over a populated M2 database. No production data exists.
- **Timing:** equal response times for hidden and missing records aren't measured.
- **Staff journey on a phone:** the staff screens were checked for reflow at 320 px, but the staff journey ran on desktop viewports only.
- **Rate limits:** the new commands and queue reads have none, in line with other staff commands except prospect creation and application return. This needs security review.
- **Departed owners:** if an owner loses access, they stay listed until a manager changes it. Nothing flags this.
- **Notifications:** a new owner isn't told, because notifications aren't in this item's deliverables. The confirmation dialog says so.
- **Known noise:** expected cross-origin refusals are logged as `INTERNAL.UNEXPECTED` (M2 exit report §6). This is unchanged.
