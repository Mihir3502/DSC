# ADR-0002 — Authentication Persistence

- **Status:** Accepted, pending recorded project approval (see Approvals)
- **Date:** 2026-10-06
- **Work item:** M1.1 (`docs/tasks/M1.1_ACCOUNT_AUTHENTICATION_SCHEMA.md`)
- **Depends on:** ADR-0001. Note: the M0 exit-gate items (ADR-0001 approvals and the second-person setup check) were still open when M1.1 started; the project owner directed work to continue on 2026-10-06.

## Context

Release 1 needs candidate and invitation-only staff identities, verified-email state, account controls, and revocable sessions (`PRODUCT_REQUIREMENTS.md`, `SECURITY_AND_PRIVACY.md` §7–9). ADR-0001 selected Better Auth with the Drizzle adapter, where authentication establishes identity and the application owns authorization.

## Decision

### One authoritative account

The Better Auth `user` table **is** the conceptual `user_account` (`DATA_MODEL.md` §4.1). There is no second application user table. Application-owned fields are added to it through Better Auth `user.additionalFields`, declared `input: false, returned: false`. Sign-up and update request bodies can't set them, and auth responses don't return them:

| Field | Type / rule |
|---|---|
| `email` | Normalized login email (trim, NFC, lowercase, ASCII, ≤254), unique, `CHECK email = lower(btrim(email))` |
| `email_display` | Entered form, display only, never used for equality |
| `account_type` | `CANDIDATE`, `STAFF`, or `SERVICE` (CHECK), required, no default |
| `status` | `INVITED`, `ACTIVE`, `LOCKED`, `DISABLED`, or `CLOSED` (CHECK), required, no default |
| `email_verified` | Better Auth boolean; independent of status |
| `last_authenticated_at` | Set when a session is created |
| `disabled_at`, `disabled_reason_code` | Required exactly when status is `LOCKED`/`DISABLED`/`CLOSED` (coherence CHECK); reason codes `SECURITY_LOCK`, `ADMINISTRATIVE_DISABLE`, `ACCOUNT_CLOSED` |
| `version` | Optimistic-concurrency integer, incremented by restriction commands only |

IDs are native UUIDs generated by PostgreSQL (`gen_random_uuid()`, built in; no extension). Timestamps are `timestamptz`.

### Ownership

| Concern | Owner |
|---|---|
| Password hashing and credential linkage (`auth.account`) | Better Auth (its maintained hasher; no custom crypto) |
| Session tokens and lifecycle (`auth.session`) | Better Auth, database-backed |
| Email-verification tokens | Better Auth |
| Account type/status, restriction policy | Identity-access module (`src/modules/identity-access`) |
| Roles, permissions, scopes | M1.4 (Better Auth admin/roles plugins are **not** used) |
| Route/object/field authorization | M1.5 |
| Immutable business/security audit | M1.6 |

### Schema namespace and migrations

- Tables `auth.user`, `auth.account`, `auth.session`, `auth.verification` live in a dedicated PostgreSQL schema `auth`, using the Drizzle adapter's supported `schemaName` option.
- Drizzle TypeScript (`infrastructure/auth-schema.ts`) is the source of truth. It started from `auth generate` (pinned CLI `auth@1.7.7`) and was reviewed. `pnpm auth:schema:check` validates it against the runtime options in CI.
- The reviewed migration is `drizzle/0001_authentication_foundation.sql`, applied by the migration role. The Better Auth `migrate` command and `drizzle-kit push` are never used. `pnpm db:check-drift` fails CI when the schema and committed migrations differ.
- Foreign keys from `session`/`account` to `user` use `ON DELETE CASCADE`, as Better Auth generates. Account deletion isn't exposed (`deleteUser` is disabled, and the app role has no `DELETE` on `auth.user`/`auth.account`). Closed accounts are retained.

### Least privilege

The local bootstrap gives `psa_app` `USAGE` on `auth` and `SELECT/INSERT/UPDATE` on its tables, with `DELETE` only on `auth.session` and `auth.verification`. It has no `CREATE` and no journal access. Because table-specific grants need the tables to exist, the documented sequence is `db:bootstrap:local → db:migrate → db:bootstrap:local`. Missing grants fail closed: revocation errors rather than succeeding with too many privileges.

### Signup and account types

- Generic sign-up is disabled (`emailAndPassword.disableSignUp`). Candidate registration arrives in M1.2; staff accounts only through the M1.3 invitation flow.
- `account_type`/`status` have no defaults, so creation fails unless server code supplies valid values. A `user.create.before` hook refuses anything outside the closed sets.
- The `session.create.before` hook is the authoritative gate: no session is created for unknown, non-`ACTIVE`, or `SERVICE` accounts. A refused sign-in returns the same public response as a wrong password.

### Sessions and revocation

- Database sessions with `cookieCache` disabled, so every lookup hits PostgreSQL.
- Cookie `psa.session_token`: HttpOnly, SameSite=Lax, Path=/, no Domain. It's Secure (`__Secure-` prefix) for https origins and in staging/production.
- Expiry and refresh come from configuration (local defaults: 8 h expiry, 1 h refresh). JSON responses have `token`/`session.token` stripped, so tokens never reach browser JavaScript, URLs, or storage.
- `resolveCurrentAccount` validates the session through `auth.api.getSession`, then re-reads the account and resolves only `ACTIVE`, non-service accounts. The principal contains the ID, type, status, `emailVerified`, session ID, and `authenticatedAt` only.
- `revokeSession`, `revokeAllSessions`, and `lockAccount`/`disableAccount`/`closeAccount` run in **one transaction** on the runtime connection: `SELECT … FOR UPDATE`, policy and version check, status update, and session deletion. They're idempotent, and results contain only safe codes and the account ID.
- A sign-in racing a restriction may insert a session after the restriction commits; the resolver's authoritative status recheck still rejects it.

### Email verification (accepted risk — superseded)

> **Superseded by ADR-0003 (M1.2, 2026-10-06):** email verification now uses Better Auth's email-OTP plugin with hashed, single-use, attempt-limited codes, and the verification-link endpoints are disabled. The text below records the M1.1 decision.

Better Auth 1.7.7 verification links are **stateless HS256 JWTs**. They're signed with the auth secret, carry the email, expire after `AUTH_VERIFICATION_EXPIRES_IN_SECONDS` (default 1 h), and aren't stored.

They are **single-effect, not single-use**: replaying a valid link before it expires returns "already verified" with no state change and no session (`autoSignInAfterVerification` is off, and email change is disabled). The project owner accepted this on 2026-10-06 over switching to the email-OTP plugin. Revisit if verification starts granting anything beyond the boolean.

Database-backed single-use records (`auth.verification`, atomically consumed through `consumeVerificationValue`) are used by Better Auth for flows such as password reset (M1.2). M1.1 sends no email: the default delivery adapter refuses, and an in-memory capture adapter exists for `APP_ENV=test` only.

### Configuration

`BETTER_AUTH_SECRET` must be ≥32 characters, and placeholder or test markers are rejected outside test; generate it with `openssl rand -hex 32`. `BETTER_AUTH_URL` and `AUTH_TRUSTED_ORIGINS` take exact http(s) origins with no wildcards, and must be https and non-loopback in staging/production. Session, verification, and rate-limit values are bounded. Better Auth telemetry is explicitly disabled. Library log messages are replaced by a fixed event code.

## Open decisions

- **Session timeout policy** for candidates and staff (idle and absolute): local defaults only, not approved for production.
- **Distributed rate-limit store:** rate limiting uses per-process memory, so staging/production auth startup is **refused** until a store is chosen with the hosting decision.
- **Compromised-password checking:** M1.2 added a port with a local denylist only (ADR-0003); a privacy-preserving production provider is still undecided, so production-like startup fails closed.
- **Internationalized email addresses:** login emails are ASCII because Better Auth's sign-in validator accepts ASCII only.
- **Staff MFA** (M1.3) and **recent-authentication enforcement**: implemented by ADR-0004 (staff only; business actions adopt the primitive in later work items).

## Consequences

**Positive:** a single source of truth for identity; library-maintained credential and session security; immediate, transactional revocation; schema drift caught in CI.

**Negative:** coupling to Better Auth's table shapes and upgrade cadence. The two-pass grant bootstrap is an extra local step. Verification links can be replayed (no effect) until they expire.
