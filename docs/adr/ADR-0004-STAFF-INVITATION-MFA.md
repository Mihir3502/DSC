# ADR-0004 — Staff Invitation, MFA, and Recent Authentication

- **Status:** Accepted, pending recorded project approval (see Approvals)
- **Date:** 2026-10-06
- **Work item:** M1.3 (`docs/tasks/M1.3_STAFF_INVITATION_MFA.md`)
- **Depends on:** ADR-0001, ADR-0002, ADR-0003
- **Consumed by:** ADR-0005 (M1.4 authorization composes the assurance primitive into permission-level named recent-auth requirements and adds inline-only purposes)

## Context

Staff accounts are invitation-only. Every staff account must use multifactor authentication, and later high-risk commands need server-verifiable recent authentication (`SECURITY_AND_PRIVACY.md` §7.1, §7.3–7.5, §8; `ROLE_PERMISSION_MATRIX.md` §15.2; PRD-AUTH-001/004).

Roles, scopes, authorization adapters, and immutable audit arrive in M1.4–M1.6. M1.3 therefore cannot let anyone administer staff in production yet.

## Decisions

### MFA for every staff account, through Better Auth's two-factor plugin

M1.3 cannot yet tell privileged staff from other staff (roles arrive in M1.4), so MFA is required for every `STAFF` account.

The plugin is `better-auth/plugins/two-factor` from the pinned `better-auth@1.7.7`. It was verified against the installed source on 2026-10-06.

| Concern | Configuration / behaviour |
|---|---|
| Factor | TOTP: 6 digits, 30-second period, ±1-step window (fixed by the library, not client controlled). Issuer is the reviewed constant `PSA Workforce Hiring`, never taken from input. |
| Enrollment | `skipVerificationOnEnable: false`. `twoFactorEnabled` becomes true only after the first valid code. |
| TOTP seed at rest | `auth.two_factor.secret` holds XChaCha20-Poly1305 ciphertext from Better Auth's `symmetricEncrypt`, keyed by the auth secret (versioned envelope). |
| Backup codes | 10 codes of 10 random alphanumeric characters (`xxxxx-xxxxx`, about 59 bits each), generated by the plugin and stored encrypted as above. |
| Backup-code consumption | Each code is consumed with a compare-and-set update, so it works once. |
| Backup-code regeneration | Replaces every earlier code. |
| Code viewing | `viewBackupCodes` and `generateTOTP` are `serverOnly` and are connected to nothing. |
| Lockout | Each challenge allows 5 attempts. Failures across TOTP and backup codes share one per-account counter: after `AUTH_STAFF_MFA_MAX_FAILURES` (default 5) the account is locked for `AUTH_STAFF_MFA_LOCKOUT_SECONDS` (default 900 s). Reauthentication has no library lockout, so an application limiter (5 per 15 minutes per account) applies there. |
| Email/SMS OTP | No `otpOptions.sendOTP` is configured, so OTP cannot be enabled or sent. Every `/two-factor/*` HTTP path, and `/verify-password`, is in `disabledPaths`, and the `/api/auth` route forwards only `GET /get-session`. |
| Trusted devices | Disabled by policy. Application commands never send `trustDevice`, every staff call strips any incoming `trust_device` cookie, and `trustDeviceMaxAge` is set to 1 second as defense in depth. |
| QR code | Rendered on the server from the `otpauth` URI with `uqr@0.1.3` (zero dependencies, local, no network) as an SVG path. The text setup key is always shown beside it. |

**Replay.** The plugin verifies TOTP statelessly, so a code could be accepted twice within its window. NIST SP 800-63B requires single acceptance. The application therefore records an HMAC digest of every presented code per account in `auth.totp_replay_guard` before verification, for 4 periods. A repeated code is refused. No TOTP is computed by the application.

**Key dependency and rotation.** TOTP seeds and backup codes are protected by the same auth secret as sessions.

- **Rotation:** use Better Auth's versioned `secrets` configuration. Retiring a key that still encrypts enrollments makes those seeds unreadable, so a rotation plan must re-encrypt them or force reenrollment.
- **Backups:** must preserve the key ↔ data pairing.
- **Separation:** each environment has its own secret. Test and placeholder secrets are rejected outside `APP_ENV=test` (ADR-0002).

### Passkey evaluation (not adopted)

Better Auth's maintained passkey plugin (`@better-auth/passkey`, current docs, verified 2026-10-06) provides passwordless primary sign-in. Its default `userVerification` is `"preferred"`. It has no integration with the two-factor plugin as a second factor or step-up within the password flow.

Using it would mean either passwordless login, which must not be labelled MFA without approved user-verification semantics, or custom protocol glue, which is prohibited. Passkeys are deferred. They remain the preferred phishing-resistant direction for a future, approved work item.

### Server-declared session issuance and assurance

- Better Auth's `session.create.before` hook stays the single authoritative gate. It calls the pure `decideSessionIssuance(account, intent, now)`, where the intent is declared by the running application command through an `AsyncLocalStorage` context. Nothing from a request can set it.
  - **No intent:** only candidate sessions (`STANDARD`, M1.2 rules). A staff session is refused.
  - **`STAFF_FIRST_FACTOR`:** an ACTIVE, verified, MFA-enrolled staff account. The resulting session is deleted immediately by the plugin's two-factor hook, which issues its signed, short-lived (`AUTH_STAFF_MFA_CHALLENGE_SECONDS`) challenge cookie instead.
  - **`STAFF_ACTIVATION`:** an INVITED staff account inside an invitation-bound activation. This enrollment-only session never resolves a principal.
  - **`STAFF_MFA`:** an ACTIVE, MFA-enrolled staff account after a verified second factor.
- Each session row carries server-owned assurance columns: purpose, method (`PASSWORD`, `PASSWORD_TOTP`, `PASSWORD_BACKUP_CODE`), first-factor time, MFA time, account version, and purpose-bound reauthentication (time, method, purpose). CHECK constraints keep them coherent. They are `input: false, returned: false`.
- The first-factor time is recorded in a server-side challenge record. Its identifier is a SHA-256 digest of the plugin's signed challenge cookie, stored hashed in `auth.verification`. The second-factor command reads the account and time from that record, never from the client.
- `resolveCurrentAccount` resolves a staff principal only for a `STAFF` session with an MFA method, whose account version is current, on an account with `twoFactorEnabled`.
  - Any account-version increment invalidates all issued assurance. Restriction, MFA reset, and staff password change all increment it.
  - Session revocation removes the evidence with the session.
- Better Auth's `freshAge` is not used for this: it measures only session creation.

### Recent-authentication primitive

`evaluateAssurance(evidence, request)` lives in `domain/authentication-assurance.ts`, framework-neutral. It returns `ALLOW`, `CHALLENGE`, or `DENY` with a safe reason.

| Policy | Satisfied by |
|---|---|
| `NORMAL_STAFF_SESSION` | Any MFA-complete staff session |
| `RECENT_STAFF_AUTH` | An MFA event (TOTP or backup code) younger than `AUTH_STAFF_RECENT_AUTH_SECONDS` (default 300 s) |
| `RECENT_STRONG_AUTH` | A password + TOTP event within the interval. Backup codes never qualify. |

- **Strict boundary:** an event exactly the interval old is not recent.
- **Sign-in time:** a sign-in event is dated by the older of its password and MFA times.
- **Skew:** future-dated evidence beyond 5 seconds of skew is denied.
- **Purpose binding:** a purpose-bound request counts only reauthentication recorded for that purpose. Purposes come from a closed registry (`STAFF_SECURITY`, `CHANGE_PASSWORD`, `REGENERATE_BACKUP_CODES`). Unknown keys and URLs fall back to `/staff/security`.
- **Reauthentication:** `/staff/reauthenticate` checks the current password and a TOTP code (no backup code). It then records evidence on the current session only, without changing its token or expiry.
- **Uses in M1.3:**
  - Staff password change requires `RECENT_STAFF_AUTH`, then ends every session and increments the account version.
  - Backup-code regeneration uses an inline password + TOTP step-up and `RECENT_STRONG_AUTH` bound to `REGENERATE_BACKUP_CODES`.
  - Business commands adopt the primitive in their own work items.

### Staff invitations

- **Table:** `auth.staff_invitation`.
  - **Statuses:** `PENDING`, `ACCEPTED`, `REVOKED`, `EXPIRED`, `SUPERSEDED`.
  - **Purposes:** `STAFF_ACTIVATION`, `STAFF_REENROLLMENT`.
  - **Constraints:** CHECKs keep each status and its timestamp coherent. A partial unique index allows one `PENDING` invitation per normalized email. The token digest is unique. Each invitation carries a sequence number and a version.
- **Capability:** a random 256-bit token. Only its SHA-256 digest (purpose-prefixed) is stored.
  - **Link:** built from `BETTER_AUTH_URL` as `/staff/activate#invite=…`. The fragment is read and then removed from history before the form renders.
  - **Email:** generic. No role, branch, or system detail; no codes.
- **Concurrency:** issuance takes a transaction-scoped advisory lock per email, so a resend supersedes the previous invitation in order. Accept, revoke, and expire are version-checked conditional updates. Activation completes at most once.
- **Ineligible addresses:** candidate, service, and active or restricted staff addresses get the same `ACCEPTED` outcome with no record and no email. No account is ever converted or duplicated.
- **Issuance boundary:** issue and revoke require an explicit actor and the `StaffAdministrationGate` port.
  - The runtime default is `RefusingStaffAdministrationGate`, including in the running web application.
  - `NonproductionHarnessGate` throws on construction unless `APP_ENV` is `local` or `test`. It is used only by `pnpm auth:staff:invite:local` (reason code required; the email is never printed) and by tests.
  - There is no route, page, seed invitation, or default staff/admin account.

### Activation

1. Exchange the invitation, then create or resume the single `STAFF` / `INVITED` account. The invitation proves email ownership, so `email_verified = true`. The email cannot be edited.
2. Set the password: M1.2 password policy plus the compromised-password port, hashed by Better Auth.
3. Open an enrollment-only session and call the plugin's `enableTwoFactor`.
4. Verify the first TOTP code (the plugin's `verifyTOTP`), then generate backup codes with `generateBackupCodes`; this requires the password again.
5. Require explicit confirmation that the backup codes were saved.
6. In one transaction: `INVITED → ACTIVE` (only if MFA is enabled) and invitation `ACCEPTED`.
7. Rotate to a new `STAFF` session through a `serverOnly` plugin endpoint that uses Better Auth's own `createSession` and `setSessionCookie`.

Abandoning at any step leaves the account `INVITED`. A restart, revoke, or resend ends earlier enrollment contexts.

No staff profile, role, or scope is created.

### Staff recovery and MFA reset

- **Public request:** `/staff/recover` always returns the same confirmation. It opens a `REQUESTED` case in `auth.staff_recovery_case` only for an ACTIVE staff account, with at most one open case per account. The case stores references, timestamps, and safe codes only: no evidence, identity documents, answers, or free text.
- **State machine:** in the domain layer.
  - **Path:** `REQUESTED → IDENTITY_VERIFICATION_PENDING → APPROVAL_PENDING → APPROVED → COMPLETED`.
  - **Other outcomes:** `REJECTED`, `CANCELLED`, and `EXPIRED` (request expiry, or approval expiry after `AUTH_STAFF_RECOVERY_APPROVAL_SECONDS`).
  - **Separation of duties:** nobody acts on their own case, only the assigned verifier confirms identity, and the approver must differ from the verifier. Database CHECKs repeat these rules.
- **Completion,** in one transaction:
  - every session is revoked;
  - the TOTP enrollment, all backup codes, pending challenge and trusted-device records, and replay markers are removed;
  - the account returns to `INVITED`, and its version increments;
  - a short-lived single-use reenrollment invitation is issued (`AUTH_STAFF_REENROLLMENT_EXPIRES_IN_SECONDS`, default 4 h) and emailed to the verified address.
  - Reenrollment always sets a new password and requires fresh MFA before `ACTIVE`. No seed or code is ever emailed.
- **Who can drive cases:** every administrative step goes through the same refusing gate. Only `pnpm auth:staff:recovery:local` and tests (local/test) can drive cases. There is no production completion route.
- Candidate self-service recovery never targets staff (ADR-0003).

### Security events

Typed `staff.*` event codes go through the M1.2 `SecurityEventPort`. They carry only the code, a result category, opaque account and record UUIDs, and the correlation ID. This is future-audit-ready, not audit: PRD-AUTH-007 stays incomplete until M1.6. *Superseded for events by ADR-0012 (M1.6): invitation, activation, recovery, and MFA-reset events now append in the same transaction; Better Auth MFA enrollment and sign-in are provider-committed.*

### Schema

Migration `drizzle/0002_staff_invitation_mfa.sql` is additive only:

- `auth.two_factor` (plugin table, plus a unique `user_id` and a CHECK);
- `auth.user.two_factor_enabled`;
- the session assurance columns and CHECKs;
- `auth.staff_invitation`, `auth.staff_recovery_case`, and `auth.totp_replay_guard`.

The runtime role has DELETE only on `two_factor` and `totp_replay_guard` among the new tables. Invitations and recovery cases are evidence and are never deleted.

## Open decisions

- Passkeys / WebAuthn as a phishing-resistant factor (requires an approved true second-factor or step-up design).
- Trusted-device policy (duration, revocation). Disabled until approved.
- Recovery staffing: who verifies and approves, the identity-verification procedure, and approval-window length. The defaults are local.
- Production email provider and delivery worker (ADR-0003).
- Auth-secret key-rotation runbook covering encrypted TOTP seeds and backup codes.
- Staff session idle/absolute timeouts and the production recent-authentication interval.
- Immutable audit persistence (M1.6) and the authorization adapters for invitation issuance and recovery steps (M1.4–M1.5).

## Consequences

**Positive:**
- Staff cannot hold a usable session without a verified second factor.
- MFA material is generated, encrypted, and verified only by the maintained library.
- Assurance is server-owned and reusable by later commands.
- No production administration surface exists before authorization and audit.

**Negative:**
- TOTP is phishable, and passkeys are deferred.
- MFA material depends on the auth secret.
- The replay guard, challenge record, and session-rotation endpoint are application glue around the plugin and must be revisited on Better Auth upgrades.
- Rate limits are still per-process (production-like startup is refused; ADR-0002).
