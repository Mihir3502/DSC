# Work Item M0.1 — Initialize the TypeScript Application

## 1. Status

- Milestone: M0 — Repository Foundation
- Status: Ready for review
- Execution order: First coding work item
- Primary outcome: A minimal production-buildable Next.js TypeScript application exists without implementing hiring behavior.

## 2. Outcome

Initialize the repository as a single Next.js App Router application using strict TypeScript, `pnpm`, Tailwind CSS, ESLint, and a minimal shadcn/ui foundation.

The application must provide safe placeholder entry pages for:

- Public site: `/`
- Candidate portal: `/candidate`
- Staff portal: `/staff`

This task establishes only the web-project foundation. It must not implement authentication, database access, hiring workflows, forms, screening, onboarding, or business data.

## 6. In Scope

### 6.1 Application scaffold

- Next.js App Router.
- React version selected by the stable Next.js scaffold.
- Strict TypeScript.
- Source code under `src/`.
- Tailwind CSS.
- ESLint with Next.js and TypeScript rules.

- `pnpm-lock.yaml` committed.
- Exact `packageManager` entry in `package.json`.
- Supported Node LTS pinned in `.nvmrc`.
- Compatible Node engine range in `package.json`.

- `pnpm dev`
- `pnpm build`
- `pnpm start`
- `pnpm lint`
- `pnpm typecheck`
- `pnpm format`
- `pnpm format:check`

### 6.4 Minimal UI foundation

- Root layout with meaningful default metadata.
- Global styles and design tokens using neutral, accessible defaults.
- Minimal shadcn/ui configuration for the existing Next.js application.
- Add only the small number of components needed by the three foundation pages, preferably `Button`, `Card`, and related primitives when genuinely used.
- Reusable `AppShell` or similarly small layout primitives only if they eliminate real duplication.

### 6.5 Route-group foundation

Use App Router route groups without changing public URLs:

```text

├── layout.tsx
├── globals.css
├── (public)/
│   └── page.tsx
├── (candidate)/
│   └── candidate/
│       └── page.tsx
└── (staff)/
    └── staff/
        └── page.tsx
```

The exact addition of route-group layouts is allowed only when needed for clear separation and they contain no authentication logic.

### 6.6 Module-boundary placeholders

Create only lightweight documentation/placeholders needed to establish intended directories:

```text

src/shared/README.md
```

The files must explain that business modules will follow the architecture’s `domain`, `application`, `infrastructure`, and `ui` boundaries. Do not create dozens of empty directories or speculative modules.

### 6.7 Repository hygiene

- Preserve every existing project document.
- Update `.gitignore` for Next.js, Node, local environment files, coverage/test output, Playwright authentication/output, and local private documents.
- Provide `.env.example` only if the generated framework needs a safe public variable; otherwise defer it to M0.2.
- Do not create an `.env` file.
