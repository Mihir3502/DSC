# Work Item M1.6 — Append-Only Audit Foundation

## 1. Status

- Milestone: M1 — Identity, Access, and Audit
- Status: Ready for implementation
- Execution order: After M1.5 is implemented, committed, and accepted
- Primary outcome: Compliance-significant identity and authorization actions produce immutable, minimally disclosed, tamper-evident audit records with actor/effective-authority context; future business mutations can append audit records atomically through one transaction boundary, and authorized callers can query only safe scoped projections.

## 2. Outcome

Replace the temporary future-audit event boundary from M1.1–M1.5 with durable append-only audit persistence.

Deliver:

- A reviewed `audit_event` schema, Drizzle model, SQL migration, indexes, constraints, and least-privilege grants.
- A separate bounded `security_event` stream for authentication/abuse telemetry where it must not be mixed into business history.
- A versioned event catalog defining names, categories, outcomes, required context, metadata schemas, sensitivity, retention class, and audit requirements.
- Server-owned actor, effective role/scope, target, source, time, request, correlation, reason, outcome, and record-version context.
- Strict safe metadata schemas that prevent secrets, personal data, medical/screening contents, and unrestricted before/after snapshots.
- Database- and application-layer append-only protections with no ordinary update/delete path.
- A tamper-evident integrity chain with versioned canonicalization/key handling and a read-only verification tool.
- One transaction helper that commits business/security-relevant state changes and required audit events together or rolls both back.
- Standalone required-denial/security append behavior that never turns an audit failure into an authorization/authentication success.
- Idempotent event handling that prevents duplicate audit rows for one accepted command while preserving distinct attempts.
- Integration of current M1 account, authentication, MFA/recovery, role/scope, security-setting, restricted-access, and high-risk authorization-denial events.
- An authorized, scope-filtered, field-redacted, keyset-paginated audit query service/projection.
- Safe operational alert/metric behavior for audit-write and integrity-verification failures.
- Real PostgreSQL migration, immutability, atomicity, concurrency, integrity, authorization, privacy, and recovery-oriented tests.
- `ADR-0004` documenting audit immutability, transaction, integrity-chain, privacy, and query decisions.
- Traceability updates for PRD audit/auth requirements without claiming the M1.7 full authorization matrix complete.

This task creates no hiring-business aggregate, audit dashboard, export, retention-deletion workflow, legal-hold UI, or production access-administration screen.

## 6. Audit Versus Logs and Security Telemetry

Keep three concerns distinct:

| Concern | Purpose | Persistence/behavior |
| --- | --- | --- |
| Operational log | Diagnose runtime behavior | Structured, redacted, bounded retention; not authoritative business history |
| Security event | Detect authentication/abuse/security patterns | Restricted, bounded safe risk/outcome facts; may include attempts with no authenticated actor |
| Audit event | Preserve compliance-significant business/access history | Append only, authorization scoped, transactionally tied to required changes, tamper evident |

Rules:

- A log entry is never a substitute for an audit event.
- An audit event is not a debugging dump.
- Security telemetry is not displayed as ordinary business history.
- The same occurrence may produce one audit event and one operational metric when both are required, but it must not create duplicate audit rows through multiple adapters.
- Routine ordinary page views need not create individual audit rows unless the approved event catalog says they do.
- Restricted data access, role/scope changes, security-setting changes, and high-risk denials require durable evidence.

## 7. Audit Event Schema

### 7.1 Core fields

Implement `audit_event` with equivalents of:

- `id`: nonsequential immutable event ID.
- `schema_version`: closed positive integer identifying the event envelope version.
- `event_name`: stable catalog code, not free text.
- `category`: stable category such as `IDENTITY`, `ACCESS_CONTROL`, `SECURITY`, `RESTRICTED_ACCESS`, `CONFIGURATION`, or future business category.
- `outcome`: closed value such as `SUCCEEDED`, `DENIED`, `FAILED`, or approved equivalent.
- `organization_id`: nullable until a real M2 organization exists.
- `candidacy_id`: nullable until a real M2 candidacy exists.
- `actor_type`: `USER`, `SERVICE`, `SYSTEM`, or `ANONYMOUS`.
- `actor_user_id`: nullable only when actor type legitimately has no user.
- `effective_role_code`: nullable for candidate/system/anonymous events.
- `effective_assignment_id`: nullable; opaque current assignment reference.
- `effective_scope_type` and `effective_scope_reference_id`: nullable only when the event legitimately has no staff scope.
- `permission_code`: nullable when no authorization permission applies.
- `action`: stable action/command code.
- `target_type` and `target_id`: stable resource type and opaque ID; null only for catalog-approved targetless security events.
- `source`: closed source such as `WEB`, `API`, `JOB`, `PROVIDER`, `SYSTEM`, or `LOCAL_TEST`.
- `reason_code`: closed safe reason; required by the catalog where applicable.
- `correlation_id` and `request_id`: server-issued bounded identifiers.
- `command_id` or accepted idempotency reference where applicable.
- `occurred_at`: trusted server/database time for the occurrence.
- `recorded_at`: database insertion time.
- `metadata_json`: versioned allowlisted safe metadata only.
- `previous_record_version` and `new_record_version`: nullable controlled integers.
- Integrity fields described in Section 12.
- `retention_class_code`: approved audit/security retention classification, not a deletion date.

The table has no mutable `updated_at`, mutable status, soft-delete flag, or ordinary deletion marker.

### 7.2 Constraints

At minimum enforce:

- Closed values for actor type, category, outcome, source, scope type, and schema/canonicalization versions.
- Actor/user coherence.
- Staff effective-role/scope coherence where required.
- Target type/ID coherence.
- Previous/new version coherence and nonnegative bounds.
- Bounded string lengths and metadata byte size.
- `occurred_at` cannot be unreasonably future dated; external caller timestamps are not trusted.
- Event name/category/retention consistency through application catalog validation and database checks where stable.
- Unique event/command idempotency key where the catalog declares exactly-once-per-command semantics.
- Required correlation/request identifiers according to source.
- No cascading foreign key can erase an audit event.

Do not add foreign keys to M2 entities that do not exist. Actor account references should use `RESTRICT`/retained identity semantics consistent with the accepted account model. Record the deliberate opaque-reference strategy in ADR-0004.

## 8. Security Event Schema

Implement a separate append-only `security_event` table only for bounded authentication and abuse evidence that does not belong in ordinary business history.

Equivalent fields:

- Nonsequential immutable ID and schema version.
- Nullable account/user reference.
- Stable event name and outcome.
- Safe risk/reason code.
- Source, occurred/recorded times, request/correlation identifiers.
- Optional privacy-reviewed network/device risk tokens, never raw network/device strings by default.
- Minimal safe metadata with a strict schema/size limit.
- Retention class.
- Integrity fields or an explicitly documented equivalent protected stream.

Do not store raw IP addresses, full user-agent strings, device fingerprints, passwords, credentials, tokens, cookies, headers, request bodies, email addresses, or entered identifiers. If rate limiting already uses ephemeral network indicators, do not copy them into durable audit/security rows without an approved privacy purpose and retention decision.

The distinction between `audit_event` and `security_event` must be deterministic in the event catalog.

## 10. Safe Event Construction

Define a typed `AuditContext` populated only from server-owned sources:

- Current principal/actor and actor type.
- Effective M1.4 role assignment and scope used for the decision.
- Stable permission/action/event names from code/catalog.
- Opaque target reference and safe organization/candidacy reference when known.
- M1.5 correlation/request/source context.
- Stable reason/outcome code.
- Command/idempotency reference.
- Record versions.
- Trusted clock.

The browser/provider/job payload cannot supply actor, authority, permission, event name, outcome, policy version, audit timestamp, or arbitrary metadata.

Use event-specific constructors/builders that accept narrow typed facts. Do not expose a generic `append(eventName, metadata: any)` API to business code.

## 11. Metadata Minimization and Change Summaries

### 11.1 Allowed metadata

Use small versioned safe facts such as:

- Changed field-category codes, not values.
- Prior/new status codes where classification permits.
- Count of affected sessions/items.
- MFA method category, never factor material.
- Assignment scope type and opaque reference already present in the envelope.
- Safe denial/risk/policy code.
- Template/catalog/policy version.

### 11.2 Prohibited metadata

Never copy into audit/security metadata:

- Passwords/hashes, MFA seeds/codes, backup codes, recovery/invitation/verification tokens, session tokens/cookies, authorization headers, API/provider secrets, encryption/HMAC keys, or signed URLs.
- Full emails, phone numbers, addresses, names where an opaque reference is sufficient, government/tax/document/bank identifiers, or date of birth.
- Application answers, free-text notes, reasons, internal deliberations, compensation details, document contents, signatures, screening reports, criminal/registry results, drug/TB/medical details, or dispute narratives.
- Request/response bodies, query strings, raw URLs, raw SQL/database errors, stack traces, IP addresses, user agents, device fingerprints, or provider payloads.
- Unrestricted before/after JSON snapshots.

### 11.3 Change summary

Before/after values are included only when an event-specific schema explicitly permits safe closed values. Prefer:

- `changed_fields: [safe_code]`
- `from_status_code`
- `to_status_code`
- `previous_record_version`
- `new_record_version`

Free-text reason may remain in its protected owning business record when later implemented; audit stores the approved reason code/reference only.

## 12. Append-Only and Tamper-Evident Integrity

### 12.1 Database immutability

Protect audit and security rows at multiple layers:

- Runtime repositories expose insert/query only; no update/delete methods.
- Runtime database identities receive only the minimum insert/select/execute privileges required by the accepted design.
- Revoke/omit `UPDATE`, `DELETE`, `TRUNCATE`, and schema ownership for runtime identities.
- Add database trigger/rule protection rejecting update/delete attempts, including updates that appear to change nothing.
- Foreign keys never cascade-delete audit/security rows.
- Ordinary application commands cannot disable triggers, change ownership, or alter grants.
- Migration/break-glass database ownership remains outside the application and is operationally controlled.

Database append-only controls do not replace integrity verification or backups.

### 12.2 Integrity chain

Implement a reviewed tamper-evident chain using maintained cryptographic primitives:

- Stable chain/partition identifier.
- Monotonic per-chain sequence.
- Previous integrity hash stored on each row.
- Versioned canonical envelope serialization.
- Versioned keyed HMAC/integrity algorithm over the complete immutable envelope plus previous hash/sequence.
- Integrity key version stored, but never the key.
- Transactionally locked chain-head state preventing forks/duplicate sequence under concurrency.
- Chain-head updates and event insertion in the same transaction.

Use a narrow chain partition strategy that supports current global/security events and future organization-bound events without accepting client-selected partitions. Avoid one unbounded global hot lock when a reviewed server-owned partition is available, but do not create fake organizations.

Keys come from approved environment-specific secret configuration. Local/test uses deterministic synthetic keys. Production-like configuration rejects missing, placeholder, reused, or test keys. Define a key-ring/rotation verification strategy; old verification keys must remain available according to audit retention.

If the accepted runtime/database boundary cannot safely compute, store, and verify the chain without exposing key material or creating race forks, stop and document the blocker. Do not substitute an unkeyed checksum and call it tamper proof.

### 12.3 Verification

Provide a read-only verification service/script that:

- Streams rows in chain/sequence order with bounded memory.
- Reconstructs the exact historical canonical version.
- Verifies sequence continuity, previous hash, HMAC, key version, and chain-head agreement.
- Detects modification, deletion, insertion, reordering, duplication, and fork where evidence permits.
- Returns a safe summary/count/range and first failing opaque event/sequence reference.
- Never repairs, rewrites, rehashes, deletes, or prints metadata/secrets.
- Exits nonzero on any integrity failure and emits a safe operational alert/metric.

Document the limitation that append-only/tamper evidence is not a substitute for independent backups, access control, external checkpoints, or operational database monitoring.

## 13. Atomic Audit Transaction Helper

### 13.1 Required behavior

Implement a framework-neutral application transaction boundary equivalent to:

```text
withAuditedTransaction(context, transactionClient => {
  authorize/recheck current facts
  apply business or security-relevant mutation
  append required audit event(s)
  append outbox event(s) when a later task requires them
  return safe result
})
```

All repositories receive the same explicit transaction client. No nested independent connection/transaction may write the audit event.

For a compliance-significant allowed mutation:

- If authorization fails, no mutation occurs.
- If mutation fails, no audit success event commits.
- If audit construction/validation/insertion/integrity-head update fails, the mutation rolls back.
- If commit fails, neither change nor audit is reported as successful.
- Success is returned only after durable transaction commit.
- An audit failure emits only safe operational failure telemetry and blocks success.

### 13.2 Required denied/failed events

For a catalog-required high-risk denial or failed security attempt with no business mutation:

- Persist the denial/failure through a bounded standalone append transaction.
- Audit failure never converts the original denial into success.
- Do not reveal audit-write failure, account existence, or internal reason to the requester.
- Raise a safe operational alert/metric.
- Apply a documented fail-closed/availability policy for operations that cannot proceed without required audit evidence.

### 13.3 No audit-after-commit pattern

Do not allow business code to commit and then enqueue/best-effort append its required audit row. The transactional outbox later supports asynchronous side effects, not delayed creation of the authoritative audit event.

## 14. Idempotency, Retries, and Concurrency

- Reuse the accepted command/idempotency key for one logical command.
- A retry returning the existing accepted result must not append a duplicate success event.
- Distinct authentication/authorization attempts remain distinct events even if their safe context is similar.
- Unique constraints and repository logic agree on deduplication semantics.
- Concurrent appends to one integrity chain serialize only the chain-head critical section and cannot fork or reuse a sequence.
- Events across independent approved chains may append concurrently.
- Deadlock/serialization failures use bounded safe retry only around the complete transaction and preserve idempotency.
- Never retry a denied decision into an allow or duplicate a business mutation/audit event.
- Tests use deterministic barriers to prove chain/order/atomicity behavior.

Replace the M1.1–M1.5 temporary audit-event adapters with the durable service.

### 15.1 Authentication/security integration

- Use maintained Better Auth hooks/application services only at supported boundaries.
- A successful security-setting/account change that requires audit is not reported successful unless the audit requirement is durably satisfied.

## 16. Authorized Audit Query Projection

Implement an application query service/repository projection; do not expose a production audit page or generic audit API yet.

### 16.1 Authorization

- Require `audit.read.assigned` or a narrower approved permission.
- Enforce current active account, assignment, scope, audit-assignment/date/category bounds, field sensitivity, and recent authentication where policy requires.
- Candidate users cannot query internal audit history in M1.6.
- `SYSTEM_ADMINISTRATOR` has technical support access only and no routine unrestricted business-audit authority.
- `AUDITOR_READ_ONLY` remains read-only and limited to an active approved audit assignment.
- The actor whose actions are recorded cannot modify/delete the event; no query permission creates mutation authority.

### 16.2 Query limits

- Apply scope/date/category/resource predicates in SQL before materialization.
- Use keyset pagination ordered deterministically by occurred time and event ID/sequence.
- Bound page size and date range.
- Allowlist event/category/outcome/target filters.
- Do not expose arbitrary JSON-path metadata search, raw SQL-like filters, unrestricted actor enumeration, or bulk export.
- Return counts/facets only when they cannot reveal out-of-scope activity.
- Recheck event projection authorization before return where required.

### 16.3 Safe projection

Return an exact view model containing only approved equivalents of:

- Event ID/reference.
- Occurred time.
- Safe display event/action/category/outcome codes.
- Safe actor display/reference only when authorized.
- Effective role/scope summary only when authorized.
- Safe target type/reference.
- Reason code when authorized.
- Correlation/reference number where appropriate.
- Approved safe metadata summary.

Never return integrity HMAC values/key version, raw chain-head state, unrestricted metadata JSON, internal denial policy context, request IDs useful for correlation attacks, secret/personal fields, or database details through ordinary projections.

Querying restricted audit data is itself auditable according to the event catalog without recursive infinite event creation. Define a recursion-safe rule, such as auditing the query once outside its own returned result window/context.

## 17. Database Migration and Privileges

Create a reviewed forward migration containing:

- `audit_event` and `security_event` tables.
- Integrity chain-head technical state and required constraints.
- Append-only update/delete protection functions/triggers.
- Required sequences/indexes/unique constraints.
- Least-privilege grants/revocations for migration and runtime identities.
- No default audit rows, users, assignments, organizations, candidacies, or fake business data.

Indexes should support bounded queries by:

- Chain/sequence.
- Occurred time plus event ID.
- Target type/ID plus time.
- Actor plus time where authorized.
- Organization/candidacy plus time when nonnull.
- Event/category/outcome plus time where justified.
- Correlation/command/idempotency reference where required.

Avoid broad GIN indexes on unrestricted metadata. Validate index cost/selectivity with synthetic data.

Migration rules:

- Apply from an empty database and from the accepted M1.5 schema with representative synthetic data.
- Review ownership, functions, `SECURITY DEFINER` usage if any, search path, grants, trigger bypass, foreign-key deletion behavior, metadata bounds, and rollback/forward recovery.
- Application runtime must not own the tables/functions or disable protections.
- Any privileged function has a fixed safe search path, typed inputs, no dynamic SQL, and minimum grants.
- Do not use `drizzle-kit push` on shared environments.

## 18. Retention, Backup, and Recovery Boundary

- Assign an approved audit/security retention class, but do not invent final legal durations.
- No normal application retention/deletion command may delete audit/security rows in M1.6.
- M9.6 will implement approved retention/legal-hold foundation; it must preserve audit integrity and authority.
- Account/resource closure does not erase audit history.
- Backup/restore procedures must preserve events, chain heads, sequence, key-version references, and verification ability.
- Restore tests verify integrity after recovery using synthetic data.
- Key rotation/backup custody is documented; keys are never stored in the audit tables, repository, fixtures, logs, or artifacts.
- If a future legally required disposition conflicts with hash-chain continuity, it requires a separately approved cryptographic tombstone/checkpoint design; do not implement it here.

## 19. Operational Failure Behavior

- Audit-write failure is a high-severity safe operational event/metric.
- Integrity-verification failure is a high-severity incident signal and must not trigger automatic repair.
- Do not retry indefinitely or create an unbounded in-memory/disk fallback containing audit payloads.
- Do not write audit payloads to ordinary logs as a fallback.
- Health/readiness checks expose only safe status codes; they do not reveal event counts/targets/integrity values.
- Production-like startup rejects missing integrity keys, invalid key-ring configuration, absent append-only protections, or runtime ownership/excess grants when these checks are feasible.
- Incident handling preserves evidence and follows the security specification; ordinary administrators cannot clear failures.

## 23. Acceptance Criteria

### AC-M1.6-01 — Versioned audit schema

Audit/security tables store controlled event envelopes with actor/effective-authority/action/target/time/source/reason/outcome/correlation/version/retention/integrity context and bounded metadata.

### AC-M1.6-02 — Event catalog

Every emitted M1 event is registered with exact schema, stream, actor/source/outcome, context, metadata, transaction, retention, and audit rules; unknown names/versions/keys deny persistence.

### AC-M1.6-03 — Data minimization

Audit/security rows, logs, errors, metrics, scripts, and test artifacts contain no prohibited secrets, raw personal/restricted content, free-text dumps, request bodies, IP/user-agent data, or unrestricted before/after JSON.

### AC-M1.6-04 — Append-only enforcement

Runtime code/roles cannot update, delete, truncate, alter, own, cascade-delete, or bypass audit/security protections; direct prohibited SQL fails.

### AC-M1.6-05 — Tamper evidence

Versioned keyed integrity chains detect row modification, deletion, insertion, reorder, duplicate/fork, sequence gap, and chain-head mismatch; concurrency cannot fork a chain.

### AC-M1.6-06 — Safe key lifecycle

Integrity keys are environment separated, versioned, absent from storage/logs/artifacts, retained for verification, and required with production-safe configuration.

### AC-M1.6-07 — Atomic allowed mutations

Required state change and audit append share one transaction; either both commit or both roll back, and success is never returned after audit failure.

### AC-M1.6-08 — Safe denial/failure persistence

Required high-risk denial/security failures append once through a bounded transaction; audit failure never creates access/success or exposes internal/account facts and emits safe operational alerting.

### AC-M1.6-09 — Idempotency and concurrency

Command retries do not duplicate success events/effects, distinct attempts remain distinct, and deterministic concurrent tests prove sequence, chain, rollback, and deduplication behavior.

### AC-M1.6-10 — Current M1 integration

Accepted account/authentication/MFA/recovery/role/scope/security-setting/restricted-access/high-risk-denial events use durable persistence with correct safe context and no duplicate adapter events.

### AC-M1.6-11 — Authorized query projection

Audit queries require current permission/scope/assignment/sensitivity/assurance, filter before materialization, use bounded keyset pagination, return exact redacted projections, and expose no integrity or raw metadata details.

### AC-M1.6-12 — Migration and database permissions

Migration succeeds empty and from M1.5, indexes/constraints/triggers/grants are reviewed, runtime is not owner, and least-privilege/rollback-forward checks pass.

### AC-M1.6-13 — Verification and recovery

Read-only verification detects corruption without repair/disclosure, and synthetic backup/restore preserves events, heads, sequences, key references, and valid verification.

### AC-M1.6-14 — Operational failure safety

Audit-write/integrity/configuration failures create only safe high-severity signals; no payload fallback, automatic repair, or insecure production startup occurs.

### AC-M1.6-15 — ADR and traceability

ADR-0004 documents design/threats/limitations, and traceability accurately marks implemented audit requirements without claiming M1.7/M2+ history/report/export complete.

### AC-M1.6-16 — Regression and scope containment

All accepted M0–M1.5 tests remain green, and no business aggregate, dashboard, export, final retention/deletion, external audit service, or M1.7 work is added.
