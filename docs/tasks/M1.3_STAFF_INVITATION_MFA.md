## 1. Status

- Milestone: M1 — Identity, Access, and Audit

## 2. Outcome

Implement staff authentication security without yet granting business permissions or candidate-record access.

Deliver:

- A versioned staff-invitation lifecycle with issue, resend, revoke, expire, accept, and supersede behavior.

- Separate accessible staff sign-in and MFA challenge screens.
- Mandatory TOTP for every staff account in M1.3, with single-use backup codes.
- A documented evaluation boundary for future phishing-resistant WebAuthn/passkey authentication.
- Safe staff session handling, MFA assurance state, and session rotation.
- A reusable recent-authentication/assurance policy primitive for later high-risk commands.
- A controlled staff MFA/password recovery case process requiring administrative verification and approval.
- A minimal authenticated `/staff/security` area containing only account/MFA/session controls.
- Local Mailpit and deterministic test-email delivery.
- Real PostgreSQL, component, accessibility, security, concurrency, and Playwright coverage.
- Traceability updates that distinguish implemented authentication from future authorization/audit work.

This task does not grant roles, permissions, organization/branch/team scopes, candidate-record access, business approvals, or immutable audit persistence.

## 6. Security Decisions for M1.3

### 6.1 MFA requirement

Roles are introduced in M1.4, so M1.3 cannot reliably distinguish privileged from nonprivileged staff. Apply MFA to every interactive `STAFF` account. This is stricter than the minimum requirement and avoids an authorization gap.

- Staff never receive a normal application principal after password-only authentication.
- Staff account activation is incomplete until MFA enrollment and first-factor verification both succeed.
- Candidate accounts are not enrolled into staff MFA through this task.
- Service accounts remain noninteractive.

M1.4 may later attach role-aware policy, but it must not weaken the production requirement for privileged staff.

### 6.2 MFA method

Use maintained TOTP as the required M1.3 second factor because the selected Better Auth two-factor plugin explicitly supports password-plus-TOTP challenges and backup codes.

Phishing-resistant WebAuthn/passkeys remain preferred. During implementation:

- Evaluate whether the pinned maintained passkey plugin can act as a true second factor/step-up within the current password flow.
- If yes without custom protocol/security code, document an approved optional design but do not expand scope without reviewer approval.
- If it provides passwordless authentication rather than a true second factor, defer it and record the limitation.
- Do not label passwordless passkey sign-in as “MFA” unless the assurance policy and authenticator user-verification semantics are explicitly approved.

Email OTP and SMS are not accepted as the normal staff second factor in M1.3. SMS requires separate risk acceptance. Email is already the invitation/recovery channel and is not independent enough for the default second factor.

### 6.3 Trusted devices

Disable trusted-device bypass in M1.3 unless management/security explicitly approves a duration and revocation model. Client input requesting `trustDevice=true` must not override server policy.

### 6.4 Audit dependency

M1.6 will add immutable audit persistence. M1.3 must emit typed future-audit-ready security events through the established port but must not create a competing audit table or claim PRD-AUTH-007 complete.

## 7. Staff Invitation Model

### 7.1 Invitation entity

Add an application-owned staff invitation record in the identity-access module with fields equivalent to:

- Nonsequential invitation ID.
- Normalized invited email and protected display email.
- Status: `PENDING`, `ACCEPTED`, `REVOKED`, `EXPIRED`, `SUPERSEDED`.
- Protected token digest/reference; never raw token.
- Purpose/version.
- Issued time, expiry time, accepted/revoked/superseded times.
- Issuer account reference when a real authorized issuer exists.
- Bootstrap/test issuer reason code for nonproduction setup.
- Optional safe display name/job-title seed only if approved; no role/scope.
- Version for optimistic concurrency.
- Common timestamps.

Do not add organization, branch, team, role, permission, or scope fields. Those belong to M1.4 and later business configuration.

### 7.2 Constraints

- One live invitation per normalized email and invitation purpose.
- Invitation token digest is unique.
- Accepted/revoked/expired/superseded records are terminal.
- Expiry and terminal timestamps are coherent with status.
- Resend supersedes the prior live capability and creates a new version/token.
- Accept is concurrency-safe; at most one request succeeds.
- Existing candidate/service account email cannot be silently converted to staff.
- Existing active/locked/disabled/closed staff receives a safe nonenumerating result; no duplicate staff account is created.

### 7.3 Issuance boundary

M1.4/M1.5 will authorize staff administration and M1.6 will persist audit evidence. Therefore M1.3 must not expose a production invitation-issuance UI or public/admin route.

Implement:

- Application service/command requiring an explicit actor and future authorization context.
- A deterministic test harness.
- An optional local-development bootstrap command that is unavailable in production-like environments, accepts one email interactively/through explicit argument without logging it, and requires a reason.
- No default staff/admin account and no seed invitation.

Production invitation issuance remains disabled until M1.4–M1.6 authorization/audit integration is complete.

## 8. Invitation Delivery and Link Security

- Send through the M1.2 auth-email port and local Mailpit/test capture adapters.
- Build links only from validated configured origin.
- Token is random, purpose-bound, short-lived, single-use, and stored only as a digest/protected value.
- Prefer fragment/immediate-exchange handling consistent with M1.2.
- Remove the capability from visible URL/history before rendering interactive content.
- Apply `Referrer-Policy: no-referrer` and load no third-party resources.
- Never log token, full invitation URL, normalized email, or email body.
- Resend invalidates/supersedes the prior capability.
- Revoke prevents acceptance immediately.
- Expired/revoked/accepted/superseded/unknown states render one safe public outcome where differentiation creates risk.
- Invitation email contains no role, branch, candidate data, or internal system access detail beyond a generic staff-account activation message.

## 9. Staff Activation Flow

Implement `/staff/activate` as a restricted activation workflow:

1. Validate/exchange the invitation capability.
2. Bind the normalized email and prevent editing to another email.
3. Create or complete one `STAFF` account in `INVITED` state.
4. Mark email ownership verified through the accepted invitation proof.
5. Collect password and confirmation using M1.2 password policy/compromised-password port.
6. Establish only the minimum temporary activation context needed for maintained MFA enrollment.
7. Enroll TOTP and verify the first code.
8. Generate backup codes through the maintained plugin.
9. Display backup codes once with accessible copy/print/download-safe options; require confirmation that they were saved.
10. Transition account to `ACTIVE` only after MFA enrollment succeeds.
11. Consume invitation and rotate/create the final staff session.
12. Redirect only to the allowlisted minimal `/staff/security` route.

Failure rules:

- Abandoned activation leaves the account `INVITED` and unable to resolve a normal staff principal.
- Password completion without verified MFA does not activate the account.
- Invitation reuse or parallel activation permits at most one final activation.
- Candidate/service accounts cannot be upgraded through invitation acceptance.
- TOTP secret and backup codes never appear after enrollment confirmation.
- Do not create a staff profile/role/scope unless required by the accepted identity design; if a minimal profile is necessary, stop and review its future M1.4 ownership before adding it.

## 10. TOTP and Backup-Code Protection

### 10.1 TOTP enrollment

- Use the maintained Better Auth two-factor plugin.
- Set a reviewed issuer/application label.
- Generate QR locally using a maintained dependency only if required; never call a public QR service.
- Offer the secret/manual key accessibly during enrollment, but do not log, persist in client storage, or display after completion.
- Require a valid current TOTP code to finish enrollment.
- Enforce bounded attempts and temporary lockout through supported server behavior.
- Do not accept client-controlled clock windows or issuer/account labels.

### 10.2 Secret storage

- Use Better Auth's supported protected storage.
- Prove the raw TOTP seed is not present in ordinary query output, logs, errors, artifacts, or client bundles after enrollment.
- If encryption at rest relies on the main auth secret, document key dependency, rotation impact, backup/recovery requirements, and environment separation.
- Production-like configuration rejects test keys and missing protection.

### 10.3 Backup codes

- Generate sufficient high-entropy codes through the maintained plugin.
- Store them hashed or strongly encrypted according to the approved library behavior.
- Show only once during enrollment/regeneration.
- Each code is single use and atomically consumed.
- Regeneration invalidates every prior unused code.
- Never email backup codes.
- Never expose them through an ordinary “view codes” endpoint after initial confirmation.
- Server-only library APIs capable of viewing codes must not be connected to a route/UI.
- Using a backup code creates a full staff session only after all account checks pass and records a safe event code.

## 11. Staff Sign-In and MFA Challenge

### 11.1 First factor

`/staff/sign-in`:

- Accepts staff email/password through accessible bounded forms.
- Uses generic invalid-credentials responses for nonexistent, candidate, service, invited, locked, disabled, closed, wrong-password, or other ineligible accounts where disclosure would create risk.
- Does not issue a normal staff application principal after password alone.
- Uses maintained Better Auth temporary two-factor challenge state.
- Rejects candidate accounts even if their credentials are valid.
- Applies origin/CSRF, redirect allowlist, no-store, and rate-limit controls.

### 11.2 Second factor

`/staff/mfa`:

- Accepts TOTP or one backup code.
- Does not accept email/SMS OTP as default.
- Ignores/rejects trusted-device requests under the M1.3 policy.
- Uses one generic invalid-factor response.
- Applies shared per-account attempt limits across TOTP and backup codes where supported.
- Temporary lockout does not reveal whether the account exists.
- On success, rotates/creates the session and stamps server-owned authentication-assurance evidence.
- Redirects only to allowlisted staff security/home destination.

Challenge state must be short-lived, purpose-bound, protected, and unusable as an application session.

## 13. Recent-Authentication Primitive

Create a framework-neutral application policy for later high-risk actions.

### 13.1 Assurance model

Represent server-owned evidence such as:

- Account ID.
- Session ID/reference.
- Primary authentication time.
- MFA authentication time.
- Authentication method/strength: password+TOTP, password+backup-code, future approved passkey.
- Session/account version where needed for invalidation.

Never derive assurance from a client-submitted timestamp/boolean or merely from route middleware.

### 13.2 Policy check

The primitive accepts a named policy, for example:

- `NORMAL_STAFF_SESSION`
- `RECENT_STAFF_AUTH`
- `RECENT_STRONG_AUTH`

It returns a typed allow/challenge/deny result with safe reason code. It must be usable by M1.4–M1.6 and later commands without importing Next.js or Better Auth types.

### 13.3 Freshness

- Use a configurable short interval for recent authentication.
- Store/evaluate timestamps server-side using UTC.
- Do not rely solely on session creation time if MFA occurred later.
- Reauthentication success rotates or updates assurance without extending absolute session lifetime improperly.
- Account disable, password reset, MFA reset, critical role change, or session revocation invalidates assurance.
- Clock-boundary tests cover exact expiry and skew.

### 13.4 Reauthentication flow

Implement `/staff/reauthenticate` for the minimal security-page actions and future use:

- Require current password plus TOTP, or an approved strong method.
- Do not allow backup code for the highest assurance policy unless explicitly approved; default deny for `RECENT_STRONG_AUTH`.
- Validate a server-issued purpose/continuation key, not arbitrary URL/action.
- Produce short-lived server-owned evidence bound to the current session/account.
- Prevent replay for a different action/purpose where purpose binding is used.
- Use generic errors and rate limits.

Business actions do not consume this primitive until their later tasks.

## 14. Staff Recovery and MFA Reset

Staff must not use candidate self-service recovery to bypass MFA.

### 14.1 Recovery request

Provide a generic `/staff/recover` request screen only if the approved operational process requires it. It may create a bounded recovery case for an eligible staff account but always returns the same public confirmation.

The case contains:

- Nonsequential case ID.
- Target account reference stored only after internal resolution.
- Status: `REQUESTED`, `IDENTITY_VERIFICATION_PENDING`, `APPROVAL_PENDING`, `APPROVED`, `COMPLETED`, `REJECTED`, `EXPIRED`, `CANCELLED`.
- Requested/expiry/resolution timestamps.
- Safe reason code.
- Verifier and approver account references when those authorized roles exist.
- Version for concurrency.

Do not store submitted identity evidence, government IDs, security-question answers, free-text secrets, or raw support communications in this table.

### 14.2 Administrative process boundary

M1.4–M1.6 will add authorization, separation of duties, and immutable audit. Therefore:

- Do not expose a production recovery approval/reset UI or API in M1.3.
- Implement domain/application state transitions and test them with synthetic actors.
- Provide only a local/test recovery harness unavailable in production-like environments.
- Require distinct verifier and approver for privileged reset when later exposed.
- Require documented identity verification outside the application according to approved policy.
- Do not let system administrators approve their own reset.

### 14.3 Completion effects

An approved staff recovery/MFA reset must, when later invoked by an authorized adapter:

- Revoke every session.
- Invalidate prior MFA challenge/trusted-device state.
- Invalidate all backup codes.
- Disable/remove the old TOTP enrollment through supported Better Auth behavior.
- Put the account into `INVITED` or a dedicated approved reenrollment state that cannot resolve a staff principal.
- Issue a short-lived single-use reenrollment invitation through the safe email port.
- Require password reset if compromise is suspected/selected.
- Require fresh MFA enrollment before returning to `ACTIVE`.
- Notify the staff member through the verified channel.

Never send a new TOTP seed or backup codes by email.

## 20. Acceptance Criteria

### AC-M1.3-01 — Invitation-only staff

Staff accounts can be created/activated only from a valid email-bound staff invitation; generic/candidate signup cannot create staff.

### AC-M1.3-02 — Protected invitation lifecycle

Invitations are expiring, single-use, digest-protected, concurrency-safe, revocable, and superseded on resend; raw capabilities never persist or leak.

### AC-M1.3-03 — No premature production administration

Invitation issuance and recovery completion have no production UI/API until M1.4–M1.6 authorization/audit exist; local/test harnesses fail closed in production-like configuration.

### AC-M1.3-04 — MFA before activation

Password/email verification alone cannot activate or authenticate staff; first valid TOTP enrollment is required before `ACTIVE` state and a normal staff principal.

### AC-M1.3-05 — Mandatory TOTP

Every staff sign-in requires the maintained password-plus-TOTP flow or a valid one-time backup code; trusted-device and email/SMS bypasses are disabled.

### AC-M1.3-06 — Protected MFA secrets

TOTP seeds and backup codes are generated by maintained libraries, protected at rest, absent from logs/artifacts/client persistence, and shown only when strictly necessary.

### AC-M1.3-07 — Single-use backup recovery

Backup codes are shown once, individually consumed, replay resistant, and fully invalidated on regeneration/reset.

### AC-M1.3-08 — Safe staff session
