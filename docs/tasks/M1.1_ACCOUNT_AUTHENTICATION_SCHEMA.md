## 1. Status

- Milestone: M1 — Identity, Access, and Audit

## 2. Outcome

Integrate Better Auth into the accepted TypeScript modular monolith and establish the identity/authentication persistence boundary.

Deliver:

- Stable Better Auth integration using the accepted Drizzle and PostgreSQL stack.
- Reviewed, committed SQL migrations for the Better Auth core tables and application-owned account fields.
- One authoritative account record rather than a duplicated Better Auth user plus unsynchronized business user.
- Candidate, staff, and noninteractive service account types.
- Invited, active, locked, disabled, and closed account states.
- Verified-email state and verification-record foundation.
- Database-backed, server-revocable sessions with safe cookie settings.
- An application-owned current-account/session resolver that rejects nonactive accounts.
- Server-side primitives for revoking one session, all sessions, and all sessions during account restriction.
- Strict auth configuration validation and secret handling.
- Test-only synthetic account/session factories.
- Unit and real-PostgreSQL integration coverage for schema, status, verification, session, revocation, and data leakage.
- An architecture decision record defining ownership between Better Auth and the application.

This is a persistence and server-integration task. It must not implement candidate registration screens, password recovery, staff invitations, MFA, roles, permissions, scopes, route authorization, business audit persistence, or any hiring workflow.

## 6. Architecture Decision

### 6.1 One authoritative account record

Use the Better Auth user model as the physical implementation of the conceptual `user_account` entity unless the accepted repository already records another approved mapping.

The selected design must:

- Avoid a second application user table that can drift from the Better Auth user.
- Preserve Better Auth-required fields and relations.
- Add application-owned account type/status fields through supported schema extension or reviewed table mapping.
- Mark server-owned account fields as non-input fields so signup/profile input cannot assign them.
- Prevent sensitive account-control fields from being returned through ordinary auth responses unless explicitly required and reviewed.
- Keep roles, permissions, scopes, staff profiles, person/candidacy records, and business audit tables out of M1.1.

Record the exact choice in `ADR-0002-AUTHENTICATION-PERSISTENCE.md`.

### 6.2 Schema namespace

Prefer a dedicated PostgreSQL `auth` schema for Better Auth tables when supported by the accepted stable adapter. Keep application technical/business tables in the existing `app` schema and migration metadata in the existing migration schema.

If the adapter or current migration tooling cannot safely support a custom PostgreSQL schema, stop and document the incompatibility rather than silently placing tables in `public` or duplicating schema definitions.

### 6.3 Ownership boundary

| Concern | Owner |
|---|---|
| Password hash and credential linkage | Better Auth |
| Session token lifecycle | Better Auth |
| Email-verification token lifecycle | Better Auth |
| Account ID and normalized login email | Better Auth-backed user account |
| Account type and account status | Application-owned fields on authoritative account |
| Account-state transition policy | Identity-access domain/application layer |
| Role, permission, scope, separation of duties | M1.4, not Better Auth roles |
| Route/object/field authorization | M1.5 |
| Immutable business/security audit | M1.6 |

Do not use Better Auth role/admin features as a substitute for the project's authorization model.

## 7. Data Model

### 7.1 Better Auth core tables

Define the stable schema required by the selected Better Auth version, including its supported equivalents of:

- User/account identity table.
- Credential/provider account table.
- Database session table.
- Verification table.

Use the names and required columns produced by the reviewed Better Auth configuration and Drizzle schema generator. Do not manually omit library-required indexes, foreign keys, timestamps, or uniqueness constraints.

### 7.2 Application-owned account fields

The authoritative account record must support:

- `id`: nonsequential application-generated identifier compatible with Better Auth.
- `email`: normalized login email used for uniqueness and authentication.
- `email_display`: preserved display form when needed; never used for equality.
- `account_type`: `CANDIDATE`, `STAFF`, or `SERVICE`.
- `status`: `INVITED`, `ACTIVE`, `LOCKED`, `DISABLED`, or `CLOSED`.
- `email_verified` or Better Auth's required verified-email representation.
- `last_authenticated_at`, nullable.
- `disabled_at`, nullable.
- `disabled_reason_code`, nullable and drawn from a closed safe code set.
- `version`: optimistic-concurrency integer if compatible with Better Auth updates.
- Creation/update timestamps required by Better Auth and the application.

If a field cannot be safely added to the Better Auth user model, record the precise reason and stop before creating a second mutable source of truth.

### 7.3 Email normalization

Implement one server-owned normalizer used before account lookup/creation:

- Trim surrounding whitespace.
- Apply a documented Unicode normalization strategy supported by the application.
- Apply case normalization appropriate for login comparison.
- Reject invalid or excessively long addresses through a bounded schema.
- Preserve the user-entered/display form separately only when safe and necessary.
- Do not perform provider-specific rewriting such as Gmail dot removal or plus-address stripping.

Enforce uniqueness at the database layer on the normalized login email. Concurrency tests must prove two differently cased/normalized equivalents cannot create two accounts.

### 7.4 Account-type rules

- Candidate accounts may eventually register only through the controlled M1.2 flow.
- Staff accounts are invitation-only and may not self-register.
- Service accounts may not use interactive email/password sign-in.
- Account type is immutable through ordinary profile or auth endpoints.
- Changing account type is not implemented in M1.1.
- No client input may select `STAFF` or `SERVICE`.

### 7.5 Account-state rules

| State | Interactive sign-in | Existing session accepted | Intended meaning |
|---|---:|---:|---|
| `INVITED` | No, until invitation activation is implemented | No | Reserved staff/candidate invitation identity |
| `ACTIVE` | Yes when other auth conditions pass | Yes | Normal usable account |
| `LOCKED` | No | No | Temporary security restriction |
| `DISABLED` | No | No | Administrative/security disablement |
| `CLOSED` | No | No | Closed account retained under policy |

Only `ACTIVE` accounts can produce an authenticated application principal. Email verification remains an independent condition.

Do not implement public/admin controls for these transitions in M1.1. Provide tested application-layer primitives for later authorized use.

### 7.6 Database constraints and indexes

At minimum enforce:

- Primary keys and Better Auth-required foreign keys.
- Unique normalized account email.
- Unique session tokens as required by Better Auth.
- Appropriate verification identifier/value indexes required by the library.
- Closed checks/enums for application account type and status.
- Coherent disable fields, for example a disabled timestamp/reason when status is disabled if the approved design requires both.
- Bounded string lengths for account-owned fields.
- Cascades/restrictions that do not erase required future audit references.

Review every `ON DELETE` behavior. Deleting an auth account must not be exposed in M1.1; closed/retained state is preferred until retention rules and audit are implemented.

## 8. Migration Rules

- Drizzle TypeScript schema remains the source of truth.
- Use the Better Auth CLI only to generate or validate the schema shape. Do not use Better Auth's database migrate command against shared databases.
- Generate reviewed SQL through the accepted Drizzle migration workflow.
- Commit the Drizzle schema, migration SQL, metadata/snapshot files, and any Better Auth schema-generation configuration required for reproducibility.
- Never use `drizzle-kit push` against shared, CI, staging, or production databases.
- Migration must succeed from an empty database using the existing migration identity.
- The least-privileged application identity must have only the privileges required to read/write auth runtime tables and no schema-creation privileges.
- Existing M0 technical tables and seed behavior must remain intact.
- Do not seed default users, staff, passwords, sessions, or credentials.

The migration review must explicitly inspect secret-bearing columns, indexes, foreign keys, uniqueness, delete behavior, defaults, and schema grants.

## 9. Better Auth Configuration

### 9.1 Configuration factory

Create a server-only auth configuration factory under the identity-access module or shared auth infrastructure according to accepted boundaries.

It must:

- Use the accepted Drizzle database connection lifecycle.
- Use the reviewed Better Auth Drizzle adapter and exact schema object.
- Set the custom PostgreSQL schema name when approved.
- Load secrets and base/trusted origins only through validated server environment configuration.
- Integrate Better Auth logging with the M0.5 application logger without serializing credentials, tokens, cookies, user objects, headers, SQL, or raw errors.
- Keep framework route handlers thin.
- Fail closed on missing/unsafe production configuration.

### 9.2 Auth secret and base URL

- Require a high-entropy Better Auth secret outside test-only deterministic configuration.
- `.env.example` contains only a nonsecret placeholder.
- Test configuration uses an unmistakably synthetic deterministic secret isolated to disposable tests.
- Local development uses a developer-provided ignored secret.
- Production-like environments reject placeholder/test secrets.
- Base URL and trusted origins are explicit and validated; no wildcard origin is allowed.
- Never derive trusted origins from an untrusted request header.

### 9.3 Password support

Configure Better Auth's maintained email/password mechanism, but do not expose uncontrolled public registration in M1.1.

- Do not implement password hashing directly.
- Permit long passphrases and password-manager paste.
- Do not add arbitrary composition rules.
- Do not log password input, hashes, credential records, or auth request bodies.
- Known-compromised-password checking is deferred until a privacy-preserving provider/approach is approved; record this open control without pretending it is implemented.
- Candidate registration and recovery endpoints/UI belong to M1.2.
- Staff creation belongs only to the M1.3 invitation flow.

If Better Auth's catch-all handler would expose a generic signup endpoint, configure signup disabled or block it through a documented supported hook until M1.2 provides a controlled candidate path. Tests must prove client input cannot create a staff/service account.

### 9.4 Email verification foundation

- Require verified email before a candidate can perform future sensitive actions.
- Configure the Better Auth verification model and token lifetime through supported options.
- Verification tokens must be random, purpose-bound, expiring, and single use according to the library contract.
- Do not place tokens in logs, analytics, error details, page titles, or persistent browser storage.
- Do not implement the final verification page, resend UX, public candidate signup, or real email delivery in M1.1.
- Provide an application-owned email-delivery port or test capture seam needed by M1.2, without sending externally.
- Local/test delivery must remain in Mailpit or an in-memory capture adapter.

### 9.5 Session configuration

Use database-backed sessions and secure cookie behavior:

- HTTP-only session cookie.
- Secure cookie in production-like HTTPS environments.
- SameSite policy appropriate for same-origin browser flows.
- Narrow path/domain; do not use a broad shared parent domain without approval.
- Explicit idle/refresh and absolute expiration values drawn from configuration.
- Session identifier rotation through supported Better Auth behavior after authentication-sensitive changes.
- No auth token in URLs or browser local storage.
- Cookie cache disabled initially unless immediate account/session revocation is proven despite caching.
- No stateless-only JWT session mode.

The exact candidate/staff timeout policy is an open management/security decision. Implement bounded safe defaults for local/test and make policy values configurable and documented; do not claim final production approval.

### 9.6 Rate limiting and CSRF/origin protection

- Preserve Better Auth's supported CSRF/origin protections.
- Configure bounded authentication rate limiting through a supported mechanism suitable for local/test.
- Do not trust proxy/client IP headers without an approved ingress trust model.
- Production distributed rate-limit storage is deferred to the hosting decision; production configuration must not silently use a per-process limit if that would be ineffective across replicas.
- Do not disable origin checks to make automated tests pass.

## 10. Current Account and Session Resolver

Create an application-owned server-only resolver that converts a valid Better Auth session into the minimal application principal needed by later authorization work.

The initial principal contains only:

- Account ID.
- Account type.
- Account status.
- Email-verified boolean.
- Session ID/reference.
- Authentication timestamp/freshness information available from the library.

It must not yet contain roles, permissions, branch/team scope, candidate record ownership, or sensitive profile data.

On every protected server-side resolution:

1. Validate the Better Auth session through the supported server API.
2. Load/evaluate current account status from authoritative data rather than trusting stale client claims.
3. Reject missing, expired, revoked, malformed, or nonactive sessions safely.
4. Return no account-enumerating detail.
5. Bind the M0.5 correlation ID to safe auth log events.

Middleware may later provide navigation convenience, but it is not the authoritative resolver.

## 11. Session Revocation and Account Restriction

Implement server-side primitives, without UI, for:

- Revoke one session belonging to the current account.
- Revoke all sessions belonging to an account.
- Lock an account and revoke all sessions.
- Disable an account and revoke all sessions.
- Close an account and revoke all sessions.

Requirements:

- Use transactions where application state and session deletion are controlled through the same database boundary.
- Recheck current account version/status for concurrent changes.
- Be idempotent.
- Never return session tokens.
- Do not expose lookup differences to unauthorized callers; caller authorization is added later.
- A concurrent request with a session revoked/restricted before principal resolution must fail.
- Do not provide public route handlers or admin screens for these primitives in M1.1.
- Produce future-audit-ready result data containing safe codes and opaque references only, but do not persist business audit events yet.

If Better Auth's adapter/API prevents an atomic restriction-plus-revocation transaction, document the limitation and implement the safer sequence plus authoritative status recheck; do not falsely claim atomicity.

- Service account that cannot sign in interactively.

Factories must:

- Never expose plaintext session/verification tokens in ordinary test output.

- Provider-specific dot/plus rewriting is not applied.

### 13.4 Verification

- Verification records expire.
- Successful verification is single use.
- Wrong-purpose/malformed/expired/consumed token behavior fails safely.
- Verification responses/logs do not expose the token or whether an unrelated account exists.
- External email is never sent in local/test.

### 13.5 Session security

- Successful supported authentication creates a database session.
- Session cookie flags match environment policy.
- Session is absent from local storage and URLs.
- Expired/revoked/malformed session is rejected.
- Revoke-one leaves other sessions valid.
- Revoke-all invalidates all sessions.
- Lock/disable/close immediately prevents principal resolution.
- Concurrent status/revocation cases fail closed.
- No stale cookie cache preserves access after restriction.

### 13.6 Configuration and logging

- Missing secret/base URL fails safely.
- Placeholder/test secret is rejected in production-like configuration.
- Wildcard/untrusted origin is rejected.
- Auth errors map through the M0.5 safe error boundary.
- Password, hash, cookie, session token, verification token, authorization header, full email, request body, and database credential canaries never appear in logs/errors/artifacts.

### 13.7 Regression and boundaries

- Existing M0 unit/component/integration/E2E/security/CI suites remain green.
- Domain/shared account policy does not import Better Auth, Next.js, Drizzle, or HTTP types.
- No roles, permissions, route authorization, MFA, recovery, invitation UI, audit persistence, or business feature appears.

## 16. Acceptance Criteria

### AC-M1.1-01 — Stable supported integration

Better Auth and its Drizzle adapter are stable, compatible, lockfile-pinned, and isolated behind the identity-access infrastructure boundary.

### AC-M1.1-02 — One authoritative account

The Better Auth user model implements the conceptual user account without a second drift-prone mutable identity table.

Candidate/staff/service type and invited/active/locked/disabled/closed status are closed, database-constrained, non-client-writable fields.

No client or generic auth endpoint can self-create a staff or service account, and M1.1 does not expose uncontrolled candidate signup.

### AC-M1.1-06 — Verified-email foundation

Email verification state and expiring single-use verification records work through supported Better Auth behavior without external delivery or token leakage.

### AC-M1.1-07 — Revocable database sessions

Sessions are database-backed, cookie-secured, individually/all revocable, and never stored in URLs or browser local storage.

### AC-M1.1-08 — Immediate account restriction

Invited, locked, disabled, and closed accounts cannot resolve an authenticated principal even if a prior cookie/session exists.

### AC-M1.1-09 — Safe configuration

Auth secret, base URL, trusted origins, cookie policy, session lifetimes, and test/local behavior are validated and fail closed in unsafe production-like combinations.

### AC-M1.1-10 — Least-privilege database behavior

Migration identity applies schema changes; application identity can perform required runtime auth operations but cannot modify schemas/migrations.

### AC-M1.1-11 — Safe auth logging and errors

Credentials, tokens, cookies, hashes, emails, bodies, headers, SQL, and auth internals remain absent from logs, public errors, and test artifacts.

### AC-M1.1-12 — Real integration proof

Disposable PostgreSQL tests exercise actual migrations, Better Auth persistence, verification, sessions, revocation, restrictions, concurrency, and schema grants.

### AC-M1.1-13 — ADR recorded

ADR-0002 records the account ownership, schema namespace, migration, session, and deferred authorization decisions accurately.

### AC-M1.1-14 — Existing foundation remains healthy

All accepted M0 checks and hosted CI remain green.

### AC-M1.1-15 — Scope containment
