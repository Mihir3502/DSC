# Work Item M1.2 — Candidate Registration and Recovery

## 1. Status

- Milestone: M1 — Identity, Access, and Audit
- Status: Ready for implementation
- Execution order: After M1.1 is implemented, committed, and accepted
- Primary outcome: A candidate can securely create and verify a candidate-only account, sign in, recover access without account enumeration, change a password, review safe session summaries, and terminate sessions through accessible candidate-facing screens.

## 2. Outcome

Implement the complete candidate authentication journey on top of the accepted M1.1 account/session foundation.

Deliver:

- Controlled candidate-only registration from a validated public or candidate-invitation registration intent.
- Accessible candidate registration and sign-in screens.
- Email verification delivery, verification completion, resend, expiration, and single-use handling.
- Generic password-recovery request and secure password-reset flow.
- Safe password-change behavior for an authenticated candidate.
- Candidate security page listing masked active-session summaries.
- Sign out, revoke one owned session, revoke all other sessions, and sign out everywhere.
- Session rotation/revocation after authentication and recovery events.
- Local SMTP delivery to Mailpit and deterministic in-memory delivery in automated tests.
- Rate limiting, CSRF/origin protection, safe redirect validation, and enumeration resistance.
- Unit, component, real-PostgreSQL integration, accessibility, and Playwright candidate-auth journeys.
- Traceability updates for the implemented authentication requirements.

This task authenticates an account only. It must not create a person, position, candidacy, application, staff account, role, permission, scope, MFA enrollment, or immutable business-audit subsystem.

## 6. Candidate Registration Boundary

### 6.1 Candidate only

The registration path must force these values server-side:

- `account_type = CANDIDATE`
- Initial public-registration status determined by the accepted M1.1 state model.
- `email_verified = false`

The client may never submit or override account type, status, disabled fields, roles, scopes, permissions, organization, branch, team, or staff attributes.

Staff and service account creation remain impossible through candidate routes and Better Auth generic endpoints.

### 6.2 Registration source intent

M1.2 must support two future entry sources without prematurely creating M2 entities:

- `PUBLIC_POSITION`
- `CANDIDATE_INVITATION`

Because organization, position, person, and candidacy tables are introduced in M2, M1.2 must not create placeholder business rows or unvalidated foreign references.

Implement an application-owned registration-intent contract that provides only:

- A server-issued opaque intent identifier or validated signed state.
- Source type.
- Optional email binding for a candidate invitation.
- Issued/expiry time.
- Single-use/consumed state where persistence is required.
- An allowlisted post-verification continuation key, not an arbitrary URL.

For M1.2:

- A public intent may use a controlled generic continuation such as candidate security/account setup until M2 adds positions.
- An invitation intent must bind to the normalized invited email.
- Raw business position IDs supplied by a browser are not trusted or persisted.
- M2 may later add an authenticated association between the verified account and a real position/candidacy.

If a new registration-intent table is required, keep it in the identity-access boundary with no fake position foreign key and add a reviewed Drizzle migration. If the accepted Better Auth verification table safely supports this purpose without collision, document the model/purpose namespace and test it. Do not overload a password-reset or email-verification record ambiguously.

### 6.3 Registration form

The candidate registration screen collects only:

- Email address.
- Password.
- Password confirmation.
- Minimal display name only if required by the accepted Better Auth schema.
- Required notices/terms acceptance only if an approved current notice exists; otherwise defer rather than invent legal text.

Do not collect phone, address, SSN, date of birth, demographic data, employment history, work authorization, health data, documents, worker classification, or application answers.

### 6.4 Duplicate and concurrent registration

- Existing and new-account attempts return indistinguishable public outcomes where enumeration risk exists.
- Concurrent normalized-equivalent signup attempts create at most one account.
- An existing candidate receives a safe sign-in/verification path without revealing account state to another requester.
- Existing staff/service emails must not be converted to candidate accounts or disclosed.
- An invitation for one normalized email cannot create an account for another email.
- Consumed/expired/revoked intent behavior is generic and safe.

## 7. Password Policy

Use Better Auth's maintained hashing and verification.

Requirements:

- Permit password-manager paste and long passphrases.
- Enforce the approved bounded minimum and maximum through the server and accessible form guidance.
- Do not impose arbitrary uppercase/lowercase/number/symbol composition rules.
- Reject passwords containing control characters or unsafe encoding only when supported by a documented validation reason.
- Compare password confirmation only in the request/form layer; never store it.
- Never trim or silently transform a submitted password.
- Never log, return, persist outside the credential store, or place passwords in analytics/test artifacts.

Compromised-password checking must use the approved M1.1 security port:

- Production-like configuration fails closed if policy requires the check but no approved privacy-preserving adapter is configured.
- Local/test uses a deterministic synthetic adapter or approved local denylist fixture.
- No raw password is sent to an unapproved third party.
- Do not introduce an external network provider in M1.2 without a separate approval/ADR.

## 8. Email Delivery

### 8.1 Application-owned port

Implement or complete a narrow auth-email port supporting:

- Email verification.
- Password reset.
- Password-changed notification.
- Optional security notification for a duplicate signup attempt if approved.

The port accepts typed templates and bounded variables, not arbitrary HTML from user input.

### 8.2 Local and test adapters

- Local development sends through the existing Mailpit SMTP service.
- Automated tests use an in-memory/capture adapter unless specifically testing SMTP integration.
- At least one integration/manual check proves Mailpit receives each supported local template.
- No email leaves local/test infrastructure.
- Production-like startup rejects Mailpit/local SMTP settings and test adapters.

### 8.3 Message content

- Use minimal subject/body content.
- Do not include candidate application details, account existence explanations, internal status, staff names, or sensitive data.
- Use the configured application origin, never request-host headers, to build links.
- Escape display values and never accept user-authored HTML/template code.
- Do not use remote images, tracking pixels, third-party fonts, analytics parameters, or open redirects.
- Verification/recovery messages may contain only the necessary single-use link and generic support language.

### 8.4 Timing safety

Email dispatch must not create an obvious existence-based response difference.

- Recovery response is generic regardless of account existence/type/status.
- Duplicate registration response is generic.
- Queue/send work using the supported Better Auth hook and application port without waiting in a way that exposes account existence through response timing.
- Local/test assertions must avoid arbitrary sleeps; wait for a bounded observable capture event.

Do not add the production `pg-boss` worker in this task unless it was already accepted and implemented. A safe local asynchronous seam is sufficient; document the production delivery decision as deferred.

## 9. Token and Link Handling

### 9.1 Verification and reset tokens

Tokens must be:

- Generated by Better Auth or an approved library mechanism.
- High entropy.
- Purpose bound.
- Account/email bound where supported.
- Short lived through configurable approved durations.
- Single use.
- Stored hashed or otherwise nonrecoverably protected at rest for reset tokens as required by the security specification.
- Invalidated/consumed atomically on success.

Database tests must prove a captured raw reset token cannot be found in auth/verification table bytes or ordinary query results.

### 9.2 URL exposure

Session tokens are never accepted in URLs.

Verification/reset links necessarily carry a one-time capability. Prefer a custom callback that places the capability in a fragment or performs an immediate one-time exchange, then removes it from the visible URL with `history.replaceState` before rendering interactive content. The final design must ensure:

- The server access log receives no raw capability when technically possible.
- The token does not remain in browser history after page initialization.
- `Referrer-Policy: no-referrer` is applied.
- No third-party resource loads on token-processing pages.
- The token is absent from page titles, rendered errors, analytics, logs, screenshots, and Playwright traces.
- A token is never copied into a return/callback URL.

If the pinned Better Auth version cannot support a safe token-handling flow without exposing tokens to server logs or persistent browser history, stop and document the exact limitation rather than inventing an incompatible token mechanism.

### 9.3 Redirect safety

- Use a closed registry of post-auth destination keys.
- Resolve destinations server-side to same-origin relative paths.
- Reject absolute URLs, protocol-relative URLs, encoded scheme tricks, backslashes, control characters, userinfo, and nested redirect parameters.
- Default candidates to the minimal candidate security/home route available in M1.2.
- Do not redirect candidate sessions to staff routes.

## 10. Email Verification Flow

Implement:

1. Candidate submits a valid registration intent, email, and password.
2. Server forces candidate account type and creates/reuses a safe candidate registration state.
3. No authenticated session is issued before verified-email requirements pass.
4. Verification email is captured/sent through the auth-email port.
5. `/verify-email` handles safe initial, processing, success, expired, used, invalid, and resend states.
6. Successful verification marks email verified and activates an invited candidate account when the approved state transition applies.
7. Session issuance after verification follows the explicit approved option; prefer requiring sign-in unless automatic sign-in is reviewed and session rotation is proven.
8. Continuation uses the allowlisted registration intent, never an arbitrary callback URL.

Resend behavior:

- Returns a generic response.
- Enforces account/network/risk rate limits without revealing existence.
- Invalidates or safely supersedes prior verification records according to library behavior.
- Does not generate unlimited active tokens.

## 11. Candidate Sign-In and Sign-Out

### 11.1 Sign-in

`/sign-in` must:

- Accept normalized email and password through an accessible form.
- Return one generic invalid-credentials message for nonexistent account, wrong password, staff/service account at candidate entry, and restricted account where disclosure would create risk.
- Provide a separate safe verification-needed flow only when it does not expose an unrelated account and Better Auth's supported behavior is enumeration resistant.
- Rotate/create the session through supported Better Auth behavior.
- Reject invited, locked, disabled, closed, staff, and service accounts.
- Validate the return destination against the closed registry.
- Apply rate limits and origin/CSRF protections.

Do not expose staff sign-in behavior; `/staff/sign-in` remains M1.3.

### 11.2 Sign-out

- Sign out revokes the current server session and clears the cookie.
- GET requests do not perform sign-out state changes.
- A POST/action requires same-origin/CSRF protection.
- The post-sign-out destination is fixed or allowlisted.
- Repeated sign-out is idempotent and safe.

## 12. Password Recovery and Reset

### 12.1 Recovery request

`/recover`:

- Always returns the same generic confirmation regardless of account existence, type, verification, or status.
- Uses normalized bounded email input.
- Applies rate limits without allowing an attacker to lock out a target.
- Sends reset email only for an eligible candidate account.
- Does not reset/unlock/reactivate invited, locked, disabled, closed, staff, or service accounts.
- Does not reveal whether email delivery occurred.

Staff recovery follows M1.3's stronger support process and must not be available here.

### 12.2 Reset completion

`/reset-password`:

- Accepts only a valid purpose-bound, unexpired, unconsumed token.
- Validates new password and confirmation.
- Uses maintained Better Auth password reset behavior.
- Consumes the token atomically.
- Revokes all existing sessions for the candidate on success.
- Does not automatically unlock, enable, reopen, verify, or change account type.
- Sends a minimal password-changed notification through the email port.
- Shows the same safe invalid/expired/used state without technical detail.
- Requires the candidate to sign in again after successful reset.

Replaying the token, racing two reset requests, or using a token for another purpose must fail; at most one reset succeeds.

## 13. Authenticated Candidate Security Page

Implement `/candidate/security` with server-side current-account resolution.

The page shows:

- Masked candidate email.
- Verified-email status.
- Password-change form.
- Active session summaries.
- Current-session indicator.
- Safe actions: revoke one other session, revoke all other sessions, sign out everywhere.

Session summary may include:

- Opaque session ID/reference, never token.
- Current/other indicator.
- Created and last-active time.
- Expiry time.
- Coarsely parsed device/browser label when safe.
- Approximate location only if an approved privacy-preserving source exists; omit in M1.2 by default.

Do not show:

- Raw token.
- Full IP address.
- Complete user-agent string.
- Cookies/headers.
- Other accounts' sessions.
- Internal database IDs where a separate opaque reference is available.

### 13.1 Change password

- Requires the current password.
- Uses Better Auth's maintained change-password API.
- Revokes other sessions by default unless an approved policy explicitly differs.
- Rotates/revalidates the current session as supported.
- Sends a minimal password-changed notification.
- Applies recent-auth semantics available from M1.1 without implementing M1.3 step-up/MFA.
- Uses generic safe errors.

### 13.2 Session termination

- Server resolves the opaque session reference within the current account.
- Candidate cannot provide or obtain the raw session token.
- Ownership is rechecked at command time.
- Revoking another candidate's or a nonexistent session returns a non-enumerating denial.
- Revoking current/all sessions clears current access appropriately.
- Duplicate revocation is idempotent.

## 19. Acceptance Criteria

### AC-M1.2-01 — Candidate-only controlled registration

A valid server-controlled registration intent can create only a candidate account; staff/service type and account-control fields are impossible through browser/auth input.

### AC-M1.2-02 — No premature business records

Registration creates no organization, position, person, candidacy, application, role, scope, or staff record; future continuation is represented only by a validated intent.

### AC-M1.2-03 — Enumeration-resistant outcomes

Duplicate registration, sign-in failure, verification resend, and recovery request do not disclose whether an email/account exists, its type, status, or verification state beyond an approved signed-in context.

### AC-M1.2-04 — Verified email before session

An unverified candidate receives no authenticated candidate session; verification is expiring, purpose-bound, single use, and safely resendable.

### AC-M1.2-05 — Safe password handling

Maintained Better Auth password hashing is used; long passphrases/paste work; no arbitrary composition rule or password leakage exists; compromised-password policy fails closed when required.

### AC-M1.2-06 — Secure recovery

Recovery response is generic, reset tokens are protected at rest/short-lived/single-use, races allow one success, and reset does not activate or unlock restricted accounts.

### AC-M1.2-07 — Reset invalidates sessions

Successful password reset revokes all prior sessions and requires a new sign-in.

### AC-M1.2-08 — Safe email delivery

Local email goes only to Mailpit, tests use capture adapters, production-like configuration rejects local/test delivery, and templates contain minimal escaped data with safe links.

### AC-M1.2-09 — Secure candidate sign-in/out

Candidate sign-in accepts only active verified candidate accounts; sign-out is a protected mutation and clears/revokes the current session.

### AC-M1.2-10 — Candidate-owned session management

The security page exposes masked owned-session summaries using opaque references and supports revoke-one, revoke-others, and revoke-all without exposing tokens or other accounts.

### AC-M1.2-11 — Redirect, CSRF, cache, and rate-limit safety

All mutations enforce origin/CSRF and rate limits, personal/token pages are not cached, and only allowlisted same-origin destinations are used.

### AC-M1.2-12 — Token exposure minimized

No session token appears in a URL, and one-time verification/reset capabilities are removed from the visible URL/history and absent from logs/referrers/errors/artifacts.

### AC-M1.2-13 — Accessible responsive UI

Every candidate auth/security screen is keyboard usable, screen-reader understandable, mobile/reflow capable, and passes automated accessibility checks.

### AC-M1.2-14 — Real end-to-end proof

Playwright completes registration/verification/sign-in/recovery/reset/session-revocation journeys against real PostgreSQL and local capture/Mailpit with no external provider.

### AC-M1.2-15 — Safe evidence and traceability

Future-audit-ready event codes contain no sensitive fields, requirement traceability is accurate, and PRD-AUTH-007 remains marked incomplete until M1.6.

### AC-M1.2-16 — Foundation regression safety

All accepted M0 and M1.1 checks remain green in CI.

### AC-M1.2-17 — Scope containment

No staff invitation/MFA, role/scope authorization, audit persistence, M2 business entity, external email/provider, or M1.3 implementation is added.
