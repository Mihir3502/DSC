## 1. Status

- Milestone: M0 — Repository Foundation
- Status: Ready for implementation
- Execution order: After M0.5 is implemented, committed, and accepted
- Primary outcome: Every pull request and accepted main-branch change runs the repository's security, quality, database, build, and critical browser gates from a clean environment without production-capable credentials.

## 2. Outcome

Establish the first continuous-integration pipeline for the accepted M0 foundation.

Deliver:

- A least-privilege CI workflow for pull requests and the default branch.
- Frozen dependency installation using the repository-pinned Node and pnpm versions.
- Secret/prohibited-data scanning.
- Formatting, lint, strict typecheck, and module-boundary checks.
- Unit, component, coverage, migration-from-empty, and PostgreSQL integration tests.
- Production application build.
- Chromium critical Playwright smoke and accessibility coverage.
- Explicit critical-test skip detection and synthetic-data guards.
- Dependency vulnerability checking with a controlled, time-bounded exception process.
- Bounded, synthetic-only diagnostic artifacts.
- Concurrency cancellation, timeouts, and deterministic failure behavior.
- CI documentation and local parity instructions.
- `ADR-0001` documenting the accepted modular-monolith stack and development topology.

This task automates the already-approved M0.1–M0.5 checks. It must not deploy the application, create cloud infrastructure, introduce production credentials, add business functionality, or begin M1 identity/access work.

## 6. CI Security Model

### 6.1 Trust boundary

Pull-request code is untrusted. The workflow executes repository code, package lifecycle scripts, migrations, browser tests, and containers; therefore it must not receive production or staging credentials.

Rules:

- Use `pull_request`, never `pull_request_target`, for workflows that checkout and execute contributor code.
- Set top-level `permissions: contents: read` and override only when a documented job needs less or more. This baseline should not require write permissions.
- Do not provide cloud credentials, deployment tokens, package-publish tokens, SSH keys, production databases, real email credentials, or provider secrets.
- Do not use long-lived repository secrets for ordinary foundation tests.
- Do not expose secrets through command echo, debug logging, environment dumps, caches, artifacts, or failure annotations.
- Fork pull requests must execute safely without secret access.
- No workflow may approve, merge, label, comment, release, publish, deploy, or mutate repository contents.
- Dependabot or bot-originated pull requests receive the same untrusted-code treatment.

### 6.2 Synthetic configuration

CI uses only explicit test configuration:

- Synthetic database names, users, and passwords generated or defined for the ephemeral run.
- Loopback/container-only endpoints.
- Mail capture or disabled email transport.
- Local/test document storage under a temporary runner path.
- `NODE_ENV=test` for tests and an explicit non-production-safe build configuration where the application requires build-time validation.
- No production-like hostname, account number, bucket, API token, or provider endpoint.

The workflow must fail closed if a test command tries to use the normal developer database, a non-loopback external database, or production/staging provider configuration.

### 6.3 Action and dependency integrity

- Pin actions to full commit SHAs.
- Retain the human-readable release tag in a comment.
- Minimize the number of actions; prefer repository scripts over marketplace wrappers.
- Use the repository's `packageManager` field or accepted pin as the source of the pnpm version.
- Use `pnpm install --frozen-lockfile`.
- Do not automatically update the lockfile in CI.
- Do not enable package-manager caches that can execute or restore arbitrary build output.
- Cache only the pnpm package store through the supported setup mechanism; never cache `.env`, databases, private documents, Playwright traces containing nonsynthetic data, `.next` output across trust boundaries, or credentials.
- Do not execute unreviewed scripts downloaded at runtime.

## 7. Workflow Design

### 7.1 Triggers

The baseline workflow runs on:

- Pull requests targeting the repository's confirmed default branch.
- Pushes to the confirmed default branch.
- Manual `workflow_dispatch` for maintainers, with no free-text input interpolated into shell commands.

Do not add scheduled/nightly execution in M0.6 unless the repository already has an approved schedule. The test strategy's broader nightly matrix belongs to later implementation when full suites exist.

Ignore paths only if the exclusion is provably safe. A documentation-only optimization must not skip when `CLAUDE.md`, `AGENTS.md`, task packets, security policy, migrations, workflow files, lockfiles, test configuration, or scripts change. The safest M0.6 default is no path exclusion.

### 7.2 Concurrency and cancellation

- Use a concurrency group containing the workflow name and pull-request number or ref.
- Cancel an older in-progress run when a newer commit arrives for the same pull request/ref.
- Do not let cancellation hide the result required for the final commit under review.

### 7.3 Job structure

Use a small dependency graph that preserves fast feedback while avoiding duplicate expensive work. A recommended structure is:

1. `static-and-security`
2. `unit-component-coverage`
3. `database-integration`
4. `build`
5. `critical-e2e`, dependent on the build/foundation prerequisites when useful
6. `ci-gate`, an `if: always()` aggregation job that fails unless every required job succeeded

An alternative smaller job graph is acceptable if it meets every acceptance criterion and avoids hiding failures. Do not create a matrix with empty or duplicated suites merely to appear parallel.

### 7.4 Runner and shell

- Use a supported GitHub-hosted Ubuntu runner approved for the project.
- Pin the Node major/minor through the repository's existing version file or exact accepted mechanism.
- Use Bash with `set -euo pipefail` for multiline shell steps where appropriate.
- Quote variables and avoid constructing commands from event titles, branch names, commit messages, actor names, or manual inputs.
- Set job timeouts. No required job may run indefinitely.
- Do not use self-hosted runners for untrusted pull requests in this baseline.

### 7.5 Reusable setup

Keep setup understandable. Avoid a composite action until duplication clearly justifies one. Every required job should:

1. Check out the exact event commit.
2. Install the repository-approved pnpm version.
3. Install the pinned Node version with pnpm-store caching if approved.
4. Run `pnpm install --frozen-lockfile`.
5. Execute only its assigned repository scripts.

Do not check out a pull request's base branch after checking out the tested commit. Do not execute code from another ref.

## 8. Required Gates

### 8.1 Secret and prohibited-data scan

Implement both:

1. A maintained secret scanner covering the checked-out repository/history appropriate to the event.
2. The accepted M0.4 prohibited real-data/canary guard.

The secret scanner must be pinned immutably and configured through a reviewed committed file when exclusions are needed. Baseline or allowlist entries must:

- Identify the exact false positive.
- Contain no usable secret.
- Include owner, reason, approval, and expiry/review date.
- Be narrow by file, rule, and fingerprint where supported.

Do not suppress an entire directory or disable entropy/credential rules merely to make the first run pass. A finding that may be real is a stop condition until rotated and removed from reachable history according to the incident process.

If the selected scanner has licensing, fork-PR, API-token, or private-repository constraints, stop and present supported alternatives. Do not silently create a no-op `secret-scan` script.

### 8.2 Static quality

Run the accepted equivalents of:

```bash
pnpm format:check
pnpm lint
pnpm typecheck
```

The lint command must include existing module/import-boundary and sensitive-logging rules. Do not downgrade warnings or add broad ignores in M0.6.

### 8.3 Unit, component, and coverage

Run the accepted M0.4 scripts for:

- Unit tests.
- Component tests.
- Coverage.
- Critical-skip detection.
- Test-data/prohibited-pattern guard.

Do not introduce a numeric coverage threshold solely for M0.6. Preserve the honest baseline and make coverage generation fail on test failure.

### 8.4 Database and integration

Run the accepted M0.3/M0.4 migration-from-empty and integration suite.

- The harness owns a disposable PostgreSQL container/database.
- It applies actual committed SQL migrations in order.
- It runs the idempotent synthetic seed path where specified.
- It verifies UTC/schema/least-privilege behavior established by M0.3/M0.4.
- It never uses normal developer `DATABASE_URL`, Docker Compose volume, or a persistent external database.
- It always cleans up owned containers/resources, including after failure/cancellation where supported.

GitHub-hosted runners provide Docker for Testcontainers; use the accepted harness rather than replacing it with SQLite, an in-memory database, mocked migration results, or a separate untested CI-only database path.

### 8.5 Production build

Run the accepted production build with safe build-time configuration.

- Do not inject a production database or third-party credential.
- Do not weaken environment validation to make the build pass.
- Do not upload source maps or build output as public artifacts.
- Fail on TypeScript/framework build errors and unexpected external calls.

### 8.6 Critical Chromium E2E and accessibility

Run the accepted M0.4 critical Playwright suite for `/`, `/candidate`, and `/staff`:

- Install only the browsers/dependencies required for this baseline, preferably Chromium.
- Use Playwright's supported install command and pinned package version from the lockfile.
- Start the production-like local web server through accepted Playwright configuration.
- Use isolated browser contexts and synthetic fixtures.
- Run the accepted axe accessibility checks.
- Fail on page errors, unexpected console errors, unexpected network failures, or skipped critical tests.
- Never contact third-party providers or public application URLs.

Do not enable automatic test retries to convert a failure into a passing gate. One diagnostic retry may be added later only if the original failure remains visible and the approved flaky-test policy is implemented.

### 8.7 Dependency vulnerability check

Run a supported pnpm dependency audit or approved scanner against the committed lockfile.

- The command must exit nonzero for the approved severity threshold.
- An exception requires package/advisory, affected path, rationale, compensating control, owner, approval, and expiration date.
- Do not add a permanent `continue-on-error`.
- Do not automatically upgrade dependencies or rewrite the lockfile in CI.
- Treat registry/scanner unavailability as a visible infrastructure failure, not a passing scan.

License-policy enforcement may be added only if an approved license policy and maintained tool already exist. Do not invent legal approvals in this task.

## 9. Artifacts and Evidence

### 9.1 Allowed artifacts

Upload only synthetic, minimized diagnostic evidence when useful:

- Test-result summaries.
- Coverage report.
- Playwright trace/screenshots/videos only on failure and only after the sensitive-artifact guard passes.
- Scanner summaries that do not reproduce detected secret values.

### 9.2 Prohibited artifacts

Never upload:

- `.env` files or environment dumps.
- Database dumps or container volumes.
- Private document directories.
- Authentication state, cookies, sessions, tokens, headers, or browser storage state.
- Full raw logs containing unreviewed fields.
- Secret scanner output that reproduces complete credentials.
- Package-manager auth configuration.
- Source maps or build bundles merely for convenience.
- Any real candidate, employee, client, medical, screening, banking, identity, or provider data.

### 9.3 Retention and access

- Set explicit short retention, recommended 7 days for M0 diagnostic artifacts and never more than 14 days without an approved policy.
- Use unique artifact names containing job and run identifiers without untrusted text.
- Keep artifacts within the repository's authorized collaborators.
- Treat artifacts as sensitive test evidence even when synthetic.
- Artifact upload failure must remain visible. Do not allow it to hide a prior test failure.

### 14.2 Local parity

### 14.3 Clean-clone proof

In a temporary fresh clone or archive of the exact commit:

1. Confirm ignored local files are absent.
2. Install with the frozen lockfile.
3. Run the full CI command sequence.
4. Confirm migrations start from an empty disposable database.
5. Confirm no normal developer volume or `.env` is required.
6. Confirm generated artifacts are ignored.

Do not delete or reset the user's working repository or normal Docker volumes. Use a new temporary directory and disposable containers.

### 14.4 Triggered CI proof

After review and commit, push through the normal authorized workflow and record:

- Commit SHA.
- Workflow run identifier and URL.
- Job/check names and final conclusions.
- Node, pnpm, PostgreSQL, and browser versions.
- Lockfile hash.
- Migration/schema version.
- Test/coverage/security summaries without sensitive content.
- Artifact names and expiry dates.

If the agent lacks authorization to push or inspect hosted CI, it must stop after local verification and clearly mark hosted-run evidence as pending human action. It must not fabricate a successful remote run.

### 14.5 Controlled negative checks

Safely prove:

1. A lockfile-changing dependency manifest causes frozen install to fail.
2. A synthetic secret canary causes the secret/prohibited-data gate to fail without reproducing the canary in ordinary output.
3. A skipped critical test causes the guard/gate to fail.
4. A failing unit test fails its job and the aggregate gate.
5. A broken migration fails the disposable-database job without touching the normal developer database.
6. A build failure blocks the gate.
7. A critical E2E failure blocks the gate.
8. A high-severity dependency advisory fails according to policy, or a deterministic scanner-fixture test proves the configured threshold without altering project dependencies.
9. A workflow action changed from a SHA to a floating tag fails the workflow-policy guard.
10. Artifact retention outside the approved bound fails validation.
11. A production/staging URL or credential-shaped configuration in the CI workflow fails the guard.
12. Failure paths do not upload prohibited files or leak synthetic canary values.

Perform mutations only in temporary files/worktrees or through dedicated fixtures, and restore them without destructive commands.

## 15. Acceptance Criteria

### AC-M0.6-01 — Confirmed provider and safe triggers

The workflow targets the repository's actual GitHub default branch, runs on pull requests and default-branch pushes, supports safe manual runs, and never uses `pull_request_target`.

### AC-M0.6-02 — Least privilege

Workflow and job permissions are read-only/none; no write token, environment approval, deployment permission, or production-capable secret is supplied.

### AC-M0.6-03 — Immutable supply chain

All external actions use reviewed full commit SHAs, Node/pnpm derive from committed pins, and installation uses the frozen lockfile.

### AC-M0.6-04 — Required static and security gates

Secret/prohibited-data scan, formatting, lint/module boundaries, strict typecheck, and dependency vulnerability checks fail closed.

### AC-M0.6-05 — Required automated suites

Unit, component, coverage, migration-from-empty, real PostgreSQL integration, critical Chromium E2E, accessibility, and critical-skip guards all execute through accepted repository scripts.

### AC-M0.6-06 — Disposable database isolation

CI integration tests own disposable PostgreSQL resources and cannot fall back to a developer, staging, production, or persistent external database.

### AC-M0.6-07 — Safe production build

The production build succeeds with safe configuration and no production credential, external provider call, validation bypass, or uploaded build secret.

### AC-M0.6-08 — Deterministic orchestration

Jobs have timeouts, concurrency cancellation, explicit dependencies, nonzero failure behavior, and one aggregate required gate with no silent retries or `continue-on-error` on required checks.

### AC-M0.6-09 — Synthetic bounded artifacts

Only minimized synthetic evidence is uploaded, artifact names contain no untrusted text, retention is explicit and at most 14 days, and prohibited artifacts are excluded.

### AC-M0.6-10 — Clean-clone parity

A fresh checkout with no local `.env`, database volume, cache, generated output, or private files passes the same commands used by CI.

### AC-M0.6-11 — Workflow policy tests

Automated checks detect forbidden triggers, write permissions, floating actions, missing timeouts, unbounded retention, production configuration, and disabled required jobs.

### AC-M0.6-12 — CI documentation

Developers can reproduce the pipeline locally, understand artifacts and failures, and follow reviewed secret/advisory exception procedures.

### AC-M0.6-13 — ADR-0001 accepted foundation

ADR-0001 accurately records the accepted M0 architecture and clearly distinguishes implemented components from planned future components.

### AC-M0.6-14 — Hosted evidence is truthful

A real hosted run is recorded when authorized; otherwise the completion report marks it pending and never claims remote success.

### AC-M0.6-15 — Scope containment

No deployment, cloud infrastructure, production secret, authentication, authorization, persistent audit, business feature, worker, or M1 work is added.
