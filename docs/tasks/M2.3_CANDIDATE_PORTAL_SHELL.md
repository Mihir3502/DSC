# Work Item M2.3 — Candidate Portal Shell

## 1. Status

- Milestone: M2 — Candidate Intake and Application
- Status: Ready for implementation
- Execution order: After M2.2 is implemented, committed, accepted, and its completion evidence is approved
- Primary outcome: An authenticated candidate can enter a secure, accessible, mobile-ready portal shell and see only their own candidacy, a plain-language status, one accurate next action, and a foundational task list without exposing internal workflow data or implementing application drafts early.

## 2. Outcome

Implement the candidate-facing shell and read-model foundation on top of the accepted M0–M2.2 system.

Deliver:

- An authenticated candidate layout and `/candidate` home route.
- Permission-aware, route-aware candidate navigation with responsive desktop/mobile behavior.
- Safe handling of zero, one, or multiple owned candidacies.
- A candidate-visible status projection explicitly mapped from authoritative candidacy state.
- One deterministic prominent next-action card with safe title, explanation, due date, and action destination when available.
- A generic `work_item` foundation for candidate actions that remains subordinate to underlying domain records.
- `/candidate/tasks` with Action needed, Upcoming, Submitted/under review, and Completed views.
- A read-only application/candidacy landing shell that provides a valid destination before M2.4 without creating draft sections or answers.
- Compact progress counts and status summaries without invented percentages.
- Secure server-side ownership enforcement, explicit field projections, no-store/private caching, safe errors, and cross-candidate isolation.
- Loading, empty, unavailable, stale, session-expired, and safe-denial states.
- WCAG 2.2 AA-oriented semantics, keyboard behavior, focus management, reflow, touch targets, and screen-reader wording.
- Component, contract, authorization, security, accessibility, Playwright, and regression coverage.
- Traceability and data-model updates for the portal projection and work-item foundation.

This task does not implement application templates, questions, answers, autosave, attachments, submission, messages, documents, offers, screening, onboarding, training, competency, withdrawal, staff queues, or downstream workflow actions.

## 5. Specification Reconciliation

Use these interpretations unless an approved current ADR says otherwise:

- `/candidate` is the authenticated candidate source of truth, but underlying domain aggregates—not the dashboard—remain authoritative.
- Candidate-visible status is a separate mapping from internal candidacy stage/status. Internal codes are never shown directly.
- The portal may display only facts already supported by M0–M2.2. It must not fabricate downstream progress, requirements, messages, documents, or approvals.
- M2.3 may add the generic `work_item` persistence/query foundation because the implementation plan explicitly includes a task-list foundation.
- A work item is a derived/action coordination record. It never determines whether an application, offer, screening, onboarding item, training, or candidacy is valid.
- M2.3 may create or reconcile a single initial candidate task for an `APPLICATION_INCOMPLETE` candidacy, but it creates no application draft, application version, answer, section, or template.
- Completing the future underlying business action will complete its task transactionally; M2.3 does not implement those future completion commands.
- Until M2.4 provides application editing, the Application destination is a read-only candidacy/application landing shell with accurate status and no fake form.
- Navigation entries render only when their route capability is implemented and authorized. Do not ship dead links or inaccessible disabled links for future modules.
- `Documents`, `Messages`, and `Training` do not appear merely because the final design includes them; their modules register them later.
- Profile/security links may reuse accepted M1/M2.2 account pages. This task does not redesign authentication or broad profile editing.
- If a person owns multiple candidacies, the portal selects a current context deterministically and offers an accessible owned-candidacy switcher; client selection never grants access.
- Progress uses truthful counts/state labels. Do not display a percentage when the denominator is unknown or requirements have not been generated.
- A notification indicator remains absent until a real authorized notification source exists; never show a fake zero badge.

## 7. Candidate Context Resolution

### 7.1 Server-derived identity

Every candidate page must:

1. Require a current candidate-audience session.
2. Resolve the current candidate account server side.
3. Resolve its active canonical person through the M2.2 ownership link.
4. Load only candidacies belonging to that person through an ownership-constrained query.
5. Apply candidate-visible field projection before delivery or caching.

Never accept `person_id`, account ID, or an ownership flag from the client.

### 7.2 Zero candidacies

Show a safe empty state with:

- A plain-language explanation.
- Link to currently available positions when appropriate.
- Help/contact route from approved configuration.
- No implication that another record/account exists.

Do not create a default candidacy or person to populate the portal.

### 7.3 One candidacy

Select it as current automatically. Do not show a redundant switcher.

### 7.4 Multiple candidacies

Select current context deterministically using approved policy, for example:

1. Active candidacy requiring candidate action.
2. Other active candidacy with nearest known due date.
3. Most recently updated active candidacy.
4. Most recently closed candidate-visible candidacy.
5. Stable external-ID tie-breaker.

Provide an accessible switcher showing only approved opening title/location, human candidate reference, and candidate-visible status. A route/query-selected candidacy must be revalidated against the current person on every request. Tampering returns the approved safe result and no fallback data from the requested record.

## 8. Candidate-Visible Status Projection

Create an explicit, versioned mapping contract. For states available at M2.3:

| Authoritative state | Candidate label | Candidate explanation | Default action |
| --- | --- | --- | --- |
| `PROSPECT` with valid invitation/activation path | Get started | Finish setting up access or begin your application | Approved claim/start route when available |
| `PROSPECT` awaiting staff review | Under review | We are reviewing your information. No action is needed right now. | None or Help |
| `APPLICATION_INCOMPLETE` | Application in progress | Complete your application to continue. | Read-only application landing until M2.4; editable route after registration |
| Candidate-visible closed prospect | Application not continuing | This application process is no longer active. | View details/help if approved |
| Temporarily unavailable projection | Status unavailable | We could not load your current status. Try again safely. | Retry |

Rules:

- Internal stage/status/source/duplicate/owner/reason codes never render directly.
- Mapping is exhaustive for accepted M2.2 states; an unknown value fails closed to a generic unavailable state and generates safe internal telemetry.
- Candidate wording does not promise selection, employment, contractor approval, eligibility, timing, or legal outcome.
- Do not infer progress from timestamps alone.
- Candidate-visible close/review explanations come from approved codes/templates, never internal comments.
- Later modules extend this registry with reviewed mappings rather than embedding scattered `if` statements in components.

## 9. Next-Action Resolver

Return exactly one prominent next action per selected candidacy, or an explicit no-action state.

Resolution order:

1. Revalidate current candidate ownership and candidacy state.
2. Load open candidate-action-required work items authorized for that candidacy.
3. Revalidate each work item's underlying target/state through its registered resolver.
4. Discard/cancel stale or no-longer-actionable items through a controlled reconciliation path.
5. Rank valid items by blocking/action-required status, approved priority, due date, creation time, and stable ID.
6. If no work item exists, use a reviewed stage-derived fallback such as `COMPLETE_APPLICATION` for `APPLICATION_INCOMPLETE`.
7. Resolve a route key through an allowlisted server-owned route registry.
8. Return candidate-safe title, explanation, status, optional due date/timezone, estimated duration only when configured/evidenced, and action label/destination.

Never:

- Trust a stored arbitrary URL or client route.
- Show a work item whose underlying record is inaccessible/stale.
- Infer a due date or estimated duration.
- Use internal priority/risk labels as candidate language.
- Expose staff owner, staff task, blocker codes, internal reason, target table/type, or record ID.
- Let the candidate mark a business task complete from the generic task card.

If a future route capability is not yet registered, show the accurate status without an action link and with approved explanatory/help text. Do not link to a 404 or a placeholder form.

## 10. Work-Item Foundation

Implement `work_item` equivalents consistent with `docs/DATA_MODEL.md`:

- Nonsequential internal ID and candidate-safe external ID only if a task route requires one.
- Candidacy ID.
- Bounded `work_type_code` from a versioned registry.
- Bounded target-record type and target ID, validated by the work-type registry.
- Optional assigned user/team for future staff tasks; candidate tasks do not rely on these for candidate ownership.
- `candidate_action_required` boolean derived/set only by trusted commands.
- Status: `OPEN`, `IN_PROGRESS`, `BLOCKED`, `COMPLETED`, or `CANCELED`.
- Approved priority code used for deterministic ordering, not exposed as internal risk.
- Optional due-at instant and display timezone rules.
- Completed-at and completion-event/reference where applicable.
- Optimistic version and common timestamps.
- Source event/command or idempotency identity sufficient for deduplication.

### 10.1 Initial work type

Register the minimal M2.3 work type:

- `COMPLETE_APPLICATION`
- Audience: candidate
- Target: candidacy
- Valid underlying state: owned active `APPLICATION_INCOMPLETE`
- Candidate label: Complete your application
- Candidate status: Action needed
- Route key: application landing/edit capability resolved through the route registry
- Completion: future successful M2.6 submission, not a generic checkbox

If M2.2 completion evidence already created an equivalent task using an approved code, adopt it rather than duplicating it.

### 10.2 Invariants

- Work items are not the source of truth for candidacy or later workflow state.
- At most one active item exists for the same candidacy/work type/target unless the registry explicitly allows multiples.
- Candidate-action items belong to the same candidacy returned by the owning person query.
- Business actions create/update/complete/cancel tasks transactionally or via an idempotent post-commit reconciliation explicitly documented for read-only backfill.
- Candidate cannot create, edit, reprioritize, reassign, complete, cancel, or change due dates through generic task endpoints.
- No arbitrary candidate-facing text or URLs are stored in task rows.
- No hard deletion; obsolete tasks become canceled and remain in authorized history.

## 11. Existing-Candidacy Reconciliation

M2.3 may need to create the initial `COMPLETE_APPLICATION` task for candidacies accepted before the work-item table existed.

Use one reviewed approach:

- Migration-safe deterministic backfill when all qualifying rows are known and data volume is bounded, or
- Idempotent reconciliation command/job using stable deduplication keys.

Requirements:

- Synthetic/local/staging evidence before production use.
- No candidate/staff action is invented beyond authoritative M2.2 state.
- Re-running creates no duplicates.
- Closed, merged-inaccessible, terminal, wrong-stage, or unowned prospects do not receive the task.
- Reconciliation emits safe audit/operational evidence only when required by accepted policy; it does not pretend a candidate performed an action.
- Failure leaves candidacy state unchanged and is retryable.

Do not write task rows opportunistically from a GET request unless an approved architecture decision explicitly allows that pattern. Candidate page reads are side-effect free.

## 17. Authorization Model

Candidate portal access requires:

- Current authenticated candidate audience.
- Active/eligible account state under M1 policy.
- Verified email where required by accepted candidate policy.
- Active account-to-person ownership link.
- Requested candidacy belongs to that person.
- Requested task belongs to that candidacy and is candidate visible.
- Underlying target is still candidate accessible and action eligible.
- Exact field projection for the route/purpose/state.

Staff role, candidate reference, public reference, URL possession, task external ID, or cached client state never grants candidate access.

Candidate A must not learn whether Candidate B's candidacy/task exists. Unauthorized and nonexistent identifiers return the approved indistinguishable safe response where discovery creates privacy risk.

If the same account also has a staff role, audience separation remains explicit. Candidate portal requests use candidate authority only; staff authority is not unioned into candidate responses.

## 18. Query and Route Design

Use named queries such as:

- `get_candidate_portal_summary`
- `list_candidate_candidacies`
- `get_candidate_application_landing`
- `list_candidate_work_items`
- `resolve_candidate_next_action`

Each query:

1. Derives the account/person from the current server session.
2. Applies ownership in the database/repository predicate.
3. Applies state and field policy.
4. Revalidates work-item target/action capability.
5. Returns a candidate-specific DTO.
6. Emits safe operational telemetry without PII/high-cardinality record labels.

No generic `getById` route returns person/candidacy/task objects. No client component joins separate unrestricted endpoints to construct authorization-sensitive state.

GET/read routes are side-effect free. Task reconciliation uses migrations, commands, jobs, or transactionally coupled future business actions—not page loads.

## 19. Caching and Freshness

- Candidate-authenticated HTML and JSON default to `private, no-store` unless a reviewed user-bound cache design proves safe.
- Never use a shared/public cache for portal content.
- If request memoization is used, key it by authenticated subject, person, selected candidacy, authorization/projection version, and relevant aggregate versions.
- Do not key solely by candidacy/task external ID.
- Revalidate fresh account/ownership/candidacy/task state on action navigation and all future mutations.
- Projection/materialized-view lag must not make a stale action executable.
- Status/task/capability changes invalidate or bypass stale summaries after commit.
- Browser/service-worker storage must not persist portal PII or cross-account response data.
- Sign-out, account disable, ownership change, person merge, and session revocation must make prior portal state inaccessible on refresh/back navigation.

## 20. Security and Privacy

- Use server-rendered or protected same-origin delivery consistent with the accepted architecture.
- Enforce secure session cookies, origin/CSRF policy for any state-changing menu/session action, CSP, security headers, safe redirects, and output encoding.
- Keep candidate references and nonsequential IDs nonsecret; authorization still applies.
- Do not place name, email, phone, date of birth, address, internal IDs, duplicate state, staff details, or task target IDs into URLs, logs, traces, metrics labels, analytics, error messages, page titles, browser storage, source maps, screenshots, or CI artifacts.
- Bound candidacy/task list sizes, filters, query values, and response payloads.
- Resist identifier enumeration, cross-account cache poisoning, confused-deputy audience switching, open redirects, stale action replay, and DOM injection.
- Render only maintained code-owned candidate wording; do not render arbitrary staff notes or HTML.
- Use synthetic data/canaries only in tests and demos.
- Do not load external analytics/chat widgets or third-party content that receives portal data.
- Safe errors expose a correlation reference, not record/authorization/database detail.

## 21. Accessibility and Responsive Behavior

Meet WCAG 2.2 AA expectations for the delivered journey:

- Skip link, semantic header/nav/main/footer, landmarks, and one clear page heading.
- Current navigation state conveyed programmatically and visually.
- Mobile menu has correct name/state, focus containment/restoration where appropriate, Escape behavior, and no background interaction while modal.
- Logical keyboard order, visible focus, no keyboard trap, and sufficiently large touch targets.
- Status/action meaning never depends on color/icon alone.
- Task filters use accessible controls and announce result updates appropriately.
- Candidacy switcher has explicit label/context and preserves focus after change.
- Dates/times include clear timezone and screen-reader-friendly text.
- Loading uses non-disruptive status semantics; errors and session expiry move focus to a useful heading/alert.
- 200% zoom and narrow mobile reflow have no clipped controls or horizontal page scrolling for ordinary content.
- Reduced-motion preferences are respected.
- Heading/card/list/link text remains understandable out of context.
- No misleading disabled link masquerades as an action.

Test keyboard-only, screen reader, zoom/reflow, touch, contrast, reduced motion, and session-timeout behavior manually and automatically where supported.

## 22. Observability and Audit

Ordinary portal reads are not business mutations and do not create append-only business audit events unless accepted policy explicitly requires a sensitive-access event.

Use privacy-safe operational telemetry for:

- Portal summary success/failure/latency.
- Status-mapping unknown/fallback occurrences.
- Next-action resolver stale/unknown work type.
- Task reconciliation success/failure counts.
- Authorization denial category without target existence/PII.
- Client error boundary and route failure.

Use bounded codes and low-cardinality dimensions. Do not include account/person/candidacy/task IDs, candidate reference, names, contact values, routes containing record IDs, or task titles as metric labels.

If M2.3 adds a migration/backfill/reconciliation command that changes work items, use the accepted audit/operational-event policy with safe actor/source/version/count metadata. Page views do not masquerade as candidacy activity.

- Candidate-action-required consistency rules.

## 27. Acceptance Criteria

### AC-M2.3-01 — Secure portal entry

`/candidate` requires a current candidate session, resolves the server-side account/person ownership link, and returns only explicit candidate-safe data; wrong audience, disabled/revoked/unverified states, or missing ownership fail safely.

### AC-M2.3-02 — Candidacy context

Zero/one/multiple owned candidacies render truthful states; deterministic selection and an accessible switcher never expose or authorize another person's candidacy.

### AC-M2.3-03 — Candidate-visible status

Every accepted M2.2 state maps through one versioned exhaustive registry to plain candidate wording; internal/unknown/duplicate/owner/reason codes never leak, and unknown states fail closed.

### AC-M2.3-04 — Next action

The home page presents exactly one revalidated highest-priority candidate action or an explicit no-action state, using truthful due/estimate data and an allowlisted implemented route capability.

### AC-M2.3-05 — Work-item foundation

Work items use reviewed fields/constraints/indexes/registry, remain subordinate to underlying state, cannot be mutated generically by candidates, preserve history, and prevent duplicate active items.

### AC-M2.3-06 — Initial application task

Each eligible owned active `APPLICATION_INCOMPLETE` candidacy has at most one `COMPLETE_APPLICATION` task; backfill/reconciliation is bounded/idempotent and creates no application record or false actor history.

### AC-M2.3-07 — Candidate home

Home shows approved opening/reference/status/action/task counts/help only; it does not fabricate downstream panels, percentages, messages, deadlines, or staff/internal information.

### AC-M2.3-08 — Navigation shell

Desktop/mobile navigation is semantic, responsive, route/feature aware, current-state aware, and free of dead/disabled future-module links; audience separation remains intact.

### AC-M2.3-09 — Application landing boundary

An owned read-only application landing route accurately represents candidacy state and next action without template, draft, answer, section, attachment, certification, or submission behavior.

### AC-M2.3-10 — Task list

`/candidate/tasks` provides bounded, stable, server-validated candidate-safe filters/cards/counts, revalidates target state, and exposes no staff task, target internals, or stale action.

### AC-M2.3-11 — Cross-candidate isolation

Candidate A cannot infer or access Candidate B's person, candidacy, task, count, status, opening context, or route capability through ID tampering, filters, caches, errors, timing, browser state, or direct requests.

### AC-M2.3-12 — Caching and session safety

Portal responses cannot cross users or survive sign-out/revocation/ownership change through shared caches, service workers, browser storage, back navigation, or stale action execution.

### AC-M2.3-13 — Security and privacy

PII/internal data is absent from prohibited URLs/logs/metrics/analytics/errors/client artifacts; content is encoded; redirects/routes are allowlisted; pages resist enumeration, injection, cache poisoning, and audience confusion.

### AC-M2.3-14 — Accessibility and mobile

The shell, navigation, candidacy switcher, status, next action, application landing, filters, task list, errors, and session state meet the specified keyboard, screen-reader, focus, contrast, reflow, zoom, touch, and reduced-motion behavior.

### AC-M2.3-15 — Tests and regression

Migration/query/component/contract/authorization/security/accessibility/browser tests pass; M0–M2.2 gates pass twice; no critical test is skipped/quarantined/focused.

### AC-M2.3-16 — Scope containment

Traceability accurately describes delivered behavior and no application draft, attachment, submission, messaging/document/downstream workflow, staff workspace, provider, production data, generic CRUD, or M2.4+ scope is added.
