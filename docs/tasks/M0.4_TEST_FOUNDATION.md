## 6. Test Architecture

### 6.1 Test levels established now

| Level | Runner/environment | Foundation proof in M0.4 |
|---|---|---|
| Unit | Vitest, Node | Existing pure configuration/helper behavior |
| Component | Vitest, jsdom, React Testing Library | Existing reusable presentational UI behavior and semantics |
| Integration | Vitest, Node, disposable real PostgreSQL | Migrations, seed, timezone, connection, and role privileges |
| End to end | Playwright, production-like local server | Three foundation routes load and navigate correctly |
| Accessibility | Playwright plus axe, with manual keyboard review | Foundation routes have no serious/critical automated violations |

Do not create meaningless production code merely to manufacture a test at every level. Select real foundation behavior already delivered by M0.1–M0.3. A small extraction is allowed only when it creates a genuinely reusable boundary and does not change behavior.

### 6.2 Separation rules

- Unit/component tests must not connect to PostgreSQL, Docker, external services, or the network.
- Integration tests use real PostgreSQL, never SQLite, mocks, or an in-memory substitute.
- Browser tests use only the locally started application and must block or fail unexpected third-party network calls.
- Each test must be independently repeatable and must not depend on test ordering.
- Test configuration must not leak Node-only modules or server secrets into client bundles.
- Framework configuration should be explicit rather than inferred from filename collisions.
- Jest and Cypress must not be added.

### 7.2 Vitest configuration

Create a root Vitest configuration using named projects or an equivalent current stable mechanism:

- `unit`: Node environment; pure source tests only.
- `component`: jsdom environment; loads one shared Testing Library setup file.
- `integration`: Node environment; includes only PostgreSQL integration tests and uses the dedicated disposable-database lifecycle.

Requirements:

- Include/exclude patterns are disjoint and documented.
- Production code is transformed with the repository's TypeScript/path-alias settings.
- Component setup imports `@testing-library/jest-dom/vitest` once and cleans up reliably.
- No global mutable fake clock, random source, UUID, or database state may leak between tests.
- Integration concurrency must match the chosen isolation model. Use one worker initially if parallel workers cannot each receive a distinct disposable database safely.
- Local runs have zero retries. CI behavior may allow at most one diagnostic retry later, but a retry must not turn a flaky test into a silent success.
- Skipped or focused critical tests are detectable by the M0.4 guard described in section 7.9.

### 7.3 Unit-test example

Add meaningful unit coverage for accepted foundation behavior, preferably typed environment/configuration parsing or another existing pure helper.

- One valid case.
- One invalid or boundary case.
- Safe error output that identifies the bad setting without revealing a password or complete credential-bearing URL.

If the chosen environment module terminates the process or reads global state at import time, refactor only enough to expose a pure parser while preserving the existing public behavior.

### 7.4 Component-test example

Test one existing reusable foundation component or page-level presentational component with React Testing Library.

Requirements:

- Query by role, accessible name, label, or visible text; do not rely on CSS selectors or implementation details.
- Use `userEvent.setup()` for user interaction.
- Assert an observable outcome such as accessible navigation, button behavior, or status content.
- Include a keyboard interaction where the component is interactive.
- Do not attempt to render an async Server Component directly in jsdom. Extract or select a pure presentational/client boundary only when appropriate.
- Do not snapshot entire pages as the primary assertion.

### 7.5 PostgreSQL integration-test harness

Use `@testcontainers/postgresql` to launch a fresh, disposable PostgreSQL container for the integration project.

The harness must:

- Pin the same PostgreSQL major version and compatible image family used by the accepted M0.2 Compose configuration.
- Let Testcontainers allocate host resources/ports instead of assuming the developer's Compose port.
- Generate synthetic test-only database names and credentials.
- Set `APP_ENV=test` for the harness.
- Provide test-scoped runtime, migration, and bootstrap connection values through an explicit test context.
- Apply the actual committed M0.3 migrations, not copied SQL or ORM schema synchronization.
- Run the actual synthetic seed path where seed behavior is under test.
- Stop the container and close all connection pools even when setup or a test fails.
- Emit actionable diagnostics without printing passwords or full connection URLs.
- Fail clearly when Docker is unavailable.

The harness must not:

- Read or fall back to the normal `DATABASE_URL`, `DATABASE_MIGRATION_URL`, or `DATABASE_ADMIN_URL` as a test target.
- Connect to the M0.2 Compose database.
- delete/reset any pre-existing database, schema, volume, or container.
- use `drizzle-kit push`, startup auto-sync, SQLite, or an in-memory database.
- expose a reusable destructive reset command.

Prefer one container for the integration project with a clean database/schema established before the suite, followed by transaction rollback or another explicit isolation mechanism per test. If migration tests require a pristine database, create a new database within the owned container or launch a dedicated owned container; validate ownership before cleanup.

### 7.6 Database foundation integration tests

Automate the M0.3 database proof. At minimum verify:

1. All committed migrations apply to an empty disposable PostgreSQL database.
2. `app.system_metadata` has the approved columns, types, primary key, nullability, and timezone-aware timestamps.
3. The configured Drizzle migration journal exists in the approved schema.
4. Running the migration command a second time succeeds as a no-op.
5. Running the seed twice leaves one deterministic technical record and no business data.
6. The database session timezone and timestamp behavior are UTC.
7. The application role can perform expected DML on `app.system_metadata`.
8. The application role cannot create, alter, or drop application schema objects and cannot manage roles.
9. Expected connection pools/clients are drained after the suite.
10. No candidate, account, screening, offer, onboarding, readiness, assignment, timesheet, payroll, leave, audit, or job table exists.

Use PostgreSQL catalog assertions where they provide a precise result. Do not assert only that a command exited zero.

Define projects so future main/nightly execution can cover Chromium, Firefox, and WebKit without rewriting tests. M0.4 must install and verify Chromium for critical pull-request-style smoke coverage; downloading and executing every browser locally is not required in this task.

### 7.9 Synthetic fixtures and real-data canary

It must exit nonzero for a seeded forbidden example and must avoid printing the full sensitive match. This is a foundation guard, not a general-purpose DLP system.

Add a critical-test guard that exits nonzero when committed critical browser tests contain focused tests or an unapproved skip/fixme marker. Keep its scope narrow enough to avoid false positives in documentation or dependencies.

## 10. Determinism and Isolation Rules

- Tests run correctly in any order.
- Unit/component tests do not depend on a developer `.env` file.
- Integration credentials are generated for the owned disposable container.
- Browser tests run with an explicit test environment and synthetic data only.
- Restore mutated process environment, timers, mocks, and global objects after each test.
- Use fixed clocks only inside the test scope that needs them.
- Do not share mutable fixture objects across tests.
- Do not depend on public internet access.
- Do not rely on arbitrary sleeps; wait on observable state with bounded timeouts.
- Do not mark a test skipped because it is flaky. Fix or report the blocker.
- Failure output must be useful but must not reveal credentials, cookies, authorization headers, request bodies, or full page content.

## 11. Security and Privacy Rules

- All test data is synthetic.
- No production export, screenshot, document, token, credential, or copied personal information may enter the repository or generated reports.
- `.env` files and Playwright storage state remain untracked.
- Tests must never send email, call screening/signature providers, or reach third-party hosts.
- Testcontainers connection strings stay process-local and are not logged in full.
- Browser artifacts use retention-on-failure behavior and ignored locations.
- Any secret-shaped test constant is clearly fake and uses reserved/local values.
- A malicious developer `DATABASE_URL` must not redirect integration tests away from their owned container.
- Cleanup is limited to resources created and positively identified by the current test run.

- Critical E2E runner exercises all three foundation routes in Chromium.
- Accessibility runner scans all three routes.
- Data guard passes on the repository and fails against a controlled forbidden-canary fixture.
- Critical-test guard passes on committed critical tests and fails against controlled focused/skipped sample text.
- Coverage runner produces a report with no fabricated exclusions.
- Repeating the complete foundation suite does not depend on residue from the first run.
