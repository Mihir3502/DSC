- Milestone: M2 — Candidate Intake and Application

## 5. Specification Reconciliation

The implementation plan and UI flow require a hiring cycle, while the current data model defines organization, branch, team, position, and job-description version but does not fully define `hiring_cycle`.

M2.1 must update `docs/DATA_MODEL.md` to add the accepted hiring-cycle entity and relationships before or with implementation. The approved interpretation is:

- A `position` is reusable business configuration describing a role the agency may fill.
- A `job_description_version` is immutable published wording/history for a position.
- A `hiring_cycle` is one specific opening/application window for a position at a branch and optional team.
- Public “position” list/detail pages display a safe hiring-cycle projection because multiple openings may exist for one reusable position.
- A candidacy created in M2.2 will reference the selected hiring cycle and its position/branch snapshot.

Do not create a second competing concept such as job posting, requisition, vacancy, campaign, or opening unless the reviewer explicitly renames `hiring_cycle` everywhere in the same approved change.

Do not create a new ADR solely to restate this task. If implementation reveals a material architectural choice, first inspect the current ADR numbering/index and obtain review rather than colliding with an existing ADR number.

## 6. Domain Boundaries

The `organization` module owns:

- Organization, branch, and team hierarchy.
- Position configuration.
- Job-description version lifecycle.
- Hiring-cycle lifecycle and public availability policy.
- Public position-list/detail projections.
- Real scope-resolution facts for organization/branch/team resources.

It does not own:

- User-role assignments or authorization policy.
- Person/candidate identity.
- Candidacy/application creation.
- Worker-classification decisions.
- Offers, requirements, screening, onboarding, training, competency, or readiness.
- Notifications or external provider delivery.

M2.1 commands call M1 authorization and audit services; they do not duplicate those systems.

## 7. Organization Model

### 7.1 Fields

Implement `organization` with equivalents of:

- Nonsequential ID.
- Unique normalized organization code.
- Legal name.
- Public display name.
- Valid IANA timezone.
- Status: `DRAFT`, `ACTIVE`, `INACTIVE`, or `ARCHIVED`.
- Optimistic-concurrency version.
- Created/updated timestamps and actor references where the accepted convention requires them.

Release 1 may operate one organization, but the schema and authorization boundaries must not hard-code a global singleton or assume the first row is authoritative.

### 7.2 Rules

- Organization code is stable after activation and unique case-insensitively.
- Legal/display names are bounded plain text and normalized for validation, not silently rewritten for display.
- Only `ACTIVE` organizations may contain publicly open hiring cycles.
- Inactivation prevents new/public openings but preserves all history.
- Archive is allowed only when no active branch, position, cycle, scope assignment, or future business reference requires the organization.
- No ordinary hard delete.
- Organization status changes use named commands, optimistic versioning, authorization, reason code, and atomic audit.

## 8. Branch and Team Models

### 8.1 Branch

Implement `branch` with equivalents of:

- Nonsequential ID.
- Organization ID.
- Code unique case-insensitively within organization.
- Bounded name.
- Valid IANA timezone, defaulted server-side from organization only when explicitly confirmed.
- Status: `DRAFT`, `ACTIVE`, `INACTIVE`, or `ARCHIVED`.
- Optimistic version and timestamps.

### 8.2 Team

Implement `team` because M1 authorization supports team scope and the accepted data model already defines it:

- Nonsequential ID.
- Branch ID and organization relationship derived/enforced through branch.
- Code unique case-insensitively within branch.
- Bounded name.
- Status: `DRAFT`, `ACTIVE`, `INACTIVE`, or `ARCHIVED`.
- Optimistic version and timestamps.

### 8.3 Hierarchy rules

- A branch belongs to exactly one organization.
- A team belongs to exactly one branch.
- Parent/child organization consistency is enforced by database constraints and application policy, not request input.
- Parent inactive/archived state prevents publishing/opening child resources.
- Parent changes cannot silently move active teams/positions/cycles across authorization scopes.
- Reparenting a branch/team is not an ordinary edit; defer unless a separately reviewed command preserves assignments/history.
- No cycles or self-referential hierarchy.
- No ordinary hard delete after any reference exists.

Existing M1 role assignments with organization/branch/team references must not become active unless the referenced real entity exists and is valid. Do not fabricate rows to satisfy old synthetic IDs. If accepted pre-production fixtures conflict, replace them only through test/local fixture setup.

## 10. Position Model

### 10.1 Fields

Implement `position` with equivalents of:

- Nonsequential ID.
- Organization ID.
- Position code unique case-insensitively within organization.
- Internal title and approved public title/default label.
- `worker_paths_allowed`: `W2_ONLY`, `CONTRACTOR_ELIGIBLE_ONLY`, or `W2_AND_CONTRACTOR_ELIGIBLE` (adapt names to the accepted catalog while preserving meaning).
- Approved employment-type option codes only if a reviewed reference catalog already exists; otherwise omit/defer rather than inventing values.
- Nullable future references for requirement/training/competency defaults only when their tables exist; do not create dangling placeholder foreign keys.
- Status: `DRAFT`, `ACTIVE`, `INACTIVE`, or `RETIRED`.
- Optimistic version and timestamps.

### 10.2 Worker-path rules

- W-2 remains the default proposed path in later candidacy/classification work.
- “Contractor eligible” means the position may support a proposed 1099 path; it does not classify any person or guarantee contractor treatment.
- No public/staff configuration action can approve an individual's 1099 classification.
- If both paths are allowed, M2.2 still begins with `UNDECIDED`/W-2-default behavior according to the workflow specification.
- Changing worker paths cannot retroactively change a published/open cycle snapshot or existing future candidacy.

### 10.3 Lifecycle

- Draft positions are editable but not public.
- Active positions may be used to create hiring cycles.
- Inactive positions accept no new cycles/openings but preserve history.
- Retired positions cannot reopen; a new/replacement position is required when meaning materially changes.
- Position code is stable after activation.
- No ordinary hard delete.

## 11. Job-Description Versions

### 11.1 Fields

Implement `job_description_version` with equivalents of:

- Nonsequential ID.
- Position ID.
- Monotonic version number unique per position.
- Public title/summary and approved description content.
- Optional safe sections such as duties, minimum qualifications, schedule summary, and candidate instructions only when required by the approved product copy.
- Content format/version.
- Status: `DRAFT`, `PUBLISHED`, `SUPERSEDED`, or `RETIRED`.
- Created/updated/published/effective timestamps.
- Creator and publisher user references.
- Optimistic version for draft editing only.

### 11.2 Content safety

- Store bounded plain text or a tightly constrained reviewed content format.
- Do not accept executable HTML, scripts, styles, iframes, arbitrary embeds, remote resources, forms, tracking pixels, or user-authored templates/code.
- Render with context-appropriate escaping and a maintained allowlist sanitizer when formatted content is approved.
- Links, if supported, use allowed protocols and safe external-link behavior.
- Public content contains no internal notes, staffing deliberations, compensation promises, candidate data, reviewer identity, scope IDs, or restricted information.
- Accessibility uses semantic headings/lists and meaningful link text.

### 11.3 Version rules

- Published versions are immutable.
- Editing published wording creates a new draft version.
- Publishing a new version supersedes the prior current version for future cycles but does not rewrite cycles already published.
- Version allocation is concurrency safe.
- Effective dates are server controlled and coherent.
- No hard deletion of published/superseded versions.

## 12. Hiring-Cycle Model

### 12.1 Fields

Add `hiring_cycle` to the data model and implement equivalents of:

- Nonsequential internal ID.
- Nonsequential public reference used in URLs; never a sequential database identifier.
- Organization ID.
- Position ID.
- Branch ID.
- Optional team ID.
- Cycle code unique case-insensitively within organization.
- Internal bounded label and optional approved public label.
- Status: `DRAFT`, `PUBLISHED`, `OPEN`, `CLOSED`, `CANCELLED`, or `ARCHIVED`.
- Application opens-at and closes-at instants, with closes-at nullable only for an explicitly open-ended approved cycle.
- Display timezone snapshot.
- Published job-description-version ID.
- Worker-path-allowed snapshot.
- Published/closed/cancelled timestamps and actor references.
- Stable close/cancel reason code where required.
- Optimistic version and common timestamps.

### 12.2 Relational integrity

- Position and branch belong to the same organization as the cycle.
- Optional team belongs to the selected branch.
- Published description belongs to the selected position.
- Composite keys/foreign keys or equally strong database constraints prevent cross-organization/branch mismatches.
- Cycle references are immutable after publication except through an explicitly reviewed supersede/cancel replacement flow.
- No ordinary hard delete after publication.

### 12.3 Lifecycle transitions

Use named commands only:

```text
create_hiring_cycle:      none -> DRAFT
publish_hiring_cycle:    DRAFT -> PUBLISHED
open_hiring_cycle:       PUBLISHED -> OPEN
close_hiring_cycle:      OPEN/PUBLISHED -> CLOSED
cancel_hiring_cycle:     DRAFT/PUBLISHED/OPEN -> CANCELLED
archive_hiring_cycle:    CLOSED/CANCELLED -> ARCHIVED
```

Rules:

- Publish requires active organization/branch/optional team/position, a published description version, valid worker-path snapshot, coherent window, authorization, expected version, and audit reason/context.
- Open requires the same prerequisites and a current window permitting acceptance.
- A cycle cannot return from closed/cancelled/archived to open.
- Reopening requires a new cycle or explicitly reviewed superseding cycle.
- Close/cancel cannot erase or change the published snapshot.
- All transitions are optimistic-concurrency safe, idempotent where retried, and atomically audited.

### 12.4 Effective public availability

Compute public availability from trusted status and time:

- `PUBLISHED` before `opens_at`: optionally visible as upcoming only if approved; not accepting.
- `OPEN` at/after inclusive `opens_at` and before exclusive `closes_at`: visible and accepting.
- At exact `closes_at`, accepting becomes false even if a background/manual close command has not yet updated the stored status.
- `CLOSED`: excluded from the normal open list; a previously known detail URL may show a generic no-longer-accepting state.
- `CANCELLED`/`ARCHIVED`/`DRAFT`: not publicly enumerable; direct URLs return the approved safe result.

Use an injected trusted clock and explicit UTC boundaries. Do not rely on browser time or delayed background jobs for whether applications are accepted.

## 13. Published Snapshot Integrity

When publishing a hiring cycle, capture immutable references/values needed to prove what the public saw:

- Job-description version ID.
- Public title/label used by the cycle.
- Worker-path eligibility snapshot.
- Branch/public location label snapshot only if branch renaming policy requires historical wording.
- Display timezone.
- Open/close window and publication time.

Later edits to organization, branch, team, position, or a newer description version must not alter the published-cycle representation. Correcting a material published error requires close/cancel/supersede with a new version/cycle and audit history, not an in-place rewrite.

Do not snapshot internal notes, authorization assignments, restricted configuration, or future requirement matrices that do not yet exist.

## 21. Transaction, Concurrency, and Idempotency

- Every configuration mutation and required audit event share the M1.6 transaction helper.
- Published-description version allocation is concurrency safe.
- Position/cycle code uniqueness is database enforced under normalized comparison.
- Competing edits use expected version; one wins and the loser receives a safe stale conflict with preserved form input.
- Publish/open/close/cancel/archive commands are idempotent for the same command key and cannot create duplicate audit events.
- Publish racing with parent inactivation, description supersession, or cycle close rechecks all invariants inside the transaction.
- At exact close boundary, application acceptance denies even when a concurrent staff action still displays the prior state.
- Cache invalidation occurs only after commit; rollback leaves prior cache valid.
- Failed audit append rolls back the configuration mutation.

## 22. Database Constraints and Indexes

At minimum enforce:

- Primary/foreign keys with non-destructive delete behavior.
- Case-insensitive normalized uniqueness for organization, branch, team, position, and cycle codes in their parent scopes.
- Closed status/worker-path values.
- Valid bounded names/codes/public references.
- Position/branch/cycle organization coherence.
- Team/branch coherence.
- Description/position coherence.
- Open/close time coherence.
- Lifecycle timestamp/status coherence.
- Unique job-description version per position.
- At most one current published description per position when that concept is retained.
- Optimistic versions with valid positive values.
- No cascade deletion of published/audited/history rows.

Indexes should support:

- Public effectively open cycles by status/time and stable ordering.
- Public reference lookup.
- Staff scoped list by organization/branch/team/status.
- Position code/title lookup within scope.
- Description versions by position/version.
- Hiring cycles by position/branch/status/window.

Do not add unrestricted text indexes over internal/public description content without a reviewed need and data-classification/search design.

## 23. Security and Privacy

- Public projections are `PUBLIC`; draft configuration and unpublished content are `INTERNAL`.
- Staff responses use exact M1.5 projections and private/no-store caching.
- Public input is bounded and cannot select arbitrary fields/sorts/includes/statuses.
- Prevent stored/reflected XSS in titles/descriptions, link schemes, error echoes, and metadata.
- Protect staff mutations with origin/CSRF, exact inputs, authorization, recent auth where required, optimistic versions, and audit.
- Organization/branch/team IDs from requests are re-resolved and hierarchy checked.
- Never expose account, role, scope-assignment, audit-integrity, database, or candidate information publicly.
- Public list/detail must not leak draft existence through status/body/cache/timing differences beyond the approved closed-position behavior.
- Structured logs contain route template, safe action/result code, correlation, duration, and opaque internal reference only.
- Use synthetic organization/position content in local/tests/demos.

## 27. Acceptance Criteria

### AC-M2.1-01 — Organization hierarchy

Organization, branch, and team entities use nonsequential IDs, normalized scoped codes, valid status/timezone/version fields, enforced parent relationships, lifecycle commands, and no unsafe deletion/reparenting.

### AC-M2.1-02 — Real scope resolution

M1 organization/branch/team scopes resolve through real hierarchy data, reject missing/inactive/wrong-type/cross-organization references, and authorize staff configuration by current scope.

### AC-M2.1-03 — Position configuration

Reusable positions enforce organization ownership, stable codes, lifecycle, W-2/contractor-eligible paths, no individual classification, and no dangling future matrix references.

### AC-M2.1-04 — Immutable descriptions

Job-description versions are bounded/safe, concurrency-versioned while draft, immutable after publication, superseded without rewriting history, and XSS safe.

### AC-M2.1-05 — Hiring-cycle aggregate

The documented cycle entity binds coherent organization/position/branch/optional team, public reference, window, description, worker-path snapshot, lifecycle, actors/reasons, and optimistic version.

### AC-M2.1-06 — Controlled lifecycle

Only named authorized commands create/edit/publish/open/close/cancel/archive; invalid, backward, parent-inactive, stale, duplicate, or incoherent transitions deny atomically.

### AC-M2.1-07 — Published snapshot

Published/open cycle content and worker-path eligibility remain unchanged by later position/description/hierarchy edits; material corrections require version/supersession/close/cancel history.

### AC-M2.1-08 — Effective availability

Public acceptance uses server time, inclusive open and exclusive close boundaries, and current parent/cycle state; it fails closed without relying on a background job or cached UI.

### AC-M2.1-09 — Authorized staff configuration

Scoped HR/manager/designated staff can perform only granted actions through accessible screens and server commands; recruiter/auditor/administrator limits and direct-request denials match policy.

### AC-M2.1-10 — Safe public list/detail

Public routes expose only effectively public immutable projections with bounded filters/stable ordering/safe cache behavior; drafts/internal fields/history/staff/candidate data never appear.

### AC-M2.1-11 — Safe handoff

Start-application handoff binds an accepting cycle to an allowlisted candidate-auth continuation and revalidates it without creating person/candidacy/application data.

### AC-M2.1-12 — Audit and transactions

Every configuration mutation and required event commits atomically with safe actor/effective-scope/action/target/status/version/reason context; failures roll back and retries do not duplicate.

### AC-M2.1-13 — Database integrity

Migration from empty and M1 succeeds with reviewed constraints/indexes/grants; cross-parent references, duplicate codes/versions, unsafe deletes, and lifecycle incoherence fail at database/application boundaries.

### AC-M2.1-14 — Accessible UI

Public and staff position/cycle screens support keyboard, screen reader, error summaries, focus, mobile/reflow, 200% zoom, loading/empty/denied/not-found/stale/success states, and clear deadline/status wording.

### AC-M2.1-15 — Security and leakage

Stored/public content is XSS safe, staff mutations enforce M1 controls, caches/projections remain separated, and no restricted/internal/candidate/auth/audit data leaks to logs, pages, bundles, errors, or artifacts.

### AC-M2.1-16 — Scope containment

Data-model/traceability updates are accurate, all M0–M1 regressions remain green, and no M2.2+ person/candidacy/application/business workflow/provider scope is added.
