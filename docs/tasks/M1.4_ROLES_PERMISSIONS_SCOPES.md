- Milestone: M1 — Identity, Access, and Audit
- Status: Ready for implementation
- Execution order: After M1.3 is implemented, committed, and accepted
- Primary outcome: The application has a deny-by-default, server-owned authorization foundation with versioned role and permission catalogs, effective-dated scoped staff assignments, current-state policy evaluation, separation-of-duties hooks, and immediate privilege revocation without yet exposing protected business routes or field serializers.

## 2. Outcome

Implement the core application authorization model on top of the accepted M1.1–M1.3 identity and authentication foundation.

Deliver:

- Application-owned role, permission, role-permission, and user-role-assignment persistence.
- Stable Release 1 role and permission codes derived from `docs/ROLE_PERMISSION_MATRIX.md`.
- Effective-dated, revocable staff assignments with approved scope types.
- Scope evaluation for assigned-record, team, branch, organization, and audit-assignment contexts through a framework-neutral resolver contract.
- A central deny-by-default authorization service returning explicit structured allow/deny decisions.
- Current-account, current-assignment, account-status, authentication-assurance, and recent-authentication evaluation.
- A separation-of-duties policy interface with mandatory safe rules and configurable dual-control hooks.
- Transactional authorization-version changes and immediate revocation behavior.
- Controlled assignment-management application commands with approver, reason, effective dates, and no production HTTP/UI exposure yet.
- Idempotent, reviewed reference-data seeding with drift detection.
- Future-audit-ready authorization events through the existing event port, without creating audit persistence.
- Unit and real-PostgreSQL integration coverage for grants, denials, scope boundaries, concurrency, revocation, and catalog integrity.
- `ADR-0003` documenting the authorization policy and scope-evaluation design.
- Traceability updates that distinguish the M1.4 policy foundation from M1.5 route/field enforcement and M1.6 audit persistence.

This task does not grant candidate-record access, expose staff administration, enforce every application route/field, create business entities, or claim authorization complete at the M1 exit gate.

## 6. Authorization Decision Model

The central service must evaluate the project rule:

```text
allowed =
  authenticated principal
  AND active account
  AND current valid role assignment or approved candidate self relationship
  AND role grants the requested permission
  AND resource is within the effective scope
  AND data sensitivity permits the requested access
  AND workflow state permits the requested action
  AND separation-of-duties rule passes
  AND required recent authentication is present
```

M1.4 implements the reusable decision engine and typed inputs. M1.5 connects it to routes, objects, fields, serializers, files, searches, and responses.

Rules:

- Deny is the default for missing or malformed context.
- Every decision is made on the server.
- UI visibility, route middleware, session claims, and role names alone never grant access.
- The service returns an explicit `ALLOW` or `DENY` result; it must not return `undefined`, truthy objects, or throw normal denials as generic errors.
- A denial includes only a closed safe reason code and safe metadata needed for telemetry/audit; it must not reveal hidden resources, other users, policy internals, or sensitive values.
- The service must identify the effective role assignment and scope used for an allow result.
- If several assignments could grant access, select deterministically and preserve only the least-privileged sufficient authorization context.
- Authorization is recalculated at command/query execution time from current server-owned facts.

## 7. Role Catalog

### 7.1 Required roles

Persist these controlled Release 1 role definitions:

| Code | Name | Principal type | Purpose |
| --- | --- | --- | --- |
| `CANDIDATE` | Candidate | Candidate | Candidate self-service only; entitlement is relationship-based, not a staff assignment |
| `RECRUITER` | Recruiter | Staff | Recruiting operations within granted record scope |
| `HR_SPECIALIST` | HR Specialist | Staff | HR application, offer, and onboarding operations within scope |
| `CLASSIFICATION_REVIEWER` | Classification Reviewer | Staff | W-2/1099 classification review within scope |
| `COMPLIANCE_REVIEWER` | Compliance Reviewer | Staff | Screening, compliance, holds, and readiness within restricted scope |
| `TRAINER_EVALUATOR` | Trainer/Evaluator | Staff | Training and competency work within scope |
| `PSA_MANAGER` | PSA Manager | Staff | Designated management and approval functions within scope |
| `SYSTEM_ADMINISTRATOR` | System Administrator | Staff | Technical configuration and access administration only |
| `AUDITOR_READ_ONLY` | Auditor/Read Only | Staff | Read/export only within an approved audit assignment |

Codes are stable identifiers. Display labels may change without changing codes.

### 7.2 Role fields

The `role` table must include equivalents of:

- Nonsequential ID.
- Stable unique code.
- Display name and bounded description.
- Principal type constraint: `CANDIDATE` or `STAFF`.
- Controlled status: `ACTIVE` or `RETIRED`.
- System-managed flag preventing ordinary rename/delete of baseline roles.
- Catalog version/source marker.
- Creation/update timestamps.

Do not add an `is_admin`, wildcard, superuser, or bypass flag.

### 7.3 Candidate role boundary

Candidate authorization is not a mutable staff role assignment.

- Candidate account type establishes eligibility for the `CANDIDATE` policy set.
- M2 will establish the actual account-to-person/candidacy ownership relationship.
- Until that relationship exists, candidate business-resource access must deny.
- Do not backfill fake candidacy, person, position, organization, scope, or assignment rows.
- Candidate account/security self-service from M1.2 remains governed by its narrow owner checks and must not be broadened by this task.
- Staff may never obtain the `CANDIDATE` role through a staff assignment.

## 8. Permission Catalog

### 8.1 Permission shape

Use stable permission keys in the form `<resource>.<action>` or the approved more-specific form already defined in `docs/ROLE_PERMISSION_MATRIX.md`, for example:

```text
application.review
interview.scorecard.submit
classification.review.decide
offer.issue
screening.result.read_restricted
screening.disposition.decide
medical_document.download
onboarding.item.approve
training.result.record
competency.evaluation.record
readiness.final_approval
audit.read.assigned
record.export.restricted
configuration.publish
role_assignment.manage
```

The `permission` table must include equivalents of:

- Nonsequential ID.
- Stable unique code.
- Resource and action components.
- Maximum sensitivity level.
- Bounded description.
- Controlled status: `ACTIVE` or `RETIRED`.
- Flags/policy references for scope, workflow-state, recent-authentication, reason, dual approval, restricted-data, and export requirements.
- Catalog version/source marker.
- Creation/update timestamps.

### 8.2 Catalog rules

- Build one reviewed TypeScript catalog manifest as the authoritative seed input; follow the accepted repository naming convention.
- Derive the initial catalog from every command/data-domain/configuration requirement in the role-permission matrix, not only the example keys.
- Use narrow permissions. View, edit, approve, download, export, configure, and role-manage are distinct.
- Never encode row IDs, routes, UI components, branch IDs, or temporary implementation details in a permission code.
- Never implement `*`, `all`, `admin`, prefix wildcard, or implicit resource inheritance.
- Retire a permission instead of deleting or reusing its code.
- Adding or widening a permission requires an explicit catalog change, tests, and review.
- Catalog rows define maximum capability only. Scope, sensitivity, state, separation, and recent-auth rules can still deny.

### 8.3 Role-permission grants

The `role_permission` join must include:

- Role ID and permission ID composite uniqueness.
- Optional closed, schema-validated condition data only when a named condition is required.
- Catalog version/source marker.
- Creation/update timestamps.

Condition data is declarative configuration, not arbitrary executable expressions. Reject unknown keys and unknown condition versions. Prefer typed columns or named policy references for security-critical conditions.

`SYSTEM_ADMINISTRATOR` must not receive routine business view, edit, review, approval, export, screening, medical, compensation, classification, or readiness permissions. `AUDITOR_READ_ONLY` must not receive create/edit/review/approve/manage permissions.

## 9. Role Assignments

### 9.1 Assignment fields

Implement `user_role_assignment` with equivalents of:

- Nonsequential ID.
- Staff `user_account_id` foreign key.
- Role ID foreign key.
- `scope_type`.
- `scope_reference_id` where required.
- `effective_from` inclusive timestamp.
- `effective_to` exclusive nullable timestamp.
- Assignment status derived from dates/revocation, or an explicit closed status if the design needs it.
- `approved_by_user_id`.
- Bounded reason code and protected bounded reason text/reference.
- `created_by_user_id` if distinct from approver.
- `revoked_at`, `revoked_by_user_id`, and bounded revocation reason.
- Optimistic-concurrency version.
- Creation/update timestamps.

### 9.2 Assignment invariants

- Only `STAFF` accounts may receive staff roles.
- The `CANDIDATE` role is never inserted into `user_role_assignment`.
- Active privileged assignments require a distinct authorized approver.
- The subject cannot create, approve, widen, extend, or revoke their own assignment through ordinary administration.
- `effective_to`, when present, is strictly after `effective_from`.
- Revoked assignments never become active again; restoration creates a new assignment.
- Retired roles/permissions cannot be used for new assignments.
- Assignments cannot grant a role outside its supported principal type.
- Overlapping equivalent assignments are rejected or canonicalized; they must not create ambiguous effective authority.
- Updating scope, role, or effective dates creates a new assignment and revokes/supersedes the old one rather than rewriting material authorization history.
- Reason and approver fields are mandatory for grants, changes, extensions, and revocations.
- Database and application constraints must agree on time-boundary semantics.

### 9.3 Assignment commands

Implement application commands for:

- Propose/create assignment.
- Approve/activate assignment when approval is separate.
- Revoke assignment.
- Replace scope or effective dates through revoke-and-create.
- List current assignments for an explicitly authorized future caller.

Commands require a typed actor/authorization context and emit future-audit-ready safe events. Do not expose production Route Handlers, Server Actions, pages, or CLI administration in M1.4. A deterministic integration-test harness is permitted. An optional local-only bootstrap harness must be disabled in production-like environments and must not create a default administrator.

## 10. Scope Model

### 10.1 Scope types

Support exactly these initial assignment scope types:

| Scope type | Meaning | Reference requirement |
| --- | --- | --- |
| `ASSIGNED_RECORDS` | Only records explicitly assigned through a later business relationship | Required when a real assignment-set reference exists; no broad fallback |
| `TEAM` | Records belonging to one resolved team | Team reference required |
| `BRANCH` | Records belonging to one resolved branch | Branch reference required |
| `ORGANIZATION` | Records in one resolved organization, still limited by permission/sensitivity | Organization reference required |
| `AUDIT_ASSIGNMENT` | Only records, dates, and categories in an approved audit assignment | Active audit-assignment reference required |

Possession of a role never implies organization-wide scope. `SYSTEM_ADMINISTRATOR` organization scope applies only to technical configuration/access-administration permissions; it does not unlock business records.

### 10.2 Deferred business entities

Organization, branch, team, person, candidacy, and audit-assignment business records are not created in M1.4.

Implement a `ScopeResourceResolver` port that validates and resolves a scope reference into a typed, server-owned scope descriptor. The contract must:

- Accept a scope type, opaque nonsequential reference ID, evaluation time, and safe correlation context.
- Return only typed membership/ancestry/bounds needed for authorization.
- Distinguish active, inactive/expired, missing, and type-mismatch outcomes without exposing them to unauthorized callers.
- Reject cross-organization parentage and cycles.
- Fail closed when the backing module/entity is not implemented or unavailable.
- Never trust organization/branch/team/assignment membership supplied by the browser, session, URL, or request body.

Use deterministic synthetic resolvers for M1.4 unit/integration tests. Later milestones will provide real adapters and foreign-key/consistency integration. Do not persist a production assignment whose scope reference cannot be resolved as active through an approved adapter.

Document the intentionally deferred cross-module referential-integrity strategy in `ADR-0003`; do not silently accept dangling IDs.

### 10.3 Scope containment

Define typed containment rules, not string comparison:

- Organization scope may contain child branches/teams/records only when the resolver proves the ancestry.
- Branch scope may contain child teams/records only in that branch.
- Team scope contains only records resolved to that team.
- Assigned-record scope requires an explicit current assignment relationship for the actor/assignment.
- Audit scope requires active assignment, allowed data categories, record filters, and inclusive/exclusive date bounds.
- A role assignment from one organization never combines with a scope/resource from another organization.
- Multiple narrow scopes union only for the same permission and only after each independently passes.
- A narrow specialist permission is not broadened by a general role with a wider scope.
- Missing hierarchy, membership, category, or time context denies.

## 11. Central Authorization Service

### 11.1 Typed request

Define a framework-neutral `AuthorizationRequest` equivalent containing:

- Authenticated principal/account ID and account type from the server resolver.
- Requested permission code.
- Resource descriptor with opaque resource ID, resource type, organization/branch/team relationships when resolved, owner/assignee relationships, and sensitivity classification.
- Operation kind: read, create, edit, review, approve, download, export, configure, or administer.
- Workflow state/facts required by the named policy.
- Separation-of-duties facts such as proposer, creator, submitter, subject, prior approver, and required approval count.
- Server-owned authentication-assurance/recent-authentication evidence and named policy.
- Evaluation timestamp from an injected clock.
- Safe purpose/reason code when required.
- Correlation ID.

Do not accept raw database rows, arbitrary JSON, client claims, or free-form policy expressions as authorization context.

### 11.2 Decision result

Return an `AuthorizationDecision` equivalent:

```text
ALLOW:
  decision
  permissionCode
  effectiveRoleCode
  effectiveAssignmentId (staff only)
  effectiveScopeType/reference (safe opaque values)
  policyVersion
  reasonCode = ALLOWED

DENY:
  decision
  permissionCode
  policyVersion
  safe reasonCode
```

Safe denial codes may distinguish internal handling such as unauthenticated, inactive account, permission missing, assignment inactive, scope mismatch, sensitivity denied, workflow state denied, separation conflict, recent authentication required, invalid context, or policy unavailable. External adapters in M1.5 decide whether the caller receives `401`, `403`, `404`, a redacted response, or a step-up prompt.

### 11.3 Evaluation ordering

Evaluate cheap identity/account validity before loading sensitive resource facts, then permission/assignment, scope, sensitivity, workflow, separation, and assurance. Do not return early in a way that leaks resource existence through response shape, text, or materially distinguishable external behavior.

Every allow decision must be reproducible from a named policy/catalog version and current server-owned facts.

## 12. Sensitivity and Workflow Policy Inputs

M1.4 defines the policy vocabulary required by the authorization formula without implementing M1.5 serializers or later workflow aggregates.

Use the approved classifications:

- `PUBLIC`
- `INTERNAL`
- `CONFIDENTIAL_PERSONNEL`
- `RESTRICTED_IDENTITY_FINANCIAL`
- `RESTRICTED_SCREENING_MEDICAL`
- `SECURITY_AUDIT_RESTRICTED`

Rules:

- A permission's maximum sensitivity is an upper bound, not an automatic grant.
- Restricted view/download/export permissions are separate.
- Full-value access is separate from masked-value access where the matrix requires it.
- Export is denied unless a distinct export permission and required policy facts are present.
- Workflow conditions use closed named policies and closed state values supplied by the owning domain.
- Unknown sensitivity, state, policy version, or unsupported transition denies.
- M1.4 tests the engine using synthetic resource/workflow facts; it must not create M2+ aggregates.

## 13. Separation of Duties

### 13.1 Policy interface

Implement a framework-neutral `SeparationOfDutiesPolicy` interface that receives a named policy, actor ID, resource subject/participants, prior actions/approvals, configured approval requirements, evaluation time, and safe context.

It returns explicit pass/deny with a safe reason code. Missing required facts deny. Rules compare immutable actor IDs, not names or role names.

### 13.2 Mandatory rules

Provide named policy functions/tests for the matrix rules, including:

1. No actor approves their own worker-classification proposal.
2. No candidate approves/verifies their own screening, onboarding, training, competency, or readiness result.
3. The restricted-result entrant cannot make final disposition when dual review applies.
4. A signed evaluation is not edited in place; correction requires a new version/amendment.
5. A system administrator cannot perform business approvals.
6. An actor cannot approve their own compensation/offer change when dual approval applies.
7. A candidate or recruiter-only actor cannot approve final readiness.
8. A staff actor cannot access or approve their own candidacy/worker file.
9. An actor cannot modify audit records documenting that actor.
10. Break-glass authority cannot perform ordinary workflow approvals.

Provide configurable two-person policy hooks for classification, high-risk screening disposition, compensation-threshold offer approval, manual compliance waiver, final readiness, restricted export, and retention/legal-hold actions. M1.4 tests policy behavior with synthetic facts; it does not implement those workflows.

### 13.3 Role administration separation

- The assignment subject cannot approve their own access.
- The requester/creator and approver must be different when dual control is required.
- A user cannot grant permissions beyond the approver's authorized administrative scope.
- `SYSTEM_ADMINISTRATOR` implements only a previously approved access change; it does not self-approve policy.
- Bootstrap/local harnesses cannot be used as production approvers.

## 14. Recent Authentication and Assurance

Consume the M1.3 server-owned assurance primitive.

- Permission metadata may require a named recent-authentication policy.
- Privileged role/scope assignment changes require current staff MFA and the approved recent-auth policy.
- Restricted-data, high-risk approval, export, and break-glass permission definitions carry the appropriate named requirement even though their routes arrive later.
- Backup-code assurance must not satisfy the highest-strength policy unless explicitly approved by M1.3 policy.
- Client-supplied time, method, factor, purpose, or freshness is ignored.
- Missing, expired, wrong-session, wrong-account, insufficient-strength, or wrong-purpose assurance denies.

Do not duplicate M1.3 authentication logic inside the authorization service.

## 15. Immediate Change and Revocation Behavior

### 15.1 Current-state evaluation

- Never place authoritative roles, permissions, or scopes only in session/JWT/client state.
- Resolve current active assignments and current catalog grants for every sensitive command/query.
- A bounded cache is allowed only if it has proven transactional invalidation and cannot extend revoked access; the initial implementation should prefer direct current-state reads.
- Time-bound assignments expire at the exact exclusive `effective_to` boundary using the injected server clock.

### 15.2 Authorization version

Add an application-owned monotonic authorization version/epoch to the account or an approved one-to-one authorization-subject record.

In the same transaction as assignment/catalog-affecting subject changes:

1. Write the assignment change.
2. Increment the subject authorization version.
3. Emit the safe future-audit event through the existing port.
4. Invalidate/revoke affected staff sessions using the accepted M1.1/M1.3 mechanism when policy requires.

The current principal resolver must reject stale authorization/session state. A revoked, expired, or superseded assignment must stop granting access immediately, without relying on logout, token expiry, browser refresh, or UI state.

Privilege expansion must not silently reuse an insufficient old assurance state. Require a fresh authenticated session/step-up according to policy before high-risk use.

### 15.3 Concurrency

- Use optimistic concurrency and/or row locking for competing assignment changes.
- Two concurrent approvals cannot activate conflicting/duplicate assignments.
- Revoke racing with authorize must produce a defined fail-closed result; authorization must not commit a sensitive command based on a privilege revoked before that command's protected transaction boundary.
- Document transaction isolation and the application command pattern required by later modules.

## 16. Reference-Data Seeding and Drift

Implement a reviewed idempotent catalog migration/seed process:

- Stable IDs or deterministic code-based lookup.
- Explicit catalog version.
- Insert/update only expected controlled fields.
- Never delete or silently repurpose a role/permission code.
- Fail CI when the TypeScript catalog, migration/seed output, matrix traceability, and database snapshot drift.
- Re-running on the same database produces no unintended changes.
- Seeding creates no users, assignments, organizations, branches, teams, audit assignments, sessions, or default administrator.
- Production changes require reviewed migration/deployment behavior, not application startup auto-seeding with elevated schema privileges.

If the full matrix contains an ambiguous or conflicting grant, use the more restrictive interpretation and record the open decision. Do not widen a role to make tests easier.

## 17. Events, Logging, and Privacy

M1.6 owns append-only audit persistence. M1.4 must emit typed future-audit-ready events for:

- Assignment proposed/created.
- Assignment approved/activated.
- Assignment revoked/superseded/expired where an event is produced.
- Catalog version applied.
- High-risk authorization denied.
- Authorization policy unavailable/invalid.
- Subject authorization version changed.

Events may include only safe values such as opaque actor/subject/assignment references, effective role/scope codes, action, reason code, policy/catalog version, outcome, time, and correlation ID.

Never log or place in events:

- Passwords, MFA material, sessions, cookies, tokens, headers, request/response bodies, or auth secrets.
- Full email, candidate/business content, sensitive field values, medical/screening details, free-text reasons, IP addresses, or user agents.
- Raw database errors, SQL with bound sensitive values, or full policy context.

Routine authorization denials use bounded safe telemetry. High-risk denials are prepared for M1.6 audit integration without creating an alternate audit table.

## 21. Acceptance Criteria

### AC-M1.4-01 — Controlled role catalog
