# Work Item M1.5 — Route and Field Authorization

## 1. Status

- Milestone: M1 — Identity, Access, and Audit
- Status: Ready for implementation
- Execution order: After M1.4 is implemented, committed, and accepted
- Primary outcome: Every current protected server entry point uses the M1.4 authorization service for current principal, object, action, and field decisions; protected responses are explicitly projected and safely denied without exposing resource existence or restricted data.

## 2. Outcome

Connect the accepted M1.4 authorization foundation to the application delivery and serialization boundaries.

Deliver:

- An authoritative inventory/classification of every current page, Route Handler, Server Action, Better Auth/application endpoint, and other server entry point.
- Candidate/staff route-group guards used only for navigation convenience and early rejection.
- Mandatory application-service authorization for every protected read and mutation.
- Object-level authorization patterns that prevent insecure direct object reference and cross-record access.
- Action/function authorization that rejects hidden or directly invoked commands.
- Explicit field-level response projections with include, mask, status-only, omit, and whole-resource-deny behavior.
- Input allowlists that prevent mass assignment of server-owned or unauthorized fields.
- Scoped-query/search contracts that constrain results before materialization and recheck returned objects.
- Safe denial, not-found, step-up, validation, conflict, and system-error mapping.
- Protected-response cache controls and redirect rules.
- Reusable authorization gates for future files, downloads, reports, exports, jobs, and provider callbacks without implementing those features.
- Static architecture checks preventing protected delivery code from bypassing application services or returning persistence models directly.
- Unit, component, real-PostgreSQL integration, and representative Playwright coverage for the current candidate/staff security surfaces.
- Future-audit-ready allow/deny context passed through the existing event port, without creating audit persistence.
- Traceability updates that distinguish M1.5 enforcement from M1.6 immutable audit and M1.7 full authorization-matrix coverage.

This is security plumbing with minimal safe denied/not-found/step-up UI states. It does not build the candidate portal, staff dashboard, candidate workspace, business records, or production access-administration UI.

## 6. Trust and Enforcement Boundaries

Authorization must be enforced at every server boundary that can read, mutate, or disclose protected state:

- Next.js Server Components.
- Route Handlers.
- Server Actions.
- Better Auth hooks/endpoints extended by application behavior.
- Application command/query handlers.
- File preview/download handlers.
- Search/list/report/export queries.
- Background jobs.
- Provider callbacks/webhooks.
- Administrative/local harnesses.

For M1.5, enforce all currently implemented boundaries and provide typed reusable adapters/contracts for later boundaries. Do not create fake business endpoints solely to demonstrate authorization.

Browser state is untrusted. Never authorize from:

- Hidden buttons or navigation.
- Client components or React context.
- URL/path/query/body claims about role, scope, ownership, sensitivity, or workflow state.
- Session-cached role/scope claims without current server revalidation.
- Referer, prior page, UI flow, feature flag, or a successful earlier request.
- Opaque ID possession.

## 7. Route Inventory and Classification

### 7.1 Route manifest

Create a reviewed route/entry-point authorization manifest covering every current server-reachable entry point. Each entry must declare:

- Stable route/entry identifier.
- Method or invocation kind.
- Audience: `PUBLIC`, `CANDIDATE`, `STAFF`, `SERVICE`, or explicitly mixed.
- Authentication requirement.
- Account-type/status requirement.
- Required permission or narrow self-service policy.
- Resource/ownership resolver when applicable.
- Field projection/output contract.
- CSRF/origin and rate-limit policy for mutations/abuse-sensitive reads.
- Cache policy.
- External denial behavior.
- Recent-authentication policy when required.
- Whether an allow or deny requires future M1.6 audit evidence.

The manifest is reviewed policy metadata, not an executable user-authored language. Unknown/missing classifications fail CI or fail closed.

### 7.2 Current route classes

Inventory actual accepted routes rather than assuming filenames. At minimum classify equivalents of:

- Public candidate registration, verification, sign-in, and recovery/reset.
- Authenticated candidate security/session routes.
- Public staff invitation activation, first-factor sign-in, MFA challenge, and controlled recovery entry.
- Authenticated staff security, session, MFA-management, and reauthentication routes.
- Better Auth/application auth endpoints.
- Health/readiness endpoints, ensuring they disclose no protected data.
- Local/test-only invitation, recovery, and authorization harnesses.

Production invitation issuance, staff recovery completion, role assignment, and privileged administration remain unavailable until the approved M1.6 audit boundary exists.

### 7.3 Drift prevention

Add an architecture/static test that enumerates current route files and fails when:

- A new server entry point is absent from the manifest.
- A protected entry lacks an application authorization call/output contract.
- A state-changing endpoint uses an unsafe method or misses origin/CSRF policy.
- Delivery code directly imports a persistence repository/Drizzle schema where the accepted architecture forbids it.
- A local/test-only handler is reachable in production-like configuration.

Allow explicit narrowly reviewed exclusions for static assets and framework-required internal files only.

## 8. Route Guards Are Convenience Only

Implement candidate/staff route-group guards for early navigation behavior:

- Candidate-only pages require an active verified `CANDIDATE` principal.
- Staff-only pages require an active verified, MFA-complete `STAFF` principal.
- Candidate principals cannot enter staff route groups.
- Staff/service principals cannot enter candidate route groups unless a separately approved route is explicitly mixed.
- Service accounts cannot use interactive pages.
- Locked, disabled, closed, invited/incomplete, expired-session, or stale-authorization principals are rejected.
- Redirect destinations are selected from server-owned allowlists only.

These guards may redirect unauthenticated users or render a safe shell, but they do not authorize an object, command, field, file, search, or export. Every page/query/action/handler must call the same application authorization boundary again.

Do not rely on Next.js middleware as the sole control. Middleware may optimize coarse routing only and must not fetch sensitive records or become the authoritative authorization service.

## 9. Application-Service Authorization

### 9.1 Required call sequence

Every protected application query/command must follow the equivalent sequence:

1. Resolve the current server-owned principal/session.
2. Validate bounded untrusted input.
3. Resolve only the minimum safe authorization envelope for the target resource.
4. Load current role/permission/scope/account/assurance facts.
5. Call the M1.4 authorization service for the requested action and relevant fields.
6. If denied, stop before protected data is loaded or mutated and return a typed denial.
7. If allowed, load only the authorized projection or aggregate data needed.
8. Recheck object/state/version at the command transaction boundary where races matter.
9. Apply the command/query.
10. Serialize through the explicit authorized response contract.
11. Pass safe decision/effective-role/scope/correlation context to the future-audit event port.

Do not copy authorization conditions into page components or handlers. Thin delivery adapters call shared application services.

### 9.2 Reads and mutations

- Reads require authorization; they are not safer merely because they do not mutate.
- Mutations require action/function permission in addition to object and field access.
- A role that may view a resource does not automatically edit, approve, download, export, or administer it.
- A hidden/disabled control does not prevent direct command invocation.
- Recalculate authorization and workflow facts immediately before a protected mutation commits.
- Expected versions and idempotency keys remain required where the owning command specifies them.

## 10. Object-Level Authorization

### 10.1 Authorization envelope

Define a minimal typed resource authorization envelope containing only facts needed by M1.4, such as:

- Opaque resource ID and resource type.
- Owner/account relationship.
- Organization, branch, team, assigned-record, or audit-assignment references.
- Sensitivity classification.
- Workflow state/version.
- Relevant creator/proposer/subject/approver identifiers for separation rules.

Load the envelope through a dedicated repository/query that does not select restricted payload fields.

### 10.2 Query pattern

Use one of these reviewed patterns:

- Apply current scope/ownership predicates in the database query, then recheck the returned object's authorization envelope.
- Load a minimal nonsensitive envelope by opaque ID, authorize it, then load an explicit authorized projection.

Avoid loading a full restricted ORM entity and filtering it afterward. Unauthorized data must not enter logs, caches, error objects, component props, traces, or serializers.

### 10.3 Existence protection

- Candidate cross-record access must not confirm that another candidate/resource exists.
- Staff wrong-scope access to nonpublic records normally maps to the same external not-found response as an unknown ID.
- Invalid opaque identifier format, nonexistent identifier, wrong resource type, unauthorized identifier, and soft-hidden resource use equivalent external behavior where enumeration risk exists.
- Internal safe reason codes may differ for telemetry/future audit, but external body, headers, timing budget, and navigation must not materially disclose existence.
- Do not expose owner names, role names, branch/team, workflow state, deletion state, or sensitivity in a denial.

## 11. Action and Function Authorization

- Map each command/query to one stable permission or narrow candidate self-service policy.
- Never derive permission names from request input.
- Server decides the resource, action, applicable policy version, and required assurance.
- Reject unsupported methods and command names.
- State-changing behavior is unavailable through `GET`, link preview, image load, or prefetch.
- Server Actions remain thin and must not be exportable generic mutation helpers.
- Better Auth endpoints are restricted so generic profile/user update functions cannot change account type/status, roles, scopes, MFA policy, verification ownership, authorization version, or other server-owned fields.
- No generic `update(resource, fields)` or arbitrary filter/sort/select API is exposed.

## 12. Field-Level Authorization

### 12.1 Field policy vocabulary

Implement a typed field policy producing one of:

- `INCLUDE` — return the approved value.
- `MASK` — return a defined nonreversible masked representation.
- `STATUS_ONLY` — return only an approved state/summary, never the underlying value.
- `OMIT` — remove the field from the response contract.
- `DENY_RESOURCE` — deny the entire representation/action because safely omitting the field would change meaning or violate policy.

The outcome depends on permission, scope, audience, sensitivity, purpose, workflow state, separation rules, and recent authentication. Unknown field metadata denies/omits according to the explicit resource contract; it never defaults to include.

### 12.2 Explicit response projections

- Define purpose-specific response/view-model schemas for list, detail, edit, review, status, and security/session responses.
- Map values field by field. Never spread an ORM/auth/provider object into a response or React props.
- Runtime-validate the final response against an exact schema that strips or rejects unknown keys according to the accepted convention.
- Prefer repository projections that never select unneeded restricted columns.
- Do not use a single broad DTO with nullable sensitive fields for every audience.
- Candidate and staff representations are different contracts.
- List/search results are more minimal than detail views.
- Masked values are server generated and cannot be reversed or used as update input.
- `null`, empty string, omission, and masked values must not accidentally reveal whether a restricted value exists.

### 12.3 Never-return fields

Ordinary application responses must never contain:

- Password hashes or credential-provider secrets.
- Raw session tokens/cookies, verification/reset/invitation capabilities, MFA seeds/codes, backup codes, or recovery material.
- Encryption keys, blind-index secrets, storage keys, provider credentials, or signed-provider internals.
- Internal authorization conditions, full policy inputs, raw assignment approval reason text, or security controls useful for bypass.
- Raw database errors, SQL, stack traces, environment values, or server paths.

No role, including administrator, converts a never-return field into an includable field.

### 12.4 Current M1 projections

Apply explicit projections to current candidate/staff account and security/session responses. Return only approved display data and masked session summaries. Preserve M1.2/M1.3 one-time secret display behavior only at the exact controlled creation/enrollment moment; M1.5 must not introduce a way to retrieve those secrets later.

## 13. Input Field and Mass-Assignment Protection

- Define exact input schemas per command/form.
- Reject or strip unknown fields according to a documented consistent policy; security-sensitive inputs should reject.
- Assign account type/status, verification state, role, permission, scope, ownership, approver, authorization version, sensitivity, workflow state, and audit fields only on the server.
- Never pass a parsed request object directly into an ORM insert/update.
- Never allow client-controlled `select`, `include`, field list, permission code, policy name/version, or projection name.
- PATCH/partial update handlers must use an explicit per-command allowlist and distinguish missing from intentional null.
- Hidden/read-only HTML fields remain untrusted.
- Prototype-pollution keys and nested unexpected structures are rejected by bounded validation.

## 14. Scoped Lists and Search

Create reusable query contracts for future list/search/report use without building the staff dashboard or business search.

- Authorization produces a typed query-scope constraint; repositories apply it in SQL before pagination/result materialization.
- Candidate self-service queries always bind ownership from the server principal.
- Staff queries use current effective assignments/scopes, not a browser-selected unrestricted scope.
- A scope selector may narrow current authority later; it can never widen it.
- Pagination, page size, sort keys, filters, and search length are allowlisted/bounded.
- General search never selects or indexes restricted identity/financial/screening/medical contents.
- Result rows use minimal search/list projections and are individually rechecked where policy requires.
- Counts, facets, autocomplete, empty results, ordering, and timing must not reveal out-of-scope records.
- Unknown filters/fields/sorts reject rather than falling back to a broad query.
- `SYSTEM_ADMINISTRATOR` has no implicit business search authority.
- Auditor queries require current audit-assignment record/date/category bounds.

Use synthetic repositories/resources for M1.5 contract tests. Do not create M2 business tables or a production candidate search endpoint.

## 15. Files and Downloads

Implement or complete a reusable `AuthorizedDocumentAccess`/download-gate contract for later document milestones. If current M1 auth flows expose a downloadable artifact, apply it now.

- Authenticate and authorize every metadata view, preview, download, print, and export separately.
- Validate document category, parent-record scope, audience, scan/availability state, sensitivity, purpose, and recent authentication where required.
- Storage key, object URL, filename, and capability possession never authorize access.
- Do not place private files beneath a public/static web directory.
- Prefer an authorized streamed response or a short-lived, single-purpose signed URL issued only after current authorization.
- Use safe `Content-Type`, `Content-Disposition`, filename handling, `nosniff`, cache controls, and referrer policy.
- Never redirect an unauthorized caller to a storage/provider URL.
- View permission does not imply download/print/export permission.
- Restricted access passes safe context to the future M1.6 audit port.

Do not implement business upload/document persistence, object storage, malware scanning, or actual restricted documents in M1.5.

## 16. Background Jobs, Services, and Provider Callbacks

Define the enforcement contract for noninteractive callers:

- No end-user role impersonation through a job payload.
- Service principals are noninteractive, narrowly permissioned, purpose bound, and explicitly scoped.
- Jobs reload current authority/configuration before protected work and fail closed after revocation.
- Provider callbacks authenticate the provider independently and still authorize the affected application operation/resource.
- IDs, roles, scopes, field selections, or callback events supplied by a queue/provider remain untrusted.
- Job/provider responses and logs use the same field projections/redaction rules.

Only apply this to currently implemented jobs/callbacks. Otherwise deliver typed ports/test fixtures, not production provider endpoints.

## 17. Denial and Error Mapping

### 17.1 Typed internal outcomes

Map internal outcomes through one delivery adapter. Normal authorization denials are typed control flow, not uncaught exceptions.

| Internal outcome | Browser page behavior | JSON/action behavior |
| --- | --- | --- |
| Unauthenticated/expired session | Allowlisted sign-in redirect preserving only a safe destination key | `401` generic authentication required |
| Wrong account type or hidden resource | Safe not-found/return state | `404` generic not found |
| Authenticated action denied with existence already safely known | Safe authorization-denied state | `403` generic forbidden |
| Recent authentication required | Allowlisted reauthentication flow | `403` with stable safe `REAUTHENTICATION_REQUIRED` code |
| Invalid bounded input | Accessible validation state | `400` or `422` per accepted convention |
| Stale version/workflow conflict | Preserve safe user input and request reload/review | `409` stable safe conflict code |
| Rate limited | Generic retry guidance without account disclosure | `429` with bounded policy |
| Unexpected/system failure | Generic state with correlation ID | Generic `5xx` with correlation ID |

Do not expose internal M1.4 denial reason, assignment ID, effective scope, policy facts, SQL/auth errors, or resource state to the browser unless a specific safe value is required by the approved UI contract.

### 17.2 Redirect safety

- Accept only server-defined destination keys or strict same-origin allowlisted paths.
- Reject scheme-relative, absolute external, encoded, nested, backslash, control-character, and normalization-bypass destinations.
- Do not include tokens, emails, resource existence, permission/scope, or denial reason in redirect URLs.
- After reauthentication, re-run the entire authorization decision; do not resume from a cached allow result.

## 18. Cache, Rendering, and Client-Bundle Safety

- Authenticated, personalized, security, and restricted responses use reviewed `Cache-Control: private, no-store` behavior where appropriate.
- Prevent shared/CDN caching of protected responses and redirects containing user state.
- Use appropriate `Vary` behavior without relying on it as the sole privacy control.
- Protected Server Components/queries must not be statically rendered with user data.
- Do not cache an authorization allow result beyond its valid current role/account/session/assurance state.
- Client-side caches are cleared/invalidated on sign-out, account restriction, role change, and session loss where applicable.
- Never embed secret/restricted fields, authorization catalogs, hidden rows, or broad unfiltered datasets in HTML, React Server Component payloads, hydration data, source maps, or client bundles.
- Prefetch must not trigger mutations or retrieve unauthorized/restricted data.
- Error boundaries and loading states must not render stale data from another principal/resource.

## 19. Minimal Safe UI States

M1.5 may add only shared security states/components needed by existing routes:

- Authentication required.
- Authorization denied.
- Resource not found.
- Reauthentication required.
- Session/account no longer eligible.
- Generic system error with correlation/reference ID.

Requirements:

- Accessible headings, focus management, status/error announcements, keyboard operation, and 200% zoom/mobile behavior.
- No disclosure of resource existence, owner, candidate, role, scope, branch/team, sensitivity, or internal policy.
- Safe return/sign-in/reauthenticate actions use allowlisted destinations.
- Do not add the candidate portal shell, staff dashboard/navigation, candidate workspace, queues, business search, or business forms.

## 20. Static and Architecture Enforcement

Add automated checks, ESLint boundaries, and/or focused source scans that fail for prohibited patterns where practical:

- Direct Drizzle/schema/repository imports from protected page/route/client layers.
- ORM/auth-library objects returned directly from handlers or passed to Client Components.
- Object spread of persistence/provider records into response DTOs.
- Client imports of server authorization, repository, secret, or restricted-field modules.
- Role-name checks or `isAdmin` shortcuts in pages/components.
- Permission decisions in middleware/client components.
- Unclassified server entry points.
- Production imports of local/test authorization adapters.
- Unsafe redirect construction.
- State-changing `GET` handlers.
- Missing protected cache headers or exact output schemas.

Checks complement behavioral tests; they must not use fragile broad patterns that block safe code without a documented suppression path. Every suppression is narrow, reviewed, and justified.

## 21. Events, Logging, and M1.6 Boundary

M1.6 owns append-only audit persistence and atomic audit storage. M1.5 must:

- Propagate correlation ID, actor ID, effective role/scope, permission, resource reference, policy version, outcome, and safe denial/action code from authorized application calls.
- Emit future-audit-ready events for restricted reads/downloads and configured high-risk denials through the accepted event port.
- Preserve safe outcome context across page, Route Handler, Server Action, file, search, job, and provider adapters.
- Keep routine low-risk denial telemetry bounded and free of personal data.
- Avoid duplicate events when both route guard and application authorization reject the same request.
- Never create an audit table, mutable access-log substitute, or claim atomic business audit completion.

Never log request/response bodies, full URL query strings containing user input, full email, passwords, tokens, cookies, headers, session IDs, MFA/recovery data, restricted values, free-text reasons, IP addresses, user agents, database errors, or full authorization context.

## 24. Acceptance Criteria

### AC-M1.5-01 — Complete current route inventory

Every current server entry point is classified by audience, authentication, permission/self policy, projection, cache, CSRF/origin, denial, assurance, and future-audit behavior; unclassified additions fail CI.

### AC-M1.5-02 — Guards are nonauthoritative

Candidate/staff guards reject ineligible navigation safely, but every protected query/command independently calls the application authorization boundary.

### AC-M1.5-03 — Candidate/staff isolation

Candidate, staff, and service principals cannot cross interactive route groups or invoke the other audience's protected actions; inactive/incomplete/stale principals are rejected.

### AC-M1.5-04 — Object authorization

Protected resources are scope/ownership filtered and rechecked using minimal authorization envelopes; changed/guessed IDs cannot expose another resource or its existence.

### AC-M1.5-05 — Action authorization

Direct requests to hidden/unsupported commands deny; view authority never implies edit/approve/download/export/admin authority, and state changes are unavailable through `GET`/prefetch.

### AC-M1.5-06 — Field-safe responses

Purpose/audience-specific exact projections apply include/mask/status/omit/deny rules, never serialize persistence/auth objects, and never return designated secret fields.

### AC-M1.5-07 — Mass-assignment protection

Exact input schemas reject attempts to set server-owned identity, status, role, scope, ownership, approval, sensitivity, workflow, authorization-version, or projection fields.

### AC-M1.5-08 — Scoped query contracts

List/search constraints apply current scope before materialization, use bounded allowlisted inputs, exclude restricted fields, and prevent counts/timing/facets from exposing out-of-scope records.

### AC-M1.5-09 — File-access contract

Reusable file/preview/download gates require current object/category/action/field/scan/assurance authorization and never treat storage keys/URLs as authority; no business file feature is added.

### AC-M1.5-10 — Safe denials and redirects

One typed mapper produces consistent safe authentication, hidden/not-found, forbidden, reauth, validation, conflict, rate-limit, and system outcomes with no resource/policy disclosure or open redirect.

### AC-M1.5-11 — Cache and bundle safety

Protected responses cannot enter shared/static caches or leak through RSC/hydration/client bundles, source maps, loading/error states, prefetch, or stale client state.

### AC-M1.5-12 — Current M1 surfaces secured
