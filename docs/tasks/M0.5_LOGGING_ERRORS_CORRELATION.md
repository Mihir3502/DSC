# Work Item M0.5 — Logging, Errors, and Correlation

## 1. Status

- Milestone: M0 — Repository Foundation
- Status: Ready for implementation
- Execution order: After M0.4 is implemented, committed, and accepted
- Primary outcome: Every web request has a safe correlation reference, operational logs use an allowlisted structured schema with pre-serialization redaction, and internal failures map to stable public errors without leaking sensitive details.

## 2. Outcome

Establish the application-wide operational logging and error-handling foundation without implementing hiring-domain behavior.

Deliver:

- A Pino-compatible structured logger behind an application-owned interface.
- Explicit allowlisted operational-log context and centrally configured redaction.
- Request correlation-ID creation, validation, propagation, and response exposure.
- A small typed error taxonomy separating domain, application, infrastructure, and public errors.
- Central mapping from trusted internal errors to stable public error responses.
- Safe global error UI with a request reference that support staff can use.
- Safe route-handler behavior demonstrating the foundation without adding a business API.
- Unit, component, route-level, and browser tests proving sensitive canaries never appear in logs or user-visible errors.

This task creates infrastructure primitives only. It must not add authentication, authorization, audit-domain records, hiring workflows, external telemetry, metrics exporters, tracing backends, error-reporting SaaS, or production infrastructure.

## 6. Design Rules

### 6.1 Separation of concerns

Keep these concepts distinct:

| Concern | Purpose | Persistence |
|---|---|---|
| Operational log | Diagnose runtime behavior with safe context | Log destination only |
| Correlation ID | Connect one request's safe logs and public reference | Request lifetime; may appear in logs and response |
| Domain/application error | Trusted internal control-flow or failure classification | Not automatically persisted |
| Public error | Minimal stable client-facing representation | Response/UI only |
| Business audit record | Immutable evidence of sensitive business actions | Not implemented in M0.5; belongs to M1+ |

Operational logging must never substitute for the future immutable audit trail.

### 6.2 Dependency direction

- Shared error definitions must not import Next.js, React, Pino, Drizzle, HTTP request types, or provider SDKs.
- The logger adapter may depend on Pino, but callers depend on the application-owned logger contract.
- Delivery adapters map internal errors to HTTP/UI representations.
- Domain code may create typed domain errors but must not log directly.
- UI components receive safe presentation models only.

### 6.3 Fail-safe behavior

- Unknown errors map to one generic internal public error.
- Expected errors may expose only reviewed, non-sensitive user guidance.
- Logging failure must not disclose internal data or change an otherwise safe public response.
- Error mapping must not infer authorization from string matching or raw database/provider messages.
- Stack traces may be emitted only to an approved local diagnostic sink after redaction; they are never returned to users.

## 7. In Scope

### 7.1 Minimal dependencies

Add only the stable logging dependency or dependencies actually required by the chosen design. Prefer `pino` directly. A development formatter is optional and must be development-only, locally enabled, and never required for tests or production JSON output.

Do not add an external transport, log collector, telemetry SDK, tracing SDK, analytics SDK, or hosted error reporter.

### 7.2 Application-owned logger contract

Create a small typed interface under `src/shared/logging/` with supported levels such as `debug`, `info`, `warn`, and `error`.

The contract must:

- Accept a message key or short safe message plus a typed allowlisted context object.
- Support child/bound context without accepting arbitrary request objects.
- Prevent passing an `Error`, request, response, headers collection, ORM row, or unknown provider payload as unrestricted structured context.
- Use stable event/result/error codes for machine filtering.
- Be straightforward to replace or wrap later without changing business modules.

Avoid a generic `Record<string, unknown>` public logging API. If a low-level escape hatch is unavoidable, keep it private to the logging adapter and test its redaction behavior.

### 7.3 Allowlisted operational context

The initial schema may include only safe fields such as:

- `service`
- `environment`
- `module`
- `action`
- `eventCode`
- `resultCode`
- `errorCode`
- `correlationId`
- `routeTemplate`
- `method`
- `statusCode`
- `durationMs`
- `actorRef` as a non-secret opaque internal reference
- `recordRef` as a non-secret opaque internal reference

Do not log raw URLs or query strings by default. Route information must use a static route template or reviewed low-cardinality label.

Never log request or response bodies by default. Never automatically serialize cookies, authorization headers, all headers, query parameters, form data, multipart content, server actions, database records, environment variables, or provider payloads.

### 7.4 Central redaction

Configure redaction before serialization for known sensitive paths and defensive variants, including at minimum:

- Password, passcode, credential, secret, token, API-key, cookie, session, authorization, and MFA fields.
- SSN/TIN, bank account, routing number, payment, identity-document, and date-of-birth fields.
- Full addresses and personal application answers.
- Medical, TB, drug-screen, background-report, and screening-detail fields.
- Document contents, signed URLs, encryption keys, raw SQL bindings, and raw provider payloads.

Redacted values must be removed or replaced with one constant marker. Redaction must not preserve prefixes, suffixes, lengths, hashes, or reversible encodings of secrets.

Redaction is defense in depth; it does not authorize callers to pass broad objects to the logger.

### 7.5 Correlation ID lifecycle

Implement one application-owned correlation helper that:

1. Reads an incoming correlation header only at the trusted web boundary.
2. Accepts it only if it matches a strict bounded format. Use an opaque UUID or similarly constrained identifier; do not accept arbitrary text.
3. Generates a cryptographically strong identifier when the incoming value is absent or invalid.
4. Makes the identifier available to server-side logging during the request without global mutable state.
5. Returns the identifier in one documented response header, such as `x-correlation-id`.
6. Makes a safe request reference available to the public error mapper and error UI.

Use `AsyncLocalStorage` only if it is compatible with the accepted Next.js runtime and actual execution paths. Do not use it in the Edge runtime. Do not rely on a module-level mutable variable.

Do not implement distributed tracing or honor `traceparent` as trusted correlation state in this task. Document how a future tracing adapter could coexist with the application correlation ID.

### 7.6 Request lifecycle logging

Add minimal server-side lifecycle logging at an appropriate Node-runtime boundary:

- Request started or completed using safe route labels.
- Method, safe route template, status/result code, correlation ID, and bounded duration.
- No automatic request/response serialization.
- Expected health/static/framework traffic may be excluded or sampled only through explicit documented rules.

If the accepted Next.js version cannot reliably provide status and duration from middleware/proxy without invasive wrapping, implement the smallest truthful boundary and document the limitation. Never report fabricated success status or duration.

### 7.7 Typed error taxonomy

Create a small taxonomy under `src/shared/errors/`:

- Base trusted application error with stable internal code and safe classification.
- Domain error for violated business invariants.
- Validation/input error.
- Authentication and authorization placeholders only if needed for mapping contracts; do not implement auth behavior.
- Conflict/not-found/state error as justified by current requirements.
- Infrastructure/dependency error whose raw cause remains internal.
- Unknown-error normalization.

Each trusted error must carry only the minimum required properties. Do not store request bodies, candidate data, provider payloads, SQL, headers, secrets, or arbitrary metadata on the error.

Preserve JavaScript `cause` internally where supported, but never serialize the cause into public responses or unrestricted logs.

### 7.8 Public error model and mapping

Create a single mapper from unknown/internal errors to a safe immutable public model. Align the HTTP representation with RFC 9457 where practical, for example:

```json
{
  "type": "about:blank",
  "title": "Unable to complete the request",
  "status": 500,
  "code": "INTERNAL_ERROR",
  "correlationId": "opaque-request-reference"
}
```

Rules:

- Use stable machine-readable public codes from a closed union.
- User-visible `title` and optional `detail` text must come from an allowlist, never from `error.message` by default.
- Do not return a stack, error name, database error, SQL, file path, provider response, raw cause, validation library internals, or server configuration.
- Treat unknown thrown values as internal failures.
- Use appropriate reviewed status codes without revealing whether a protected record exists.
- Set `application/problem+json` for problem responses from route handlers.
- Include the correlation ID in the response body and response header for errors.
- Do not expose internal opaque actor/record references.

### 7.9 Safe demonstration route or handler

Exercise the mapper through the smallest non-business route handler or test-only fixture that fits the accepted repository. It must not create a public production endpoint capable of intentionally throwing arbitrary errors.

Prefer testing the route adapter directly. If a demonstration endpoint is necessary, constrain it to the test environment and prove production refuses it. Do not add a generic debug, echo, exception, log-viewing, or log-download endpoint.

### 7.10 Safe error UI

Implement the applicable Next.js App Router error boundary files for the existing public/candidate/staff foundation:

- A global fatal-error fallback when technically required by the accepted framework.
- Segment-level error UI where it materially improves recovery.
- A concise generic message, safe retry action where appropriate, and request reference.
- Accessible heading, focus behavior, keyboard operation, and live/error semantics without repeatedly announcing technical details.
- No stack trace, digest, internal error message, route internals, SQL, provider name/payload, personal data, or secret.

Next.js-generated `digest` values are not the system's correlation ID. Do not label a digest as a request reference unless the application has explicitly and safely mapped it.

### 7.11 Development behavior

- Production/test logging output remains structured JSON.
- Local pretty-printing, if used, is opt-in and development-only.
- Test log capture uses an in-memory destination or controlled stream, not console monkey-patching when a supported logger destination is available.
- Tests must be able to assert parsed log objects without printing canaries to ordinary test output.
- Never weaken error sanitization in development route responses.

### 7.12 Documentation and scripts

Document:

- Log field allowlist.
- Forbidden fields and object types.
- Correlation header name and validation rule.
- Public error schema and code registry.
- How developers create a child logger and map an error.
- How tests safely capture logs.
- The distinction between operational logs and future business audit records.

Add only scripts needed to run M0.5-focused tests if existing M0.4 scripts cannot express them cleanly.

## 10. Security and Privacy Rules

- Use synthetic canaries only; never use real personal, candidate, employee, medical, screening, banking, or credential data.
- Canary values must be unmistakably fake and must not resemble usable credentials.
- Never log whole objects and then depend solely on path redaction.
- Never interpolate untrusted text into log messages; record reviewed codes and safe bounded fields.
- Sanitize newline/control characters if any bounded external identifier can reach a log field.
- Prevent log injection and unbounded-cardinality field creation.
- Never expose environment variables or configuration objects in errors.
- Never use `JSON.stringify(error)` as a public response.
- Never return `error.message` for an unknown or infrastructure error.
- Never suppress or swallow a required future audit failure; operational logging and business audit are different obligations.
- No test may place a sensitive canary in ordinary console output, snapshots, Playwright artifacts, or failure messages.

## 11. Tests Required in This Task

### 11.1 Logger contract and schema

- Emits valid structured JSON with timestamp/level and allowlisted context.
- Child context preserves correlation ID and approved fields.
- Disallowed broad context is rejected by types where possible.
- Test and production modes do not require a pretty printer.

### 11.2 Redaction and leakage resistance

Using synthetic canaries, prove they are absent from serialized logs when placed in:

- Nested password/token/session/authorization fields.
- Request-like headers, cookies, body, and query objects presented to the low-level defensive boundary.
- SSN/TIN, banking, identity, medical, screening, document, signed-URL, SQL-binding, and provider-payload fields.
- Error message, stack, and nested `cause` from an unknown/infrastructure error.

Also assert the constant redaction marker or field omission as designed. Search the complete captured output, not only selected parsed fields.

### 11.3 Correlation behavior

- Missing incoming ID generates a valid new ID.
- Valid bounded incoming ID is preserved according to the documented trust rule.
- Invalid, oversized, whitespace/control-character, and injection-shaped IDs are rejected and replaced.
- Concurrent requests do not leak IDs across contexts.
- Response header and public error body use the same correlation ID.

### 11.4 Error normalization and mapping

- Every trusted error class maps to its approved public code/status/title.
- Unknown `Error`, string, object, promise rejection, database-like error, and provider-like error map to the generic internal response.
- Internal code/cause/message/stack/SQL/path/provider payload never appears in the public model.
- Protected-resource not-found/forbidden behavior remains non-enumerating where the contract requires it.

### 11.5 UI behavior

- Error UI renders a generic accessible message and request reference.
- Retry/reset control works through user interaction when provided.
- Keyboard and screen-reader queries locate the heading, message, reference, and action.
- Technical fields and canaries are absent from rendered content.

### 11.6 Route/adapter behavior

- Problem response uses the documented media type, safe schema, status, and header.
- Successful behavior is unchanged.
- No request body, headers, query, cookies, or full URL is logged.
- Unexpected errors produce one safe error log with correlation and stable code, without duplicate leakage.

### 11.7 Browser smoke regression

- `/`, `/candidate`, and `/staff` still pass critical Chromium and accessibility smoke tests.
- No new unexpected console or page error appears.
- If an error-boundary E2E fixture is used, it is unavailable in production mode or is an internal deterministic test route with no arbitrary input.

## 12. Acceptance Criteria

### AC-M0.5-01 — Stable minimal logging dependency

The implementation uses a stable Pino-compatible logger behind an application-owned interface and adds no external telemetry or logging service.

### AC-M0.5-02 — Allowlisted structured schema

Operational logs are valid structured records containing only approved bounded fields; request/response bodies and broad objects are not logged by default.

### AC-M0.5-03 — Pre-serialization redaction

Central redaction removes designated synthetic secrets and sensitive values before bytes reach the destination.

### AC-M0.5-04 — Safe correlation lifecycle

Every exercised request receives one valid correlation ID, invalid incoming IDs are replaced, concurrent contexts remain isolated, and the same ID appears in safe logs and response references.

### AC-M0.5-05 — Framework-neutral error taxonomy

Typed internal errors and unknown-error normalization exist without importing framework, ORM, logger, or provider types into shared/domain error primitives.

### AC-M0.5-06 — Closed public error mapping

Public errors use stable allowlisted codes, titles, and statuses; raw messages, causes, stacks, SQL, paths, provider data, and sensitive fields are excluded.

### AC-M0.5-07 — Safe accessible error UI

The Next.js error fallback provides generic recovery guidance and a request reference, works by keyboard, and exposes no technical or sensitive detail.

### AC-M0.5-08 — No body or credential logging

Automated tests prove request bodies, authorization/cookie/session values, and designated privacy canaries never enter serialized logs.

### AC-M0.5-09 — Honest lifecycle logging

Logged request status/result and duration are based on observable data; the implementation does not fabricate completion, success, or timing information.

### AC-M0.5-10 — Controlled development diagnostics

Optional local formatting is development-only; test and production output remains machine-readable and sanitization rules do not weaken by environment.

### AC-M0.5-11 — Documentation complete

Developers can find the field allowlist, forbidden data, correlation contract, public code registry, safe usage examples, and audit/logging distinction.

### AC-M0.5-12 — Foundation regression safety

All accepted M0.1–M0.4 validation remains green, including migration/integration and critical browser/accessibility tests.

### AC-M0.5-13 — Deterministic repeatability

The focused M0.5 suite and full foundation suite pass twice consecutively without order dependence, stale context, leaked handles, or arbitrary sleeps.

### AC-M0.5-14 — Scope containment
