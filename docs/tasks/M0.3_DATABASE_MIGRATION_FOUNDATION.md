Establish the database foundation without implementing hiring-domain entities.

Deliver:

- Verification that all migrations reproduce the expected schema from an empty PostgreSQL database.

## 6. Database Approach

### 6.1 Source of truth

The source of truth is:

1. TypeScript Drizzle schema definitions.
2. Generated and human-reviewed SQL migrations committed under `drizzle/`.
3. Drizzle migration snapshots/journal metadata committed as required by the selected stable version.

The live database is never the source of truth for normal development.

### 6.2 Prohibited schema paths

- Do not use `drizzle-kit push` in package scripts, CI, shared environments, or documentation.
- Do not edit a migration after it has been accepted/applied; add a forward migration.
- Do not use `drizzle-kit pull` to replace the approved code-first schema.
- Do not create or alter tables from application startup.
- Do not run migrations automatically from every Next.js web replica.
- Do not use ORM auto-sync behavior.
- Do not execute generated SQL without reviewing it.

### 6.3 Schemas

Use:

- PostgreSQL schema `app` for application-owned tables.
- PostgreSQL schema `drizzle` for the migration journal, using the current stable Drizzle configuration options.
- Avoid application tables in `public`.

Do not create per-module PostgreSQL schemas in Release 1. Module ownership is enforced through code boundaries and naming, while the relational model remains within `app` unless an approved ADR changes it.

### 7.2 Environment variables

Extend typed environment validation with separate server/tool configuration:

| Variable | Consumer | Purpose |
|---|---|---|
| `DATABASE_URL` | Web/worker runtime | Least-privileged application connection |
| `DATABASE_MIGRATION_URL` | Migration/generation verification tools | DDL-capable migration connection |
| `DATABASE_ADMIN_URL` | Local bootstrap only | Creates/grants local roles; never imported by application runtime |
| `DATABASE_POOL_MAX` | Runtime | Bounded positive integer with conservative local default |
| `DATABASE_CONNECTION_TIMEOUT_MS` | Runtime/tools | Bounded connection timeout |
| `DATABASE_IDLE_TIMEOUT_MS` | Runtime | Bounded idle timeout |

Rules:

- Never expose these variables through `NEXT_PUBLIC_*`.
- Error messages name a variable but never print a full URL or password.
- Runtime configuration must not require `DATABASE_ADMIN_URL` or `DATABASE_MIGRATION_URL`.
- Migration tools must never silently fall back to `DATABASE_URL`.
- Local bootstrap must never run when `APP_ENV` is not `local` or `test`.
- Production requires an approved TLS setting later; this task must not invent a production certificate policy.

Update `.env.example` with obvious local-only example values matching the approved M0.2 database and role design.

### 7.3 Local database roles

Create or adapt a safe, idempotent local bootstrap mechanism that establishes:

- `psa_local_admin`: local database owner/bootstrap identity.
- `psa_migrator`: migration identity with required DDL authority for `app` and migration-journal objects.
- `psa_app`: runtime identity with data access but no schema/table creation or role management.

If M0.2 already chose a different approved owner name, preserve it and document the mapping rather than destroying the volume.

Required privilege intent:

| Capability | Admin | Migrator | Application |
|---|---:|---:|---:|
| Create/alter roles | Local bootstrap only | No | No |
| Create/alter `app` schema objects | Yes | Yes | No |
| Manage Drizzle migration journal | Yes | Yes | No |
| Connect to database | Yes | Yes | Yes |
| Use `app` schema | Yes | Yes | Yes |
| Select/insert/update/delete app tables | Yes | Yes | Yes |
| Create/drop database | Local bootstrap only if required | No | No |
| Bypass row-level security/superuser | No application need | No | No |

Set default privileges for objects created by the migration role so the application role receives only required table/sequence access for future migrations.

The local bootstrap must:

- Be idempotent.
- Use only fixed, reviewed local role/database identifiers.
- Avoid logging passwords or complete URLs.
- Work with an existing M0.2 volume when safely possible.
- Refuse staging/production.
- Never drop roles, databases, schemas, tables, or data.
- Report a manual recovery step rather than suggesting volume deletion when it cannot repair an existing local role layout safely.

An official PostgreSQL entrypoint initialization script may support new volumes, but an idempotent explicit command is still required for existing accepted M0.2 volumes.

- Migration database credentials from `DATABASE_MIGRATION_URL` only.

- Schema filter/configuration that avoids treating unrelated schemas as application schema when the stable API supports it.
- Clear breakpoints/verbosity choices documented in the file or README.

Do not place a credential-bearing URL literal in this file.

### 7.6 Initial technical table

Create only this application-owned table:

```text
app.system_metadata
```

Purpose: store non-secret technical metadata required to confirm that the database was initialized and seeded by the correct application foundation.

Required columns:

| Column | Type/behavior |
|---|---|
| `key` | Bounded text/varchar primary key |
| `value` | `jsonb`, required; non-secret technical data only |
| `created_at` | Timezone-aware timestamp, required, database default current time |
| `updated_at` | Timezone-aware timestamp, required, database default current time |

Rules:

- Use snake_case SQL names and idiomatic TypeScript property names according to the approved Drizzle convention.
- `updated_at` does not update magically; the seed/upsert explicitly changes it.
- Do not add generic application settings, feature flags, secrets, candidate data, audit data, or arbitrary business configuration.
- JSON is permitted here only for bounded technical metadata; it must not become a substitute for future relational business fields.
- Use the `app` PostgreSQL schema.

### 7.7 Initial migration

Generate a named migration such as `initialize_database_foundation` using Drizzle Kit.

Review and commit:

- Generated SQL.
- Required migration metadata/snapshot.
- Creation of `app` schema if supported by schema generation; otherwise use an approved custom SQL step within the committed migration.
- Creation of `app.system_metadata`.
- No unexpected tables, extensions, roles, grants, or destructive statements.

Role creation and environment-specific passwords do not belong in the portable application migration. Local-role bootstrap remains separate.

### 7.8 Connection pool

Create a lazy server-only pool using `pg.Pool` and pass it to Drizzle through the official node-postgres adapter.

Requirements:

- Use `DATABASE_URL` only.
- Create the pool lazily, not during browser import or static build evaluation.
- Apply bounded `max`, connection timeout, and idle timeout from validated configuration.
- Set an application name that identifies the PSA web/worker process without personal data.
- Establish UTC session behavior where needed and verify it.
- Add a pool error listener that sends only safe operational context to the current logging boundary; until M0.5, avoid a bespoke logger and never print connection strings.
- Provide explicit `closeDatabasePool()` for scripts/tests/process shutdown.
- Avoid pool proliferation during Next.js development hot reload using a documented global singleton pattern if required.
- Do not retain a checked-out client globally.
- Do not expose raw pool/client objects to UI code.
- Do not set production TLS to insecure certificate bypass.

### 7.9 Database scripts

Add TypeScript scripts equivalent to:

```text
scripts/db/bootstrap-local.ts
scripts/db/check.ts
scripts/db/migrate.ts
scripts/db/seed.ts
scripts/db/verify-empty.ts
```

Responsibilities:

#### `bootstrap-local.ts`

- Validate local/test environment.
- Idempotently create/grant local roles and schema prerequisites.
- Never destroy data.
- Close admin pool/client in `finally`.

#### `check.ts`

- Connect through the application identity.
- Execute bounded safe checks such as `SELECT 1`.
- Verify PostgreSQL version is expected/supported.
- Verify session timezone is UTC.
- Verify `app.system_metadata` exists after migrations.
- Verify application role cannot create a table/schema.
- Avoid printing URLs or credentials.
- Close the pool.

#### `migrate.ts`

- Use `DATABASE_MIGRATION_URL` only.
- Apply committed migrations from `drizzle/`.
- Use the configured journal schema/table.
- Fail nonzero on error.
- Close connection in `finally`.
- Never seed automatically.

#### `seed.ts`

- Use deterministic synthetic/non-secret technical metadata only.
- Insert/upsert a key such as `foundation.seed` with a versioned JSON value.
- Be idempotent.
- Use the application identity if its privileges permit ordinary DML.
- Never add candidate/staff accounts or business records.
- Close the pool.

#### `verify-empty.ts`

- Operate only against a clearly identified disposable local/test database.
- Refuse the normal developer database unless an explicit safe disposable database URL/name is supplied.
- Create or use the disposable database through approved test setup.
- Apply all committed migrations from empty.
- Verify expected schemas/table/constraints/privileges.
- Clean up only the exact disposable database it created after validating its name and environment.
- Never use broad shell variables, globs, or production-like hosts.

If safe automated disposable-database creation would add excessive complexity before M0.4, a Docker Compose run with a uniquely named temporary database/container is acceptable. The exact destructive target must be explicit and validated.

## 10. Migration Review Checklist

Before applying a generated migration, confirm:

- SQL matches the TypeScript schema.
- Only `app` and expected migration-journal objects are affected.
- No `DROP`, data truncation, role creation, secret, or unexpected extension.
- Table and column names follow conventions.
- Primary key and not-null constraints are correct.
- Timestamps use timezone-aware PostgreSQL types.
- JSONB default/constraints do not hide missing required application logic.
- Migration is deterministic.
- SQL contains no environment-specific passwords/URLs.
- Migration metadata/snapshot is committed.

Record the review in the completion report.

## 11. Safety and Security Requirements

- Database URLs are secrets even in local diagnostics; never log complete URLs.
- No credential appears in thrown validation text, command output captured by scripts, or README beyond explicit local-only placeholder values.
- Application code uses only the least-privileged URL.
- Migration/admin URLs are loaded only by tool entry points.
- Scripts close pools/clients in `finally`.
- SQL values are parameterized.
- Dynamic SQL identifiers are prohibited except fixed reviewed local role/database names.
- The application role cannot create/alter/drop schemas or tables.
- The migration role is not used for application queries.
- No public network exposure is added.
- No real personal information is seeded.
- The disposable verification target is validated before any create/drop operation.
- No normal command deletes the local volume/database.

- Local bootstrap is idempotent.
- Initial migration applies once and a second run is a no-op.

- Normal developer database/volume remains intact after disposable verification.

Use temporary/disposable targets carefully and never print credentials.

## 13. Acceptance Criteria

### AC-M0.3-01 — Stable database dependencies

Given the completed task, when dependencies are reviewed, then stable compatible Drizzle ORM, Drizzle Kit, `pg`, and `@types/pg` versions are pinned and no prerelease database package is present.

### AC-M0.3-02 — Separate connection purposes

Given configuration, then runtime code requires only `DATABASE_URL`, migration tooling requires `DATABASE_MIGRATION_URL`, local bootstrap alone uses `DATABASE_ADMIN_URL`, and no tool silently substitutes one for another.

### AC-M0.3-03 — Least-privileged local roles

Given the local database is bootstrapped, then application and migration identities are distinct; the application identity can perform expected DML but cannot create/alter/drop schema objects or manage roles.

### AC-M0.3-04 — Code-first migration source

Given a schema change, when `pnpm db:generate` runs, then Drizzle compares committed TypeScript schema/snapshots and produces reviewable SQL under `drizzle/`; no push/sync script exists.

### AC-M0.3-05 — Initial technical schema

Given an empty approved local/test database, when committed migrations are applied, then `app.system_metadata` and the configured Drizzle migration journal exist with the expected columns and constraints, and no business-domain table exists.

### AC-M0.3-06 — Repeatable migration

Given the initial migration is already applied, when `pnpm db:migrate` runs again, then it succeeds without duplicating or changing the table unexpectedly.

### AC-M0.3-07 — Safe connection pool

Given valid runtime configuration, when the application database client is first requested, then one bounded lazy pool is created, Drizzle uses that pool, and the pool can be explicitly drained without leaking checked-out clients.

### AC-M0.3-08 — UTC behavior

Given a runtime connection, when timezone is checked and timestamps are inserted/read, then the database session and stored timestamp semantics follow UTC requirements.

### AC-M0.3-09 — Idempotent synthetic seed

Given migrations are applied, when `pnpm db:seed` runs repeatedly, then one deterministic non-secret technical metadata record exists with an updated timestamp and no candidate/staff/business data is created.

### AC-M0.3-10 — Empty-database reproducibility

Given an explicitly disposable local/test database, when `pnpm db:verify-empty` runs, then all committed migrations reproduce the expected schema and the verification cleans up only its validated disposable target.

### AC-M0.3-11 — Safe failures

Given invalid/missing credentials, unavailable database, insufficient privilege, or migration error, when a database command runs, then it exits nonzero with an actionable safe message, closes resources, and prints no password or credential-bearing URL.

### AC-M0.3-12 — Existing application remains healthy

Given M0.1/M0.2 were accepted, when M0.3 is complete, then infrastructure checks, lint, typecheck, format-check, and production build still pass and the three foundation routes remain functional.

### AC-M0.3-13 — Scope containment

Given the completed change, when tables, dependencies, routes, and source files are reviewed, then no authentication, audit, job, hiring-domain, provider, UI data-access, production infrastructure, or destructive reset functionality has been added.
